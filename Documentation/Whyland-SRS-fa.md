## 1. مقدمه و دامنه پروژه

### 1.1 هدف

این سند نیازمندی‌های عملکردی و غیرعملکردی یک پلتفرم آموزش آنلاین را تعریف می‌کند که به کاربران امکان می‌دهد دوره‌های آنلاین را کشف کنند، خریداری کنند و به آن‌ها دسترسی داشته باشند.

این پلتفرم شامل موارد زیر است:

1. یک وب‌سایت عمومی پیاده‌سازی‌شده با ASP.NET Core MVC.
2. یک پنل مدیریت پیاده‌سازی‌شده با ASP.NET Core Razor Pages.
3. یک سیستم احراز هویت و مجوزدهی سفارشی بدون استفاده از ASP.NET Core Identity.
4. یک پایگاه‌داده رابطه‌ای PostgreSQL.
5. Redis برای ذخیره‌سازی سبد خرید و کش.
6. ذخیره‌سازی ویدیوها و فایل‌های دانلودی دوره‌ها در پوشه `wwwroot` برنامه.
7. یک زیرساخت مشاهده‌پذیری (Observability) مبتنی بر Serilog، OpenTelemetry، Grafana Loki، Grafana Tempo و Prometheus.

هدف از این SRS ارائه نیازمندی‌هایی با دقت کافی است تا پلتفرم وایلند بدون تکیه بر فرضیات کسب‌وکاری مستندنشده قابل پیاده‌سازی باشد. وایلند به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود تا معماری نرم‌افزاری تولید-محور، توسعه بک‌اند، توسعه وب، مجوزدهی، پایداری داده‌ها (Persistence)، پرداخت و مشاهده‌پذیری را نشان دهد.

### 1.2 بستر پروژه

وایلند یک پلتفرم آموزشی است که به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود. اگرچه هدف اصلی این پروژه یادگیری و نمایش مهارت‌های مهندسی است، اما معماری و نیازمندی‌های آن باید تا جای ممکن از رویه‌های تولید-محور پیروی کند.

پیاده‌سازی باید جداسازی روشن دغدغه‌ها (Separation of Concerns)، کد قابل نگهداری، قواعد کسب‌وکاری واقع‌گرایانه، احراز هویت و مجوزدهی امن، پردازش قابل‌اعتماد سفارش/پرداخت، و مشاهده‌پذیری کامل برنامه را نشان دهد.

### 1.3 دامنه پروژه

#### 1.3.1 در دامنه پروژه

سیستم باید موارد زیر را فراهم کند:

- دسته‌بندی‌های سلسله‌مراتبی دوره با حداکثر عمق سه سطح.
- ایجاد و مدیریت دوره.
- بخش‌ها (Sections) و اپیزودهای دوره.
- اپیزودهای پیش‌نمایش رایگان برای دوره‌های پولی.
- پیوست‌های اپیزود با محدودیت‌های قابل‌پیکربندی.
- ذخیره‌سازی و پخش محافظت‌شده ویدیوهای MP4 و فایل‌های دانلودی دوره‌ها از پوشه `wwwroot`.
- سوالات متداول اختصاصی هر دوره.
- بلاگ عمومی.
- سوالات متداول عمومی.
- کاربران پویا.
- نقش‌های پویا.
- مجوزهای پویا.
- تخصیص مجوز بر پایه نقش.
- احراز هویت با شماره تلفن.
- یک سرویس پیامک ساختگی (Fake) برای توسعه/تست.
- احراز هویت با گوگل.
- الزام دریافت شماره تلفن قبل از خرید.
- مدیریت پروفایل کاربر.
- پروفایل مدرسان.
- علاقه‌مندی‌های دوره (Favorites).
- دسترسی به دوره‌های خریداری‌شده.
- سبدهای خرید مبتنی بر Redis.
- سفارش‌ها و اقلام سفارش.
- روش‌های پرداخت که با یک enum نمایش داده می‌شوند.
- رکوردهای پرداخت.
- فاکتورها.
- کوپن‌های تخفیف قابل‌اعمال در سبد خرید و فرآیند پرداخت.
- تنظیمات پویای سایت.
- صفحات عمومی MVC.
- پنل مدیریت Razor Pages.
- مجوزدهی بر پایه Permission.
- ثبت لاگ ساختاریافته.
- ردیابی توزیع‌شده (Distributed Tracing).
- متریک‌ها.
- داشبوردهای Grafana.
- مدیریت خطاهای 403، 404 و 500.

#### 1.3.2 خارج از دامنه پروژه

موارد زیر صراحتاً خارج از دامنه پیاده‌سازی اول هستند:

- یکپارچه‌سازی با سرویس واقعی پیامک.
- یکپارچه‌سازی واقعی با پرداخت گوگل.
- یکپارچه‌سازی واقعی با درگاه بانکی.
- یکپارچه‌سازی واقعی با زرین‌پال.
- یکپارچه‌سازی واقعی با اسنپ‌پی.
- پردازش تسویه‌حساب/پرداخت به مدرسان.
- یادداشت‌های شخصی کاربر روی اپیزودها.
- اپلیکیشن موبایل بومی (Native).
- یک فرانت‌اند SPA جداگانه.
- ASP.NET Core Identity.

ارائه‌دهندگان پرداخت فقط باید از طریق انتزاع/enum روش پرداخت و یک مرز (Boundary) مناسب در سطح برنامه نمایش داده شوند. پیاده‌سازی واقعی ارائه‌دهندگان در این نسخه الزامی نیست.

### 1.4 اصطلاحات

| اصطلاح                          | تعریف                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------ |
| کاربر (User)                    | حسابی که می‌تواند احراز هویت شده و از پلتفرم استفاده کند.                                  |
| مدرس (Instructor)               | کاربری که با اطلاعات پروفایل اختصاصی مدرس مرتبط است و ممکن است به دوره‌ها تخصیص یابد.      |
| نقش (Role)                      | مجموعه‌ای پویا و قابل‌مدیریت از مجوزها.                                                    |
| مجوز (Permission)               | یک قابلیت مجوزدهی با نام مشخص که با یک کلید یکتا شناسایی می‌شود.                           |
| دوره (Course)                   | یک محصول آموزشی قابل‌خرید یا رایگان.                                                       |
| بخش (Section)                   | یک گروه‌بندی منطقی از اپیزودها درون یک دوره.                                               |
| اپیزود (Episode)                | یک درس آموزشی مجزا درون یک بخش.                                                            |
| سبد خرید (Cart)                 | مجموعه‌ای موقت از دوره‌ها که در Redis ذخیره می‌شود.                                        |
| سفارش (Order)                   | یک درخواست خرید پایدارشده که از سبد خرید تولید می‌شود.                                     |
| قلم سفارش (Order Item)          | یک ردیف دوره درون یک سفارش.                                                                |
| پرداخت (Payment)                | یک تراکنش مالی مرتبط با یک سفارش.                                                          |
| فاکتور (Invoice)                | یک سند مالی که نشان‌دهنده یک سفارش/پرداخت تکمیل‌شده است.                                   |

### 2.6 CQRS و MediatR

Commandها باید وضعیت را تغییر دهند.

Queryها باید داده را بدون تغییر وضعیت کسب‌وکاری بازیابی کنند.

MediatR باید به‌عنوان مکانیزم Dispatch برنامه برای Commandها و Queryها، در جایی که مرتبط است، استفاده شود.

دغدغه‌های میان‌بُرشی (Cross-Cutting) مانند:

- اعتبارسنجی.
- ثبت لاگ.
- اندازه‌گیری عملکرد.
- مدیریت تراکنش، در جایی که مرتبط است.

می‌توانند از طریق Pipeline Behaviorهای MediatR پیاده‌سازی شوند.

### 2.7 Result Pattern

عملیات Application باید از یک Result Pattern استفاده کنند، نه استفاده از استثناها به‌عنوان مکانیزم عادی برای خطاهای کسب‌وکاری موردانتظار.

خطاهای موردانتظار می‌توانند شامل موارد زیر باشند:

- دوره یافت نشد.
- محدودیت سلسله‌مراتب دسته‌بندی رد شده.
- کاربر غیرفعال.
- مجوز رد شده.
- شماره تلفن الزامی.
- تخفیف نامعتبر.
- دوره برای فروش در دسترس نیست.
- دسترسی ناکافی به دوره.
- وضعیت پرداخت نامعتبر.

خطاهای غیرمنتظره زیرساختی/سیستمی همچنان باید از مدیریت استثنا و مدیریت خطای متمرکز استفاده کنند.

### 3.2 نیازمندی‌های Repository و Unit of Work

#### 3.2.1 الگوی Repository

دسترسی به پایداری داده‌ها (Persistence) باید از طریق Repository انتزاع شود.

Repositoryها باید حول Aggregate Rootها و عملیات معنادار Domain تعریف شوند، نه با ایجاد یک Repository غیرضروری برای هر جدول پایگاه‌داده.

نمونه‌ها:

```text
ICourseWriteRepository / ICourseReadRepository
ICategoryWriteRepository / ICategoryReadRepository
IUserWriteRepository / IUserReadRepository
IRoleWriteRepository / IRoleReadRepository
IPermissionWriteRepository / IPermissionReadRepository
IOrderWriteRepository / IOrderReadRepository
IPaymentWriteRepository / IPaymentReadRepository
IBlogPostWriteRepository / IBlogPostReadRepository
```

جداسازی Repositoryهای خواندن و نوشتن در بخش 3.3 تعریف شده است.

Repositoryها باید:

- کوئری‌های اختصاصی پایداری داده را کپسوله کنند.
- مدل‌های Domain/Application متناسب با لایه را بازگردانند.
- از افشای `DbContext` به Handlerهای Application خودداری کنند.
- از نشت جزئیات پیاده‌سازی اختصاصی EF Core به Domain خودداری کنند.
- از عملیات ناهمگام (Asynchronous) پشتیبانی کنند.
- از Cancellation Token پشتیبانی کنند.

#### 3.2.2 Unit of Work

لایه Persistence باید یک انتزاع Unit of Work پیاده‌سازی کند.

نمونه:

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken cancellationToken);
}
```

`DbContext` مربوط به EF Core باید رفتار Unit of Work را پیاده‌سازی کند.

یک دستور (Command) واحد در برنامه که چندین موجودیت مرتبط را تغییر می‌دهد باید از یک مرز تراکنشی واحد Unit of Work در جایی که سازگاری (Consistency) لازم است استفاده کند.

نمونه:

```text
ایجاد سفارش
    |
    +-- ایجاد سفارش
    +-- ایجاد اقلام سفارش
    +-- خالی‌کردن/مصرف سبد خرید
    +-- ذخیره تغییرات
```

این عملیات نباید منجر به یک سفارش به‌صورت ناقص ذخیره‌شده شوند.

#### 3.2.3 قواعد تراکنش

در جایی که چندین تغییر پایگاه‌داده باید با هم موفق یا ناموفق شوند، باید از یک تراکنش پایگاه‌داده استفاده شود.

فراخوانی‌های سرویس خارجی نباید به‌اشتباه درون تراکنش‌های پایگاه‌داده طولانی‌مدت قرار گیرند.

Callbackهای پرداخت باید Idempotent (بی‌اثر در تکرار) باشند.

#### 3.2.4 محدودیت‌های Repository

موارد زیر باید کنار گذاشته شوند:

- Repository عمومی صرفاً برای انتزاع CRUD.
- افشای `IQueryable` از Repositoryها در جایی که موجب نشت دغدغه‌های Persistence می‌شود.
- دسترسی مستقیم به `DbContext` از Controllerها، Razor Pageها یا Handlerهای MediatR.
- پیاده‌سازی قواعد کسب‌وکاری درون پیکربندی‌های EF Core.

### 3.3 معماری Repository

معماری Repository باید مسئولیت‌های **خواندن (Read)** و **نوشتن (Write)** را صراحتاً از هم جدا کند.

یک Repository عمومی و واحد نباید استفاده شود.

برنامه باید از Repositoryهای صریح که حول نیازمندی‌های واقعی کسب‌وکار طراحی شده‌اند استفاده کند.

#### 3.3.1 Repositoryهای نوشتن (Write)

Repositoryهای نوشتن باید مسئول عملیاتی باشند که وضعیت برنامه را تغییر می‌دهند.

نمونه‌ها:

```text
ICourseWriteRepository
ICategoryWriteRepository
IUserWriteRepository
IRoleWriteRepository
IPermissionWriteRepository
IOrderWriteRepository
IPaymentWriteRepository
IInvoiceWriteRepository
```

Repositoryهای نوشتن باید از **Entity Framework Core** استفاده کنند.

EF Core باید مسئول موارد زیر باشد:

- درج (Insert).
- به‌روزرسانی (Update).
- حذف نرم (Soft Delete).
- تغییرات روابط.
- ردیابی تغییرات (Change Tracking) در جایی که لازم است.
- پایداری تراکنشی.

#### 3.3.2 Repositoryهای خواندن (Read)

Repositoryهای خواندن باید مسئول بازیابی داده باشند.

نمونه‌ها:

```text
ICourseReadRepository
ICategoryReadRepository
IUserReadRepository
IRoleReadRepository
IPermissionReadRepository
IOrderReadRepository
IPaymentReadRepository
IInvoiceReadRepository
```

Repositoryهای خواندن باید از **Dapper** استفاده کنند.

Dapper باید برای کوئری‌های خواندن‌محور، در جایی که Projection مستقیم SQL بازیابی داده ساده‌تر یا کارآمدتری فراهم می‌کند، ترجیح داده شود.

Repositoryهای خواندن باید به‌جای افشای غیرضروری موجودیت‌های EF Core، DTO/مدل‌های خواندن اختصاصی برنامه را بازگردانند.

#### 3.3.3 عدم استفاده از Repository عمومی

برنامه نباید یک Repository عمومی مانند موارد زیر را صرفاً برای ارائه عملیات CRUD پیاده‌سازی کند:

```csharp
IGenericRepository<T>
```

Repositoryها باید صریح و مبتنی بر Use-Case باشند.

برای مثال:

```csharp
public interface ICourseReadRepository
{
    Task<CourseDetailsDto?> GetDetailsAsync(
        Guid courseId,
        CancellationToken cancellationToken);
}
```

و:

```csharp
public interface ICourseWriteRepository
{
    Task AddAsync(
        Course course,
        CancellationToken cancellationToken);

    Task<Course?> GetForUpdateAsync(
        Guid courseId,
        CancellationToken cancellationToken);
}
```

انتزاع Repository باید نمایانگر عملیات معنادار برنامه باشد، نه صرفاً یک پوشش (Wrapper) روی APIهای پایگاه‌داده.

### 3.4 قواعد پایداری داده Read/Write

پیاده‌سازی Persistence باید از قواعد زیر پیروی کند. معماری نهایی Persistence به شکل زیر است:

```text
                 Presentation
              MVC / Razor Pages
                       |
                       v
                 Application
              CQRS / MediatR
                       |
              +--------+--------+
              |                 |
              v                 v
       Read Repositories   Write Repositories
              |                 |
            Dapper            EF Core
              |                 |
              +--------+--------+
                       |
                   PostgreSQL
```

#### 3.4.1 عملیات خواندن

کوئری‌ها باید:

- از Dapper از طریق Repositoryهای خواندن استفاده کنند.
- Projectionهای صریح SQL را ترجیح دهند.
- DTO/مدل‌های خواندن را بازگردانند.
- از بارگذاری کامل گراف Aggregate در جایی که فقط یک Projection لازم است خودداری کنند.
- از Pagination برای نتایج بزرگ پشتیبانی کنند.

#### 3.4.2 عملیات نوشتن

دستورها (Commands) باید:

- از EF Core از طریق Repositoryهای نوشتن استفاده کنند.
- قواعد کسب‌وکاری را در لایه Application/Domain اعمال کنند.
- در جایی که چندین تغییر باید به‌صورت سازگار ذخیره شوند از Unit of Work استفاده کنند.
- در جایی که Atomicity لازم است از تراکنش استفاده کنند.

#### 3.4.3 مرز DbContext

`DbContext` باید یک جزئیات پیاده‌سازی Infrastructure باقی بماند.

Controllerها، Razor Pageها و Handlerهای Application نباید مستقیماً به `DbContext` دسترسی داشته باشند.

### 3.5 یکپارچگی داده

پایگاه‌داده باید محدودیت‌های مناسب را اعمال کند، از جمله:

- فیلدهای الزامی.
- فیلدهای یکتا.
- کلیدهای خارجی.
- روابط ترکیبی یکتا.
- نمایش‌های معتبر enum در جایی که مرتبط است.

Invariantهای مهم کسب‌وکاری باید در لایه Application/Domain اعمال شوند و صرفاً به اعتبارسنجی رابط کاربری تکیه نکنند.

### 3.6 همزمانی (Concurrency)

عملیاتی که می‌توانند به‌صورت همزمان فعال شوند باید طوری طراحی شوند که از وضعیت ناسازگار جلوگیری شود.

نمونه‌های مهم:

- دو Callback پرداخت برای یک تراکنش یکسان.
- دو درخواست Checkout برای یک سبد خرید یکسان.
- درخواست‌های علاقه‌مندی تکراری.
- تخصیص همزمان مجوز به نقش.
- پردازش همزمان سفارش.
- استفاده همزمان از کوپن.
- رقابت انقضای سفارش در انتظار با نتیجه پرداخت.

محدودیت‌های یکتای پایگاه‌داده و Idempotency در سطح برنامه باید در جایی که لازم است با هم استفاده شوند.

### 3.7 کش

Redis باید برای موارد زیر استفاده شود:

- سبدهای خرید.
- وضعیت موقت OTP در صورت لزوم.
- ورودی‌های کش برنامه که صراحتاً پیکربندی شده‌اند.

داده‌های کش‌شده باید یک سیاست انقضا داشته باشند.

داده‌های حیاتی کسب‌وکاری پایدارشده نباید فقط در Redis وجود داشته باشند.

### 3.8 مایگریشن پایگاه‌داده

باید از مایگریشن‌های Entity Framework Core استفاده شود.

تغییرات schema پایگاه‌داده باید از کنترل سورس قابل‌بازتولید باشند.

راهبرد مایگریشن پایگاه‌داده Production نباید به ویرایش دستی پایگاه‌داده تکیه کند.

## 4. حذف داده و حسابرسی (Audit)

### 4.1 راهبرد حذف داده (Data Deletion Strategy)

برنامه باید به‌صورت پیش‌فرض از **Soft Delete** استفاده کند.

حذف فیزیکی (Physical Delete) نباید برای موجودیت‌های عادی برنامه استفاده شود، مگر در صورتی که یک نیازمندی فنی یا کسب‌وکاری مشخص صراحتاً حذف دائمی را الزامی کند.

#### 4.1.1 فیلدهای Soft Delete

موجودیت‌هایی که از حذف پشتیبانی می‌کنند باید شامل موارد زیر باشند:

| فیلد      | الزام                  |
| --------- | ---------------------- |
| IsDeleted | بولین الزامی           |
| DeletedAt | زمان (Nullable)        |
| DeletedBy | شناسه کاربر (Nullable) |

در جایی که مناسب باشد، موجودیت‌ها باید همچنین شامل موارد زیر باشند:

| فیلد      | الزام                                                  |
| --------- | ------------------------------------------------------ |
| CreatedBy | شناسه کاربر، Nullable/الزامی بسته به چرخه حیات موجودیت |
| UpdatedBy | شناسه کاربر، Nullable/الزامی بسته به چرخه حیات موجودیت |

فیلدهای حسابرسی (Audit) باید معمولاً شامل موارد زیر باشند:

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
IsDeleted
DeletedAt
DeletedBy
```

#### 4.1.2 رفتار پیش‌فرض کوئری‌ها

موجودیت‌های Soft-Delete‌شده نباید توسط کوئری‌های عادی برنامه بازگردانده شوند.

لایه Infrastructure باید این رفتار را در جایی که مناسب است از طریق Global Query Filter‌های EF Core پیاده‌سازی کند.

کوئری‌ای که صراحتاً به رکوردهای حذف‌شده نیاز دارد باید به‌صورت آشکار وارد این رفتار شود (Opt-in).

#### 4.1.3 حذف دائمی

حذف فیزیکی (Hard Delete) فقط برای موجودیت‌هایی مجاز است که حذف دائمی آن‌ها صراحتاً توجیه‌پذیر باشد.

نمونه‌ها می‌توانند شامل موارد زیر باشند:

- رکوردهای فنی موقت.
- رکوردهای مصرفی توسعه/تست.
- داده‌ای که طبق یک قاعده مستندشده کسب‌وکاری/حریم‌خصوصی صراحتاً باید به‌طور دائمی حذف شود.

رکوردهای مالی مانند پرداخت‌های موفق، سفارش‌های پرداخت‌شده و فاکتورهای صادرشده نباید از طریق عملیات مدیریتی عادی به‌صورت فیزیکی حذف شوند.

### 4.2 فیلدهای حسابرسی (Audit Fields)

برنامه باید اطلاعات حسابرسی ایجاد و تغییر را نگهداری کند.

حداقل، موجودیت‌های کسب‌وکاری‌ای که نیازمند قابلیت حسابرسی هستند باید شامل موارد زیر باشند:

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
```

در جایی که یک عملیات نمایانگر حذف باشد:

```text
DeletedAt
DeletedBy
IsDeleted
```

#### 4.2.1 CreatedBy

`CreatedBy` باید به کاربری اشاره کند که مسئول ایجاد رکورد است، در جایی که عملیات توسط یک کاربر احرازهویت‌شده انجام می‌شود.

برای رکوردهای تولیدشده توسط سیستم، می‌توان از یک هویت سیستمی مستندشده یا مقدار Nullable استفاده کرد.

#### 4.2.2 UpdatedBy

`UpdatedBy` باید به کاربری اشاره کند که مسئول آخرین تغییر است.

#### 4.2.3 DeletedBy

`DeletedBy` باید به کاربری اشاره کند که عملیات Soft-Delete را انجام داده است.

برنامه نباید به مقادیر ارسالی از سمت کلاینت برای این فیلدها اعتماد کند.

اطلاعات حسابرسی باید توسط لایه سرور/Application/Infrastructure پر شوند.

#### 4.2.4 قابلیت اعمال فیلدها

هر فیلد لزوماً برای هر موجودیت الزامی نیست، اما تمام موجودیت‌های پایدار کسب‌وکاری باید صراحتاً مشخص کنند کدام فیلدهای حسابرسی برای آن‌ها کاربرد دارد.

برای موجودیت‌های شرکت‌کننده در مجوزدهی، عملیات مالی، مدیریت محتوا و عملیات مدیریتی، قابلیت حسابرسی باید الزامی در نظر گرفته شود.

### 4.3 قابلیت حسابرسی (Auditability)

حداقل، موجودیت‌ها باید موارد زیر را نگه‌دارند (مطابق بخش 4.2):

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
```

عملیات مالی و مجوزدهی باید لاگ‌های ساختاریافته کافی برای ردیابی موارد زیر تولید کنند:

- چه کسی عملیات را انجام داده.
- چه عملیاتی رخ داده.
- کِی رخ داده.
- چه درخواست/ردیابی‌ای آن را آغاز کرده.

داده‌های حساس نباید لاگ شوند.

### 5.3 احراز هویت

این پلتفرم نباید از ASP.NET Core Identity استفاده کند.

احراز هویت باید با استفاده از مدل اختصاصی کاربر، اعتبارنامه، نقش و مجوز خود برنامه پیاده‌سازی شود.

#### 5.3.1 احراز هویت با شماره تلفن

سیستم باید از احراز هویت مبتنی بر شماره تلفن پشتیبانی کند.

جریان پایه:

```text
وارد کردن شماره تلفن
        |
        v
درخواست کد یک‌بارمصرف (OTP)
        |
        v
سرویس پیامک ساختگی
        |
        v
وارد کردن کد یک‌بارمصرف
        |
        v
اعتبارسنجی کد یک‌بارمصرف
        |
        v
احراز هویت کاربر
```

کد یک‌بارمصرف (OTP) باید:

- زمان انقضای قابل‌پیکربندی داشته باشد.
- حداکثر تعداد تلاش اعتبارسنجی قابل‌پیکربندی داشته باشد.
- پس از اعتبارسنجی موفق، باطل شود.
- در صورت ذخیره‌سازی، به‌صورت متن ساده ذخیره نشود.
- نرخ‌محدود (Rate Limited) باشد.

#### 5.3.2 سرویس پیامک ساختگی

یک اینترفیس ساده باید تعریف شود:

```csharp
public interface ISmsService
{
    Task SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

پیاده‌سازی محیط توسعه نباید پیامک واقعی ارسال کند.

این پیاده‌سازی می‌تواند:

- کد OTP را لاگ کند.
- آن را به‌صورت موقت برای اهداف تست ذخیره کند.
- یک نتیجه تحویل موفق بازگرداند.

سرویس ساختگی باید بدون تغییر منطق کسب‌وکاری Application قابل‌جایگزینی باشد.

### 5.4 احراز هویت با گوگل

احراز هویت Google OAuth/OpenID Connect باید پشتیبانی شود.

یک کاربر احرازهویت‌شده با گوگل باید بتواند یک حساب User محلی ایجاد کند یا به آن دسترسی داشته باشد.

حساب محلی باید از طریق یک رکورد ورود خارجی (External Login) مناسب به هویت خارجی گوگل متصل شود.

احراز هویت گوگل نباید جایگزین موجودیت User محلی شود.

### 5.5 الزام شماره تلفن قبل از خرید

یک کاربر می‌تواند بدون ارائه شماره تلفن با استفاده از گوگل احراز هویت شود.

با این حال، پیش از ایجاد یک سفارش قابل‌پرداخت، سیستم باید بررسی کند که شماره تلفن کاربر موجود و معتبر است.

جریان:

```text
ورود با گوگل
     |
     v
افزودن به سبد خرید
     |
     v
پرداخت (Checkout)
     |
     v
شماره تلفن موجود نیست؟
     |
    بله
     |
     v
دریافت شماره تلفن
     |
     v
ادامه فرآیند پرداخت
```

سیستم نباید اجازه دهد پرداخت بدون شماره تلفن الزامی انجام شود.

### 5.6 احراز هویت مبتنی بر Cookie

احراز هویت باید **مبتنی بر Cookie** باشد.

برنامه نباید از توکن‌های JWT Bearer به‌عنوان مکانیزم اصلی احراز هویت مرورگر استفاده کند.

#### 5.6.1 مکانیزم احراز هویت

پس از احراز هویت موفق، سرور باید یک Cookie احراز هویت صادر کند.

مرورگر باید Cookie احراز هویت را به‌طور خودکار همراه درخواست‌های بعدی ارسال کند.

از نظر مفهومی:

```text
ورود / تایید OTP
        |
        v
سرور هویت را اعتبارسنجی می‌کند
        |
        v
Cookie احراز هویت
        |
        v
درخواست‌های احرازهویت‌شده مرورگر
```

#### 5.6.2 امنیت Cookie

Cookieهای احراز هویت باید از تنظیمات امن Production استفاده کنند، از جمله در جایی که مناسب است:

```text
HttpOnly = true
Secure = true
SameSite = مقدار محدودکننده مناسب
```

رفتار دقیق SameSite باید متناسب با نیازمندی‌های احراز هویت و ورود خارجی برنامه انتخاب شود.

#### 5.6.3 وضعیت احراز هویت

هویت کاربر احرازهویت‌شده باید از طریق Claimها درون Cookie احراز هویت نمایش داده شود.

Cookie نباید به‌صورت غیرضروری حاوی اطلاعات حساس باشد.

رمزهای عبور، OTPها، اسرار پرداخت و سایر مقادیر حساس هرگز نباید درون Cookieهای احراز هویت ذخیره شوند.

#### 5.6.4 خروج (Logout)

خروج باید Session/Cookie احرازهویت‌شده را طبق مکانیزم پیکربندی‌شده احراز هویت Cookie باطل کند.

#### 5.6.5 احراز هویت گوگل

احراز هویت گوگل باید همچنان از جریان مناسب OAuth/OpenID Connect خارجی استفاده کند.

پس از احراز هویت خارجی موفق، برنامه باید Session احرازهویت‌شده مبتنی بر Cookie محلی خود را برقرار کند.

توکن‌های دسترسی/هویت گوگل نباید به‌عنوان مکانیزم عادی احراز هویت مرورگر برنامه استفاده شوند.

#### 5.6.6 جریان نهایی احراز هویت

جریان نهایی احراز هویت باید به شکل زیر باشد:

```text
                    +----------------+
                    | تلفن / گوگل    |
                    +-------+--------+
                            |
                            v
                    حساب کاربری محلی
                            |
                            v
                  احراز هویت Cookie
                            |
                            v
                 درخواست احرازهویت‌شده
                            |
                            v
              مجوزدهی بر پایه Permission
```

## 6. نقش‌ها، مجوزها و قواعد دسترسی

### 6.1 نقش‌ها

نقش‌ها باید کاملاً پویا باشند.

پنل مدیریت باید عملیات CRUD برای نقش‌ها را فراهم کند.

#### 6.1.1 فیلدهای نقش

| فیلد      | الزام         |
| --------- | ------------- |
| Id        | شناسه یکتا    |
| Name      | الزامی و یکتا |
| Title     | الزامی        |
| IsSystem  | الزامی        |
| CreatedAt | الزامی        |
| UpdatedAt | الزامی        |

#### 6.1.2 CRUD نقش پویا

مدیرانی که مجوز مناسب را دارند باید بتوانند:

- نقش ایجاد کنند.
- نقش‌ها را مشاهده کنند.
- نقش‌ها را ویرایش کنند.
- نقش‌ها را حذف کنند.
- مجوزها را به نقش‌ها تخصیص دهند.
- نقش‌ها را به کاربران تخصیص دهند.

سیستم نباید نقش‌های کسب‌وکاری مانند `Admin`، `Teacher` یا `User` را به‌عنوان تنها نقش‌های موجود Hard-code کند.

نقش‌های سیستمی می‌توانند توسط برنامه Seed شوند اما همچنان باید توسط همان موجودیت Role نمایش داده شوند.

#### 6.1.3 نقش‌های سیستمی

`IsSystem = true` به این معناست که نقش مورد نیاز برنامه است یا توسط قواعد برنامه محافظت می‌شود.

برنامه باید از حذف تصادفی یا تغییر مخرب نقش‌های سیستمی جلوگیری کند.

```text
Permission
```

یک نقش می‌تواند مجوزهای زیادی داشته باشد.

یک مجوز می‌تواند به نقش‌های زیادی تخصیص یابد.

تخصیص‌های تکراری نباید مجاز باشند.

مجوزدهی باید نقش‌های کاربر احرازهویت‌شده و مجوزهای تخصیص‌یافته به آن نقش‌ها را ارزیابی کند.

### 6.4 تخصیص نقش به کاربر

رابطه:

```text
User
  |
UserRole
  |
Role
```

یک کاربر می‌تواند چندین نقش داشته باشد.

مجوزهای مؤثر، اجتماع (Union) مجوزهای تخصیص‌یافته از طریق نقش‌های کاربر است.

اگر حداقل یک نقش تخصیص‌یافته یک مجوز را اعطا کند، کاربر برای آن مجوز مجاز محسوب می‌شود، مگر آنکه محدودیت صریح دیگری در سطح برنامه وجود داشته باشد.

### 6.5 مجوزدهی بر پایه Permission

سیستم باید عملیات مدیریتی را با استفاده از کلیدهای مجوز (Permission Key) مجاز کند، نه با بررسی نام نقش‌ها.

نادرست:

```text
if user.Role == "Admin"
```

مفهوم درست:

```text
if user.HasPermission("course.create")
```

این الزام به این دلیل است که نقش‌ها پویا هستند.

نیازمندی‌های مجوزدهی باید سمت سرور اعمال شوند و نباید صرفاً به نمایان بودن/نبودن عناصر رابط کاربری تکیه کنند.

### 6.6 داده‌های سیستمی اولیه موردنیاز

برنامه باید حداقل داده‌های موردنیاز برای عملکرد اولیه را Seed کند.

این می‌تواند شامل موارد زیر باشد:

- نقش‌های سیستمی اولیه.
- مجوزهای سیستمی اولیه.
- تخصیص‌های اولیه مجوز به نقش.
- تنظیمات سیستمی موردنیاز.

نقش‌های Seed شده همچنان رکوردهای پایگاه‌داده پویا باقی می‌مانند و نباید با مجوزدهی مبتنی بر نام نقش Hard-code شده جایگزین شوند.

### 6.7 قواعد دسترسی عمومی

وب‌سایت عمومی باید فقط محتوا را بر اساس وضعیت آن در معرض دید قرار دهد.

نمونه‌ها:

```text
دوره:
    منتشرشده -> عمومی
    پیش‌نویس -> غیرعمومی
    پنهان    -> غیرعمومی

بلاگ:
    منتشرشده/نمایش-فعال -> عمومی
    در غیر این صورت      -> غیرعمومی
```

محتوای دوره پولی، به‌جز اپیزودهای صراحتاً رایگان، نیازمند مالکیت دوره است.

### 6.8 قواعد دسترسی دوره

یک کاربر می‌تواند به یک دوره دسترسی داشته باشد اگر:

```text
Course.Price == null   (دوره رایگان)
```

یا:

```text
کاربر مالک دوره است
```

یا، برای یک دوره پولی:

```text
Episode.IsFree = true
```

دسترسی پیش‌نمایش رایگان نباید مالکیت کل دوره را اعطا کند.

## 7. کاتالوگ آموزشی (دسته‌بندی، دوره، اپیزود)

### 7.1 مدیریت دسته‌بندی

#### 7.1.1 فیلدها

یک دسته‌بندی باید شامل موارد زیر باشد:

| فیلد         | الزام               |
| ------------ | ------------------- |
| Id           | شناسه یکتا          |
| Name         | الزامی              |
| LatinName    | الزامی              |
| DisplayOrder | عدد صحیح الزامی     |
| ParentId     | قابل‌تهی (Nullable) |
| IsActive     | بولین الزامی        |
| CreatedAt    | الزامی              |
| UpdatedAt    | الزامی              |

#### 7.1.2 سلسله‌مراتب

دسته‌بندی‌ها باید حداکثر سه سطح را پشتیبانی کنند.

نمونه:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
```

مورد زیر نامعتبر است:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
            └── جنگو پیشرفته
```

برنامه باید ایجاد یا ویرایشی که منجر به تولید سطح چهارم می‌شود را رد کند.

#### 7.1.3 قواعد

- یک دسته‌بندی باید هویت یکتا داشته باشد.
- یک دسته‌بندی می‌تواند صفر یا یک والد داشته باشد.
- یک دسته‌بندی ریشه دارای `ParentId = null` است.
- یک دسته‌بندی نمی‌تواند والد خودش باشد.
- روابط والد چرخه‌ای (Circular) ممنوع هستند.
- دسته‌بندی‌های غیرفعال نباید برای دسته‌بندی دوره‌های جدید قابل‌انتخاب باشند.
- روابط موجود نباید هنگام غیرفعال شدن یک دسته‌بندی به‌صورت بی‌سروصدا حذف شوند.
- حذف یک دسته‌بندی که توسط یک دوره ارجاع داده شده باید یا جلوگیری یا به‌صراحت مدیریت شود؛ پیاده‌سازی نباید روابط دوره-دسته‌بندی را به‌صورت یتیم و بی‌سروصدا رها کند.

### 7.2 مدیریت دوره

#### 7.2.1 فیلدهای دوره

| فیلد              | الزام                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------- |
| Id                | شناسه یکتا                                                                              |
| Name              | الزامی                                                                                  |
| LatinName         | الزامی                                                                                  |
| ShortDescription  | الزامی                                                                                  |
| Description       | اختیاری/الزامی بر اساس قواعد اعتبارسنجی؛ از محتوای ویرایشگر HTML پشتیبانی می‌کند        |
| Slug              | الزامی و یکتا                                                                           |
| MainImage         | اختیاری                                                                                 |
| Price             | اختیاری؛ Null یعنی دوره رایگان و مقدار غیر-Null (بزرگ‌تر از 0) یعنی دوره پولی (بخش 7.3) |
| DiscountType      | None / Percentage / FixedAmount                                                         |
| DiscountValue     | زمانی که تخفیف فعال است الزامی                                                          |
| IsSaleActive      | الزامی                                                                                  |
| DisplayStatus     | Draft / Published / Hidden                                                              |
| IsFeatured        | الزامی                                                                                  |
| IsAmazing         | الزامی                                                                                  |
| IntroductionVideo | اختیاری                                                                                 |
| CreatedAt         | الزامی                                                                                  |
| UpdatedAt         | الزامی                                                                                  |

#### 7.2.2 توضیحات

توضیحات کامل باید از محتوای ویرایشگر HTML پشتیبانی کند.

سیستم باید HTML را بر اساس یک allowlist صریح، پیش از نمایش عمومی پاک‌سازی (Sanitize) کند.

HTML خام و کنترل‌نشده توسط کاربر نباید مستقیماً رندر شود.

#### 7.2.3 Slug

اسلاگ دوره باید:

- یکتا باشد.
- امن برای URL باشد.
- مگر با تغییر صریح، پایدار بماند.
- برای URLهای عمومی دوره استفاده شود.

#### 7.2.4 قیمت‌گذاری

قیمت دوره‌ها باید از یک نوع پولی سازگار با اعشار (Decimal) استفاده کند.

`float` و `double` نباید برای مقادیر پولی استفاده شوند.

رایگان یا پولی بودن دوره از روی `Price` تعیین می‌شود (بخش 7.3):

```text
Price == null  => دوره رایگان
Price > 0      => دوره پولی
```

سیستم نباید برای دسترسی به دوره رایگان نیازمند پرداخت باشد.

#### 7.2.5 تخفیف

انواع تخفیف پشتیبانی‌شده:

```text
None
Percentage
FixedAmount
```

تخفیف‌های درصدی باید در بازه زیر باشند:

```text
0 <= DiscountValue <= 100
```

تخفیف‌های ثابت نباید قیمت نهایی را منفی کنند.

قیمت نهایی قابل‌پرداخت باید به‌صورت متمرکز در لایه Application/Domain محاسبه شود.

#### 7.2.6 وضعیت فروش

`IsSaleActive` کنترل می‌کند که آیا دوره در حال حاضر قابل‌خرید است یا خیر.

یک دوره می‌تواند منتشرشده باشد اما در حال حاضر قابل‌خرید نباشد.

سیستم نباید وضعیت فروش را از وضعیت نمایش استنتاج کند.

#### 7.2.7 وضعیت نمایش

مقادیر پشتیبانی‌شده:

```text
Draft (پیش‌نویس)
Published (منتشرشده)
Hidden (پنهان)
```

فقط دوره‌های منتشرشده باید به‌عنوان لیست عادی دوره‌ها به‌صورت عمومی قابل‌کشف باشند.

دوره‌های پیش‌نویس و پنهان نباید به‌صورت عمومی در معرض دید قرار گیرند.

#### 7.2.8 ویژه و شگفت‌انگیز

دوره‌ها می‌توانند به این شکل علامت‌گذاری شوند:

- ویژه (Featured).
- شگفت‌انگیز (Amazing).

این پرچم‌ها متناظر با بخش‌های نمایشی خاصی هستند که قبلاً درخواست شده‌اند.

سیستم نباید برای انتشار یک دوره، تنظیم این پرچم‌ها را الزامی کند.

### 7.3 مدل قیمت‌گذاری محصول

در جایی که Domain حاوی مفهوم `Product` باشد، مدل قیمت‌گذاری باید تغییر کند.

سیستم نباید یک ستون جداگانه `IsFree` را در پایگاه‌داده ذخیره کند.

در عوض:

```text
Price = null
```

نمایانگر یک محصول رایگان است.

یک قیمت غیر-null نمایانگر یک محصول پولی است.

#### 7.3.1 فیلدهای محصول

مدل باید از موارد زیر استفاده کند:

```csharp
public decimal? Price { get; private set; }
```

به‌جای الزام موارد زیر:

```csharp
public bool IsFree { get; set; }
```

#### 7.3.2 خصیصه IsFree

مدل Domain می‌تواند موارد زیر را افشا کند:

```csharp
public bool IsFree => Price is null;
```

`IsFree` یک خصیصه مشتق‌شده (Derived) از Domain است و نباید در پایگاه‌داده ذخیره شود.

از نظر مفهومی:

```text
Price = null
    => IsFree = true

Price > 0
    => IsFree = false
```

#### 7.3.3 قواعد قیمت‌گذاری

محصولی با:

```text
Price = null
```

رایگان است.

محصولی با:

```text
Price > 0
```

پولی است.

محصولات پولی با قیمت صفر نباید برای نمایش محصولات رایگان استفاده شوند، مگر آنکه یک نیازمندی کسب‌وکاری مستندشده جداگانه صراحتاً چنین وضعیتی را معرفی کند.

#### 7.3.4 اعمال روی دوره (Course)

از آنجا که `Course` در حال حاضر نمایانگر محصول آموزشی قابل‌خرید است، همین قاعده قیمت‌گذاری برای Course اعمال می‌شود، مگر آنکه یک Aggregate جداگانه `Product` معرفی شود.

```text
Course.Price : decimal?
IsFree = خصیصه مشتق‌شده و ذخیره‌نشده
```

قاعده دسترسی به شکل زیر است:

```text
Course.Price == null
    => دوره رایگان است

Course.Price != null
    => دوره پولی است
```

برنامه باید این قاعده را به‌طور یکپارچه در موارد زیر استفاده کند:

- فهرست دوره‌ها.
- جزئیات دوره.
- سبد خرید.
- پرداخت (Checkout).
- ایجاد سفارش.
- دسترسی به دوره.
- تولید فاکتور.
- پنل مدیریت.

همین قاعده باید در جایی که مرتبط است برای رفتار پیش‌نمایش رایگان در سطح اپیزود نیز اعمال شود.

### 7.4 دسته‌بندی‌های دوره

یک دوره می‌تواند به چندین دسته‌بندی تعلق داشته باشد.

رابطه:

```text
Course
   |
CourseCategory
   |
Category
```

روابط تکراری دوره/دسته‌بندی نباید مجاز باشند.

دسته‌بندی‌های غیرفعال نباید قابل‌تخصیص به دوره‌های تازه ایجادشده یا ویرایش‌شده باشند.

### 7.5 مدرسان دوره

یک دوره می‌تواند یک یا چند مدرس داشته باشد.

رابطه:

```text
Course
   |
CourseInstructor
   |
InstructorProfile/User
```

سیستم باید رابطه مدرس را به‌طور مستقل از اعتبارنامه‌های احراز هویت نگه دارد.

فقط کاربرانی که از طریق پروفایل مدرس/تخصیص نقش خود به‌عنوان مدرس تعیین شده‌اند باید در پنل مدیریت به‌عنوان مدرس قابل‌انتخاب باشند.

### 7.6 بخش‌های دوره

هر دوره باید شامل صفر یا چند بخش باشد.

فیلدها:

| فیلد         | الزام      |
| ------------ | ---------- |
| Id           | شناسه یکتا |
| CourseId     | الزامی     |
| Title        | الزامی     |
| DisplayOrder | الزامی     |
| CreatedAt    | الزامی     |
| UpdatedAt    | الزامی     |

بخش‌ها باید بر اساس `DisplayOrder` صعودی نمایش داده شوند.

سیستم می‌تواند موارد زیر را محاسبه و نمایش دهد:

- تعداد اپیزودها.
- مجموع مدت‌زمان ویدیو.

این مقادیر نیاز نیست ذخیره (Persist) شوند مگر آنکه نیازمندی‌های عملکردی بعداً Denormalization را توجیه کنند.

### 7.7 اپیزودها

هر بخش می‌تواند شامل صفر یا چند اپیزود باشد.

#### 7.7.1 فیلدها

| فیلد         | الزام                             |
| ------------ | --------------------------------- |
| Id           | شناسه یکتا                        |
| SectionId    | الزامی                            |
| Title        | الزامی                            |
| Description  | اختیاری                           |
| Video        | اختیاری/الزامی بر اساس نوع اپیزود |
| Duration     | زمانی که ویدیو وجود دارد الزامی   |
| IsFree       | الزامی                            |
| DisplayOrder | الزامی                            |
| CreatedAt    | الزامی                            |
| UpdatedAt    | الزامی                            |

#### 7.7.2 ترتیب‌بندی

اپیزودها باید بر اساس `DisplayOrder` نمایش داده شوند.

مقادیر تکراری DisplayOrder ممکن است از نظر فنی مجاز باشند، اما عملیات Admin باید ترتیب قطعی (Deterministic) را حفظ کند.

#### 7.7.3 اپیزودهای رایگان

یک دوره پولی می‌تواند یک یا چند اپیزود را به‌عنوان پیش‌نمایش رایگان در معرض دید قرار دهد.

برای مثال:

```text
Course.Price != null   (دوره پولی)
Episode.IsFree = true
```

یک اپیزود رایگان می‌تواند توسط یک کاربر احراز هویت‌نشده یا غیرخریدار مشاهده شود، در صورتی که قواعد عمومی دوره اجازه دهد.

اپیزودهای غیررایگان یک دوره پولی نیازمند مالکیت دوره توسط کاربر هستند.

بررسی دسترسی باید به‌صورت متمرکز در لایه مجوزدهی/دسترسی برنامه انجام شود.

#### 7.7.4 وضعیت مشاهده اپیزود (به‌ازای هر کاربر)

وضعیت مشاهده اپیزود **به‌ازای هر کاربر** است و نباید مستقیماً روی Entity مربوط به `Episode` ذخیره شود.

هر کاربر باید برای هر اپیزود وضعیت مستقل خود را داشته باشد. تغییر وضعیت یک کاربر نباید هرگز بر وضعیت کاربر دیگری اثر بگذارد.

سیستم باید وضعیت‌های زیر را برای هر جفت `(User, Episode)` نگه‌داری کند:

| وضعیت      | توضیح                                                                 |
| ---------- | --------------------------------------------------------------------- |
| NotWatched | کاربر هنوز مشاهده اپیزود را شروع نکرده است.                           |
| InProgress | کاربر بخشی از اپیزود را مشاهده کرده اما آن را کامل نکرده است.         |
| Watched    | کاربر اپیزود را به‌طور کامل مشاهده کرده است.                          |
| Locked     | کاربر به اپیزود دسترسی ندارد؛ برای مثال اپیزود پولی بدون مالکیت دوره. |

##### 7.7.4.1 قواعد وضعیت

- وضعیت برای هر کاربر احرازهویت‌شده به‌صورت مستقل ارزیابی می‌شود.
- برای کاربران احرازهویت‌نشده، وضعیت ذخیره نمی‌شود؛ اپیزود بر اساس قواعد دسترسی `NotWatched` یا `Locked` در نظر گرفته می‌شود.
- اپیزود پیش‌نمایش رایگان یک دوره پولی برای کاربر غیرمالک می‌تواند `NotWatched`، `InProgress` یا `Watched` باشد، اما نباید `Locked` باشد.
- اپیزود غیررایگان یک دوره پولی که کاربر مالک آن نیست باید `Locked` باشد.
- پس از اعطای دسترسی به دوره، اپیزودهای غیررایگان از `Locked` به `NotWatched` منتقل می‌شوند.
- `InProgress` زمانی ثبت می‌شود که کاربر مشاهده را شروع کرده ولی اپیزود را کامل نکرده باشد.
- `Watched` زمانی ثبت می‌شود که کاربر آستانه تکمیل اپیزود را پشت سر گذاشته باشد؛ برای مثال 90% مدت ویدئو.
- آستانه تکمیل باید از طریق Configuration قابل تنظیم باشد.

##### 7.7.4.2 پایداری داده

وضعیت مشاهده باید در یک Entity اختصاصی و به‌ازای هر کاربر ذخیره شود:

```text
UserEpisodeProgress
    UserId
    EpisodeId
    Status
    LastWatchedPosition
    FirstWatchedAt
    CompletedAt
    LastWatchedAt
    CreatedAt
    UpdatedAt
```

باید یک محدودیت ترکیبی یکتا روی `(UserId, EpisodeId)` اعمال شود.

##### 7.7.4.3 دسترسی در برابر وضعیت

`Locked` یک وضعیت **مشتق‌شده از دسترسی** است، نه یک ترجیح ذخیره‌شده توسط کاربر. برنامه باید آن را بر اساس موارد زیر محاسبه کند:

- مالکیت دوره (`UserCourse`).
- `Episode.IsFree`.
- `Course.Price` (`null` یعنی دوره رایگان).
- وضعیت نمایش دوره.

پس از اعطای دسترسی، وضعیت `Locked` باید به‌صورت خودکار به `NotWatched` حل شود.

##### 7.7.4.4 به‌روزرسانی پیشرفت

به‌روزرسانی پیشرفت، مانند موقعیت پخش، باید سمت سرور اعتبارسنجی شود:

- `LastWatchedPosition` نباید از `Episode.Duration` بیشتر باشد.
- انتقال وضعیت‌ها باید از انتقال‌های مجاز زیر پیروی کند:

```text
Locked     -> NotWatched   (پس از اعطای دسترسی)
NotWatched -> InProgress   (با شروع پخش)
InProgress -> Watched      (پس از رسیدن به آستانه تکمیل)
InProgress -> InProgress   (به‌روزرسانی پیشرفت)
Watched    -> Watched      (مشاهده مجدد، بدون بازگشت وضعیت)
```

- وضعیت `Watched` نباید در جریان پخش عادی به `InProgress` یا `NotWatched` بازگردد.

### 7.8 پیوست‌های اپیزود

یک اپیزود می‌تواند صفر یا چند پیوست داشته باشد.

هر پیوست باید حداقل شامل موارد زیر باشد:

```text
Id
EpisodeId
FileName
StoragePath / FileReference
ContentType
Size
CreatedAt
```

سیستم باید موارد زیر را اعمال کند:

- حداکثر تعداد پیوست در هر اپیزود.
- حداکثر اندازه هر پیوست.
- پسوندها/انواع محتوای مجاز.

این محدودیت‌ها باید پیکربندی‌محور باشند.

نمونه پیکربندی:

```text
MaxAttachmentsPerEpisode
MaxAttachmentSizeBytes
AllowedAttachmentExtensions
```

این محدودیت‌ها باید سمت سرور اعتبارسنجی شوند.

### 7.9 یادداشت‌های شخصی اپیزود

یادداشت‌های شخصی کاربر روی اپیزودها صراحتاً از پیاده‌سازی اول به تعویق افتاده‌اند.

پایگاه‌داده و معماری برنامه نباید پیاده‌سازی آتی را غیرممکن کنند، اما هیچ ویژگی مدیریت یادداشت در نسخه 1 الزامی نیست.

### 7.10 سوالات متداول دوره

هر دوره می‌تواند شامل چندین سوال متداول باشد.

فیلدها:

| فیلد         | الزام      |
| ------------ | ---------- |
| Id           | شناسه یکتا |
| CourseId     | الزامی     |
| Title        | الزامی     |
| Description  | الزامی     |
| DisplayOrder | الزامی     |
| CreatedAt    | الزامی     |
| UpdatedAt    | الزامی     |

سوالات متداول باید بر اساس `DisplayOrder` نمایش داده شوند.

### 7.11 علاقه‌مندی‌ها

کاربران باید بتوانند دوره‌ها را به‌عنوان علاقه‌مندی علامت‌گذاری کنند.

موجودیت:

```text
FavoriteCourse
    UserId
    CourseId
    CreatedAt
```

یک کاربر نباید بتواند رابطه علاقه‌مندی تکراری برای یک دوره واحد ایجاد کند.

کاربران باید بتوانند:

- یک دوره را به علاقه‌مندی‌ها اضافه کنند.
- یک دوره را از علاقه‌مندی‌ها حذف کنند.
- دوره‌های علاقه‌مندی خود را مشاهده کنند.

## 8. ذخیره‌سازی ویدیو و فایل‌ها (wwwroot)

### 8.1 ذخیره‌سازی و ارائه ویدیوها

#### 8.1.1 زیرساخت ذخیره‌سازی

- سامانه باید از پوشه `wwwroot` برنامه برای ذخیره‌سازی ویدیوهای دوره‌ها، فایل‌های دانلودی و سایر فایل‌های آموزشی استفاده کند.
- پوشه‌های حاوی فایل‌های محافظت‌شده در `wwwroot` نباید از طریق میان‌افزار فایل‌های ایستا به‌صورت عمومی ارائه شوند.
- دسترسی عمومی و ناشناس به فایل‌های محافظت‌شده باید غیرفعال باشد.
- مسیرهای فیزیکی و جزئیات ساختار پوشه‌های `wwwroot` نباید در اختیار مرورگر یا کاربران قرار بگیرد.
- دانستن نام فایل یا مسیر آن در `wwwroot` نباید به‌عنوان مجوز دسترسی در نظر گرفته شود.
- اطلاعات فایل‌ها، شامل کلید ذخیره‌سازی و مشخصات مرتبط، باید در پایگاه داده نگهداری شوند.
- سامانه نباید صرفاً به غیرقابل‌حدس بودن آدرس فایل برای تأمین امنیت آن متکی باشد.
- دسترسی به منابع محافظت‌شده باید توسط سامانه یا یک لایه تحویل محتوای مورداعتماد کنترل شود.

#### 8.1.2 قالب ویدیو

- ویدیوهای دوره‌ها باید با قالب MP4 ذخیره و ارائه شوند.
- پخش ویدیو باید بدون نیاز به HLS امکان‌پذیر باشد.
- سامانه نباید به فایل‌های مانیفست `.m3u8` یا قطعه‌های ویدیویی HLS نیاز داشته باشد.
- پخش ویدیو باید با استفاده از قابلیت پخش ویدیوی HTML5 مرورگر انجام شود.
- سامانه باید از درخواست‌های HTTP Range پشتیبانی کند تا مرورگر بتواند بدون دریافت کامل فایل، به بخش‌های مختلف ویدیو مراجعه کند.
- لایه ارائه فایل باید درخواست‌های `Range` و پاسخ‌های `206 Partial Content` را به‌درستی مدیریت کند.
- نوع محتوای پاسخ برای فایل‌های MP4 باید به‌درستی تنظیم شود:
  `Content-Type: video/mp4`
- در صورت پشتیبانی مرورگر، امکان جابه‌جایی در ویدیو و ادامه پخش پس از توقف یا قطع ارتباط باید فراهم باشد.

#### 8.1.3 قوانین دسترسی به ویدیوها

سامانه باید بین ویدیوهای پیش‌نمایش عمومی و ویدیوهای محافظت‌شده دوره‌ها تفاوت قائل شود.

##### 8.1.3.1 ویدیوهای پیش‌نمایش عمومی

- فقط ویدیوهایی که صراحتاً به‌عنوان پیش‌نمایش عمومی تعریف شده‌اند، باید بدون احراز هویت قابل مشاهده باشند.
- کاربران ناشناس باید بتوانند پیش‌نمایش‌های عمومی مجاز را بدون ایجاد حساب کاربری مشاهده کنند.
- دسترسی به پیش‌نمایش نباید موجب دسترسی به محتوای کامل دوره پولی یا فایل‌های محافظت‌شده آن شود.
- ارائه فایل‌های پیش‌نمایش به‌صورت ایستا و عمومی نباید انجام شود، مگر اینکه این تصمیم صراحتاً در الزامات امنیتی تأیید شده باشد.
- اگر فایل پیش‌نمایش در فضای ذخیره‌سازی خصوصی قرار دارد، سامانه باید روش کنترل‌شده‌ای برای ارائه آن به کاربران مجاز فراهم کند.

##### 8.1.3.2 ویدیوهای محافظت‌شده دوره‌ها

- مشاهده ویدیوهای محافظت‌شده باید به احراز هویت کاربر نیاز داشته باشد.
- سرور باید بررسی کند که کاربر مجوز معتبر و فعال برای دسترسی به دوره یا درس مربوطه دارد.
- این مجوز می‌تواند از طریق خرید معتبر یا یک قانون دسترسی صریح دیگر، مانند ثبت‌نام تأییدشده توسط مدیر، ایجاد شود.
- دانستن شناسه دوره، شناسه درس، شناسه ویدیو یا نام فایل در `wwwroot` نباید برای دسترسی کافی باشد.
- پیش از ارائه دسترسی به ویدیو، مجوز کاربر باید در سمت سرور بررسی شود.
- دسترسی به یک درس نباید به‌طور خودکار دسترسی به درس‌ها یا دوره‌های دیگر را فراهم کند.
- کنترل دسترسی باید در سمت سرور اعمال شود، نه صرفاً در رابط کاربری.

#### 8.1.4 معماری ارائه ویدیوهای MP4

- فایل‌های MP4 محافظت‌شده باید در پوشه `wwwroot` نگهداری شوند و دسترسی ایستای مستقیم به آن‌ها مسدود شود.
- سامانه باید سازوکاری کنترل‌شده برای ارائه فایل MP4 به مرورگر کاربران مجاز داشته باشد.
- پیاده‌سازی می‌تواند یکی از روش‌های زیر را انتخاب کند:
  1. ایجاد یک Endpoint در ASP.NET Core که پس از بررسی مجوز، فایل MP4 را از پوشه `wwwroot` خوانده و به‌صورت جریانی به کاربر ارائه دهد.

  2. استفاده از یک لایه تحویل محتوای مورداعتماد که پس از بررسی مجوز، لینک یا توکن دسترسی امضاشده و کوتاه‌مدت صادر کند.

- روش انتخاب‌شده باید تمام الزامات کنترل دسترسی این مستند را رعایت کند.
- اگر فایل از طریق ASP.NET Core ارائه می‌شود، درخواست‌های HTTP Range باید به‌درستی پشتیبانی شوند.
- فایل نباید به‌طور کامل در حافظه سرور بارگذاری شود؛ انتقال باید به‌صورت جریانی انجام شود.
- در صورت استفاده از لینک امضاشده یا لایه تحویل محتوا، مبدأ ذخیره‌سازی در `wwwroot` باید خصوصی باقی بماند.
- لینک امضاشده ذاتاً یک‌بارمصرف نیست و معمولاً تا پایان اعتبار خود قابل استفاده مجدد است.
- سامانه نباید ادعا کند که آدرس فایل‌ها یا درخواست‌های پخش ویدیو را می‌توان به‌طور کامل از ابزارهای توسعه‌دهنده مرورگر مخفی کرد.
- هدف امنیتی، جلوگیری از دسترسی غیرمجاز به محتواست، نه مخفی‌کردن درخواست‌هایی که مرورگر برای پخش ویدیو ارسال می‌کند.

#### 8.1.5 مجوز پخش ویدیو

- سامانه باید پیش از اجازه شروع پخش ویدیوی محافظت‌شده، مجوز کاربر را بررسی کند.
- در صورت استفاده از اعتبارنامه کوتاه‌مدت پخش، اعتبارنامه باید زمان انقضای محدود داشته باشد و به ویدیو، درس یا منبع مجاز مشخصی محدود شود.
- در صورت پشتیبانی معماری، اعتبارنامه پخش بهتر است به کاربر احراز هویت‌شده یا نشست پخش مجاز مرتبط باشد.
- سامانه باید در صورت نیاز، امکان لغو یا بی‌اعتبار کردن مجوز پخش را فراهم کند.
- اعتبارنامه پخش نباید شامل مسیر فیزیکی فایل یا سایر اطلاعات حساس زیرساخت ذخیره‌سازی باشد.
- کنترل دسترسی باید با درخواست‌های متعدد موردنیاز برای پخش ویدیو، از جمله درخواست‌های Range، سازگار باشد.
- استفاده از توکن یک‌بارمصرف نباید باعث اختلال در پخش عادی، جابه‌جایی در ویدیو یا ارسال درخواست‌های تکراری شود.
- سامانه باید از آسیب‌پذیری IDOR جلوگیری کند؛ یعنی تغییر شناسه منابع در درخواست نباید باعث دسترسی به محتوای غیرمجاز شود.

### 8.2 فایل‌های دانلودی دوره‌ها

#### 8.2.1 کنترل دسترسی به دانلودها

- فایل‌های دانلودی محافظت‌شده باید در پوشه `wwwroot` قرار بگیرند و فقط از طریق Endpointهای کنترل‌شده ارائه شوند.
- سامانه باید پیش از صدور مجوز دانلود، احراز هویت و سطح دسترسی کاربر را بررسی کند.
- کاربر باید مجوز معتبر برای دوره یا درس مربوطه داشته باشد.
- دسترسی به پیش‌نمایش عمومی نباید مجوز دانلود فایل‌های محافظت‌شده را ایجاد کند.
- سامانه نباید آدرس عمومی و دائمی برای دانلود فایل‌های محافظت‌شده ارائه دهد.

#### 8.2.2 توکن یک‌بارمصرف دانلود

- در صورت نیاز کسب‌وکار به دسترسی یک‌بارمصرف، سامانه باید از توکن‌های یک‌بارمصرف برای دانلود فایل‌های محافظت‌شده استفاده کند.
- توکن باید با استفاده از مولد اعداد تصادفی رمزنگاری‌شده و امن تولید شود.
- توکن باید مدت اعتبار محدودی داشته باشد.
- توکن باید به فایل موردنظر و در صورت لزوم به کاربر مجاز وابسته باشد.
- توکن‌ها باید به‌صورت امن ذخیره شوند. بهتر است به‌جای مقدار اصلی توکن، هش رمزنگاری‌شده آن در پایگاه داده ذخیره شود.
- توکن منقضی‌شده، لغوشده، مصرف‌شده یا مرتبط با منبع یا کاربر نامعتبر باید رد شود.
- مصرف توکن باید به‌صورت اتمیک انجام شود تا درخواست‌های هم‌زمان نتوانند یک توکن را چند بار با موفقیت مصرف کنند.
- استفاده از توکن نباید کنترل دسترسی اصلی به فایل را دور بزند.
- توکن‌ها و لینک‌های امضاشده نباید به‌صورت متن آشکار در گزارش‌های سامانه ثبت شوند.

#### 8.2.3 دانلود فایل‌های حجیم

- پیاده‌سازی دانلود باید فایل‌های حجیم و قطع‌شدن ارتباط شبکه را در نظر بگیرد.
- اگر ادامه دانلود یا درخواست‌های HTTP Range پشتیبانی می‌شوند، رفتار مصرف توکن باید با درخواست‌های متعدد سازگار باشد.
- در صورت نیاز به چند درخواست HTTP، بهتر است توکن یک‌بارمصرف برای ایجاد یک نشست دانلود مجاز مصرف شود.
- درخواست‌های بعدی می‌توانند تا زمان انقضا یا لغو نشست، در محدوده همان نشست مجاز باشند.
- نشست دانلود باید به همان فایل و کاربر یا نشست مجاز محدود بماند.
- اگر لینک امضاشده استفاده می‌شود، سامانه باید در نظر بگیرد که لینک معمولاً تا پایان اعتبار قابل استفاده مجدد است، مگر اینکه کنترل تکمیلی در سمت سرور پیاده‌سازی شده باشد.
- سامانه نباید یک لینک امضاشده معمولی را ذاتاً یک‌بارمصرف معرفی کند.

### 8.3 امنیت بارگذاری و پردازش فایل‌ها

#### 8.3.1 اعتبارسنجی فایل‌های بارگذاری‌شده

- فایل‌های بارگذاری‌شده باید در سمت سرور اعتبارسنجی شوند.
- سامانه نباید صرفاً به پسوند فایل یا مقدار `Content-Type` ارسال‌شده از طرف کاربر اعتماد کند.
- حداکثر اندازه مجاز فایل باید قابل تنظیم باشد.
- قالب‌های مجاز باید بررسی شوند و در صورت امکان، امضای باینری فایل نیز اعتبارسنجی شود.
- تصاویر بارگذاری‌شده بهتر است با استفاده از یک کتابخانه معتبر پردازش تصویر، رمزگشایی و مجدداً کدگذاری شوند.
- تصاویر نامعتبر یا دارای قالب پشتیبانی‌نشده باید رد شوند.
- بارگذاری SVG باید به‌صورت پیش‌فرض ممنوع باشد، مگر اینکه سیاست مشخصی برای پاک‌سازی و ارائه امن آن پیاده‌سازی شود.
- در صورت وجود سرویس مناسب، فایل‌های بارگذاری‌شده بهتر است از نظر بدافزار اسکن شوند.
- تکمیل موفق بارگذاری نباید باعث عمومی‌شدن خودکار فایل شود.

#### 8.3.2 بارگذاری ویدیو

- ویدیوهای دوره باید پس از عبور از اعتبارسنجی و کنترل دسترسی، در پوشه `wwwroot` ذخیره شوند.
- سامانه باید محدودیت‌های قابل تنظیم برای اندازه فایل MP4 و در صورت نیاز مدت ویدیو اعمال کند.
- سامانه بهتر است بررسی کند که ویدیوی بارگذاری‌شده با محیط پخش مورد پشتیبانی سازگار است.
- فایل‌های بارگذاری‌شده نباید اجرا شوند یا به‌عنوان کد سمت سرور تفسیر شوند.
- مجوز بارگذاری ویدیو باید به مدیران، مدرسان یا نقش‌های مجاز محدود شود.
- سامانه نیازی به تبدیل اجباری ویدیوها به HLS یا تولید قطعه‌های HLS ندارد.
- هرگونه پردازش اختیاری ویدیو باید از فرایند اصلی ذخیره‌سازی و پخش MP4 مستقل باشد.

### 8.4 امنیت HTTP، مرورگر و ارائه محتوا

#### 8.4.1 امنیت ارتباطات

- تمام ارتباطات احراز هویت‌شده در محیط عملیاتی باید از HTTPS استفاده کنند.
- درخواست‌های پخش و دانلود نیز باید در محیط عملیاتی از HTTPS استفاده کنند.
- اطلاعات محرمانه ذخیره‌سازی نباید در اختیار مرورگر قرار بگیرند.

#### 8.4.2 سیاست کش

- پاسخ‌های مربوط به ویدیوها و فایل‌های محافظت‌شده باید سیاست کش متناسب با حساسیت محتوا داشته باشند.
- استفاده از کش در پراکسی معکوس یا CDN باید آگاهانه پیکربندی شود.
- کش مشترک نباید محتوای محافظت‌شده یک کاربر را در اختیار کاربر غیرمجاز دیگری قرار دهد.
- پاسخ‌های وابسته به مجوز کاربر بهتر است از `Cache-Control: private` و در صورت نیاز `no-store` استفاده کنند.
- اگر از CDN یا لایه تحویل محتوا استفاده می‌شود، قوانین کش و اعتبارسنجی توکن باید کنترل دسترسی به هر منبع را حفظ کنند.
- محتوای پیش‌نمایش عمومی می‌تواند در صورت تأیید الزامات محصول از سیاست کش بازتری استفاده کند.

#### 8.4.3 امنیت مرورگر

- سیاست CORS باید متناسب با معماری واقعی فرانت‌اند و لایه تحویل محتوا تنظیم شود.
- CORS نباید به‌عنوان جایگزین احراز هویت یا کنترل دسترسی در نظر گرفته شود.
- در صورت استفاده از احراز هویت مبتنی بر کوکی، درخواست‌های تغییردهنده وضعیت باید در برابر CSRF محافظت شوند.
- سرور باید سربرگ‌های امنیتی مناسب، از جمله `X-Content-Type-Options: nosniff`، را در محل مناسب تنظیم کند.
- اطلاعات محرمانه زیرساخت ذخیره‌سازی، از جمله مسیرهای فیزیکی فایل‌ها، نباید در پاسخ‌های فرانت‌اند افشا شوند.

#### 8.4.4 محدودسازی درخواست‌ها و ثبت رویدادها

- سامانه بهتر است برای صدور مجوز پخش، ایجاد توکن دانلود، مصرف توکن و سایر نقاط حساس محدودیت نرخ درخواست اعمال کند.
- سامانه بهتر است الگوهای مشکوک، از جمله تلاش‌های مکرر برای دسترسی غیرمجاز یا مصرف بیش‌ازحد توکن‌ها، را شناسایی کند.
- خطاهای کنترل دسترسی و فعالیت‌های مشکوک باید در گزارش‌های امنیتی ثبت شوند.
- رمز عبور، توکن دسترسی، کلید محرمانه و توکن کامل دانلود نباید در گزارش‌ها ثبت شوند.
- ثبت رویدادها نباید اطلاعات شخصی حساس را بیش از حد لازم ذخیره کند.

### 8.5 کنترل دسترسی و یکپارچگی داده‌ها

- هر ویدیو و فایل دانلودی محافظت‌شده باید به دوره یا درس مالک آن مرتبط باشد.
- سرور باید محدوده مجوز دسترسی را بر اساس روابط معتبر در پایگاه داده تعیین کند.
- شناسه‌های ارسال‌شده توسط کاربر نباید به‌تنهایی برای اثبات مالکیت یا مجوز دسترسی کافی باشند.
- تغییر شناسه دوره، درس، ویدیو یا فایل نباید موجب دسترسی غیرمجاز شود.
- لغو مجوز کاربر باید از صدور مجوزهای جدید پخش و دانلود جلوگیری کند.
- سامانه باید رفتار اعتبارنامه‌های کوتاه‌مدت صادرشده قبلی را هنگام لغو مجوز مشخص کند.
- اطلاعات فایل‌های ذخیره‌شده در پایگاه داده باید با فایل‌های موجود در `wwwroot` سازگار بمانند.
- کلید فایل‌ها باید توسط سرور تولید یا اعتبارسنجی شوند و نباید امکان دسترسی به مسیر دلخواه در فضای ذخیره‌سازی را فراهم کنند.

### 8.6 الزامات آزمون امنیتی

پیاده‌سازی باید شامل آزمون‌های زیر باشد:

1. کاربر ناشناس بتواند ویدیوی پیش‌نمایش عمومی مجاز را مشاهده کند.

2. کاربر ناشناس نتواند به ویدیوی محافظت‌شده دوره دسترسی پیدا کند.

3. کاربر احراز هویت‌شده فاقد مجوز معتبر نتواند ویدیوی محافظت‌شده را مشاهده کند.

4. کاربر دارای مجوز معتبر بتواند ویدیوی MP4 مجاز را پخش کند.

5. تغییر شناسه‌های درخواست نتواند امکان دسترسی به ویدیوی دوره دیگر را فراهم کند.

6. کاربر غیرمجاز نتواند مستقیماً و بدون بررسی مجوز به فایل محافظت‌شده در `wwwroot` دسترسی پیدا کند.

7. درخواست‌های معتبر HTTP Range در صورت نیاز پشتیبانی شوند.

8. کاربران غیرمجاز نتوانند برای ویدیوهای محافظت‌شده توکن یا مجوز پخش دریافت کنند.

9. اعتبارنامه‌های منقضی‌شده یا نامعتبر پخش رد شوند.

10. کنترل دسترسی پخش با درخواست‌های تکراری و جابه‌جایی در ویدیو سازگار باشد.

11. توکن دانلود معتبر مطابق سیاست تعریف‌شده قابل مصرف باشد.

12. توکن دانلود منقضی‌شده، لغوشده یا قبلاً مصرف‌شده رد شود.

13. درخواست‌های هم‌زمان نتوانند یک توکن یک‌بارمصرف را بیش از یک بار با موفقیت مصرف کنند.

14. نشست دانلود، در صورت پیاده‌سازی، نتواند برای دریافت فایل دیگری استفاده شود.

15. دانلود فایل حجیم بدون بارگذاری کامل فایل در حافظه سرور انجام شود.

16. فایل‌های نامعتبر یا دارای قالب غیرمجاز هنگام بارگذاری رد شوند.

17. محتوای محافظت‌شده از طریق تنظیمات اشتباه کش به‌صورت عمومی در دسترس قرار نگیرد.

18. گزارش‌های سامانه حاوی اعتبارنامه‌ها، توکن‌های آشکار یا لینک‌های امضاشده کامل نباشند.

19. لغو مجوز کاربر مانع صدور مجوز جدید پخش و دانلود شود.

20. دسترسی به پیش‌نمایش عمومی موجب دسترسی به درس پولی یا فایل دانلودی محافظت‌شده نشود.

### 8.7 معیارهای تکمیل قابلیت

این قابلیت زمانی تکمیل‌شده محسوب می‌شود که:

- پوشه ذخیره‌سازی فایل‌های محافظت‌شده در `wwwroot` پیکربندی شده باشد و دسترسی ایستای مستقیم به آن مسدود شود.
- ویدیوهای پیش‌نمایش عمومی، در صورت مجاز بودن، بدون احراز هویت قابل پخش باشند.
- پخش ویدیوهای MP4 محافظت‌شده به احراز هویت و مجوز معتبر نیاز داشته باشد.
- روش انتخاب‌شده برای ارائه MP4، کنترل دسترسی و پشتیبانی موردنیاز از HTTP Range را فراهم کند.
- پخش ویدیو به HLS، فایل‌های `.m3u8` یا تبدیل اجباری با FFmpeg وابسته نباشد.
- دانلود فایل‌های محافظت‌شده به مجوز معتبر نیاز داشته باشد.
- توکن‌های یک‌بارمصرف دانلود، در صورت پیاده‌سازی، انقضا و مصرف اتمیک داشته باشند.
- دانلود فایل‌های حجیم بدون بارگذاری کامل فایل در حافظه سرور انجام شود.
- اعتبارسنجی فایل‌های بارگذاری‌شده و کنترل دسترسی به فضای ذخیره‌سازی پیاده‌سازی شده باشد.
- سیاست‌های کش و امنیت ارتباطات برای محتوای محافظت‌شده تنظیم شده باشند.
- آزمون‌های کنترل دسترسی، توکن دانلود، بارگذاری فایل و ارائه محتوا با موفقیت اجرا شوند.
- هیچ اطلاعات محرمانه‌ای از زیرساخت ذخیره‌سازی (مانند مسیرهای فیزیکی) در اختیار مرورگر قرار نگرفته باشد.

## 9. سبد خرید، سفارش و پرداخت

### 9.1 دوره‌های خریداری‌شده / ثبت‌نام (Enrollment)

سیستم باید دسترسی به دوره‌های خریداری‌شده را نگه‌داری کند.

موجودیت:

```text
UserCourse
    UserId
    CourseId
    OrderId
    PurchasedAt
```

یک پرداخت موفق برای یک دوره باید دسترسی به دوره را اعطا کند.

این عملیات باید Idempotent باشد.

Callbackهای تکراری پرداخت یا پردازش‌های تکراری نباید رکوردهای دسترسی تکراری ایجاد کنند.

### 9.2 مالکیت موجود

اگر کاربری از پیش مالک یک دوره باشد، سیستم نباید یک حق دسترسی دوم برای همان جفت کاربر/دوره ایجاد کند.

جریان سبد خرید/پرداخت باید از خرید مجدد غیرضروری دوره‌های از پیش مالکیت‌شده جلوگیری کند.

### 9.3 سبد خرید

سبد خرید باید در Redis ذخیره شود.

نباید به‌عنوان منبع اصلی سبد خرید در PostgreSQL پایدار (Persist) شود.

#### 9.3.1 قلم سبد خرید

هر قلم سبد خرید باید شامل موارد زیر باشد:

```text
CourseId
Quantity
```

یک دوره نباید بیش از یک‌بار در یک سبد خرید ظاهر شود.

از آنجا که محصول یک حق دسترسی (Entitlement) به دوره است، قاعده کسب‌وکاری معمولاً باید تعداد را به یک عدد در هر دوره محدود کند.

اگر API مقداری بزرگ‌تر از مقدار مجاز دریافت کند، باید آن را بر اساس یک قاعده مستندشده واحد رد یا نرمال (Normalize) کند. پیاده‌سازی باید از یک رفتار یکسان و پایدار استفاده کند.

#### 9.3.2 کلید سبد خرید

کلید Redis باید با کاربر احرازهویت‌شده مرتبط باشد.

نمونه:

```text
cart:{userId}
```

پایداری سبد خرید کاربران احرازهویت‌نشده در این نسخه الزامی نیست، مگر آنکه صراحتاً بعداً اضافه شود.

#### 9.3.3 کوپن اعمال‌شده

یک سبد خرید حداکثر می‌تواند یک کوپن اعمال‌شده داشته باشد.

علاوه بر اقلام، سبد خرید ذخیره‌شده در Redis باید یک کد کوپن اختیاری نیز حمل کند:

```text
cart:{userId}
    Items      : CourseId, Quantity
    CouponCode : اختیاری
```

فقط کد کوپن باید در سبد خرید ذخیره شود. مبالغ تخفیف حاصل از کوپن هرگز نباید به‌عنوان مقادیر قابل‌اعتماد ذخیره شوند و هرگز نباید از مرورگر پذیرفته شوند. سرور باید هر بار که سبد خرید یا خلاصه پرداخت خوانده می‌شود، آن‌ها را مجدداً محاسبه کند.

کد کوپن باید در موارد زیر از سبد خرید حذف شود:

- کاربر آن را حذف کند.
- سبد خرید خالی شود یا پس از خرید موفق پاک شود.

اگر کوپن اعمال‌شده در حالی که هنوز در سبد خرید است واجد شرایط بودن را از دست بدهد (برای مثال منقضی شود، سقف استفاده آن تکمیل شود، یا پس از حذف یک قلم، جمع جزء واجد شرایط از حداقل مبلغ سفارش کمتر شود)، سرور باید تخفیف آن را از تمام مجموع‌ها کنار بگذارد و به کاربر اطلاع دهد که کوپن دیگر قابل اعمال نیست. سبد خرید هرگز نباید تخفیفی را که معتبر نیست نمایش دهد.

قواعد واجد شرایط بودن و محاسبه در بخش 9.4 تعریف شده‌اند.

### 9.4 قواعد کسب‌وکار کوپن

1. اعتبار کوپن باید در زمان ایجاد سفارش، در سمت سرور مجدداً بررسی شود، نه فقط زمانی که کد برای اولین بار اعمال می‌شود، تا از سوءاستفاده از وضعیت کهنه یا شرایط رقابتی جلوگیری شود.
2. `UsedCount` باید به‌صورت اتمیک افزایش یابد تا از استفاده بیش از حد در درخواست‌های هم‌زمان جلوگیری شود.
3. یکتایی `Code` باید در لایه ذخیره‌سازی اعمال شود.
4. منطق محاسبه تخفیف (درصدی در مقابل مبلغ ثابت) باید در لایه دامنه قرار گیرد و نباید در لایه‌های اپلیکیشن یا ارائه تکرار شود.
5. محدودیت استفاده به ازای هر کاربر مستقیماً روی موجودیت Coupon مدل‌سازی نمی‌شود. در صورت نیاز، باید از طریق یک رکورد ردیابی استفاده جداگانه که Coupon، User و Order را به هم مرتبط می‌کند، اعمال شود.
6. فیلدهای Coupon باید از الزامات استاندارد حسابرسی و حذف نرم تعریف‌شده در بخش‌های 4.2 و 4.1 پیروی کنند.
7. یک سبد خرید و یک سفارش هر کدام حداکثر یک کوپن اعمال‌شده دارند.
8. یک کوپن فقط زمانی قابل اعمال است که تمام شرایط زیر برقرار باشند:
   - وجود داشته باشد و حذف نرم نشده باشد.
   - `IsActive` برابر `true` باشد.
   - زمان جاری UTC در بازه `StartDate` تا `EndDate` (با احتساب دو سر بازه) باشد.
   - `UsageLimit` تهی باشد یا `UsedCount < UsageLimit` برقرار باشد.
   - `MinOrderAmount` تهی باشد یا جمع جزء سبد خرید حداقل برابر `MinOrderAmount` باشد.
9. جمع جزء سبد خرید پس از تخفیف‌های سطح دوره و پیش از کوپن محاسبه می‌شود. مبالغ باید با این ترتیب محاسبه شوند:

   ```text
   قیمت دوره
       -> تخفیف سطح دوره (قیمت واحد مؤثر)
       -> جمع جزء
       -> تخفیف کوپن
       -> مبلغ قابل پرداخت
   ```

   - `Percentage`: تخفیف کوپن = جمع جزء ×`Value` / 100.
   - `FixedAmount`: تخفیف کوپن =`Value`.
   - محاسبه باید از `decimal` و یک قاعده گردکردن مستندشده واحد استفاده کند.

10. کوپنی که تخفیف آن مبلغ قابل پرداخت را به صفر یا کمتر برساند قابل اعمال نیست. سفارش‌های با مبلغ صفر در این نسخه پشتیبانی نمی‌شوند.
11. کوپن روی کل سبد خرید اعمال می‌شود. محدودسازی به دوره‌ها یا دسته‌بندی‌های خاص مدل‌سازی نشده است. دوره‌های رایگان سهمی در جمع جزء ندارند.
12. استفاده از کوپن با افزایش `UsedCount` هنگام ایجاد سفارش، داخل تراکنش ایجاد سفارش و با یک به‌روزرسانی شرطی (`UsedCount < UsageLimit`) رزرو می‌شود تا درخواست‌های هم‌زمان نتوانند از سقف عبور کنند.
    - اگر سفارش `Failed` یا `Cancelled` شود، استفاده رزروشده باید دقیقاً یک‌بار آزاد شود و آزادسازی باید Idempotent باشد.
    - اگر سفارش `Paid` شود، استفاده مصرف‌شده باقی می‌ماند.
    - پردازش مجدد نتیجه پرداخت هرگز نباید `UsedCount` را تغییر دهد.
    - سفارش‌هایی که پس از انقضای خود در حالت `Pending` باقی بمانند مطابق بخش 9.6.1 لغو می‌شوند که استفاده رزروشده را آزاد می‌کند.
13. سفارش باید `CouponId` و `CouponDiscountAmount` را ذخیره کند. تغییر، انقضا یا حذف نرم کوپن در آینده نباید سفارش‌های موجود را تغییر دهد و سفارش‌های تاریخی همچنان باید بتوانند کوپن خود را شناسایی (Resolve) کنند.
14. کدهای کوپن باید Trim شوند و بدون حساسیت به حروف تطبیق داده شوند و قاعده یکتایی لایه ذخیره‌سازی (قاعده 3) باید با آن سازگار باشد. تلاش‌های اعمال باید Rate Limit شوند و پیام‌های شکست نمایش‌داده‌شده به کاربر باید از قواعد صفحه سبد خرید در بخش 13.3 پیروی کنند.

- تخفیف دوره.
- پیکربندی کوپن (کد، نوع، مقدار، بازه اعتبار، سقف استفاده).

نباید مبالغ سفارش‌های موجود را تغییر دهند.

سفارش باید مبلغ تخفیف کوپنی را که هنگام ایجاد سفارش اعمال شده است ذخیره کند.

سرور باید تمام مجموع‌های پولی را محاسبه کند.

مجموع‌های ارسالی از سمت کلاینت هرگز نباید مورد اعتماد قرار گیرند.

### 9.6 وضعیت سفارش

enum وضعیت اولیه باید شامل موارد زیر باشد:

```text
Pending (در انتظار)
Paid (پرداخت‌شده)
Cancelled (لغوشده)
Failed (ناموفق)
```

انتقال‌های وضعیت باید توسط قواعد کسب‌وکاری برنامه کنترل شوند.

یک سفارش نباید صرفاً به این دلیل که یک کلاینت موفقیت را گزارش می‌دهد، به `Paid` تغییر یابد.

#### 9.6.1 انقضای سفارش در انتظار (Pending Order Expiration)

یک سفارش `Pending` نباید برای همیشه در حالت انتظار باقی بماند.

هنگامی که یک سفارش به‌صورت `Pending` ایجاد می‌شود، `ExpiresAt` باید برابر زمان ایجاد به‌علاوه مدت انقضای پیکربندی‌شده (`PendingOrderExpirationMinutes`) مقداردهی شود.

یک Job پس‌زمینه باید به‌صورت دوره‌ای سفارش‌های `Pending` را که `ExpiresAt` آن‌ها گذشته است پردازش کند. برای هر سفارش، باید:

- وضعیت سفارش را به `Cancelled` تغییر دهد.
- رکورد پرداخت `Pending` آن را به `Cancelled` تغییر دهد.
- استفاده رزروشده کوپن را دقیقاً یک‌بار آزاد کند (بخش 9.4).

انتقال از وضعیت `Pending` باید یک به‌روزرسانی شرطی و اتمیک باشد تا انقضا نتواند با نتیجه پرداختی که همان سفارش را `Paid` می‌کند دچار رقابت (Race) شود. هر انتقالی که زودتر اعمال شود نهایی است.

Job باید Idempotent باشد و زمانی که چند نمونه برنامه هم‌زمان آن را اجرا می‌کنند ایمن باشد.

اگر نتیجه پرداخت موفق برای سفارشی برسد که پیش‌تر با انقضا لغو شده است، سیستم نباید آن را بی‌صدا نادیده بگیرد و نباید به‌صورت خودکار دسترسی دوره اعطا کند یا فاکتور صادر کند. باید نتیجه پرداخت را به‌صورت Idempotent ثبت کند، آن را به‌عنوان خطا همراه با اطلاعات همبستگی (Correlation) لاگ کند و آن را در ماژول‌های سفارش‌ها و پرداخت‌ها برای بررسی مدیریتی قابل شناسایی کند.

انقضای سفارش باید با لاگ ساختاریافته ثبت شود.

### 9.7 یکپارچگی خرید

پیش از ایجاد سفارش، برنامه باید موارد زیر را مجدداً ارزیابی کند:

- وجود دوره.
- وضعیت انتشار دوره، در صورت لزوم.
- در دسترس بودن فروش.
- قیمت فعلی.
- تخفیف فعلی.
- واجدشرایط بودن کاربر.
- الزام شماره تلفن.
- مالکیت موجود.
- اعتبار کوپن، در صورت اعمال کوپن.

سرور هرگز نباید به مقادیر قیمت، تخفیف یا مبلغ کوپن دریافت‌شده از مرورگر اعتماد کند.

### 9.8 روش‌های پرداخت

روش‌های پرداخت باید با یک enum نمایش داده شوند.

نمونه:

```csharp
public enum PaymentMethod
{
    BankGateway,
    ZarinPal,
    SnappPay
}
```

هیچ پیاده‌سازی واقعی درگاه در نسخه 1 الزامی نیست.

لایه Application باید به یک انتزاع وابسته باشد تا ارائه‌دهندگان واقعی بعداً بدون تغییر قواعد کسب‌وکاری سفارش قابل‌پیاده‌سازی باشند.

### 9.9 پرداخت

فیلدهای پرداخت:

| فیلد           | الزام      |
| -------------- | ---------- |
| Id             | شناسه یکتا |
| OrderId        | الزامی     |
| PaymentMethod  | الزامی     |
| Amount         | الزامی     |
| Status         | الزامی     |
| TrackingNumber | قابل‌تهی   |
| CreatedAt      | الزامی     |
| PaidAt         | قابل‌تهی   |

وضعیت پرداخت:

```text
Pending (در انتظار)
Successful (موفق)
Failed (ناموفق)
Cancelled (لغوشده)
```

مبلغ پرداخت باید متناظر با مبلغ قابل‌پرداخت سفارش باشد.

### 9.10 Idempotency پرداخت

پردازش نتیجه پرداخت باید Idempotent باشد.

اگر نتیجه پرداخت یکسان چندین بار دریافت شود، سیستم نباید:

- پرداخت‌های تکراری ایجاد کند.
- ثبت‌نام‌های (Enrollment) تکراری ایجاد کند.
- فاکتورهای تکراری ایجاد کند.
- در وضعیت برنامه، از کاربر چندین‌بار هزینه دریافت کند.

در جایی که قابل‌اعمال است باید از یک شناسه پایدار پرداخت/ارائه‌دهنده استفاده شود.

## 10. فاکتور

### 10.1 فاکتور

یک سفارش پولی موفق باید یک فاکتور در دسترس از پروفایل کاربر داشته باشد.

اطلاعات فاکتور باید شامل موارد زیر باشد:

- شماره فاکتور.
- تاریخ فاکتور.
- اطلاعات مشتری.
- ارجاع سفارش.
- اقلام دوره/سفارش.
- تعداد.
- قیمت واحد.
- تخفیف.
- کد کوپن و تخفیف کوپن، در صورت استفاده از کوپن.
- مبلغ نهایی.
- وضعیت پرداخت.

فاکتور باید تصویر لحظه‌ای مالی خرید تکمیل‌شده را حفظ کند.

تخفیف فاکتور باید شامل تخفیف کوپن باشد و کد کوپن و مبلغ تخفیف کوپن باید به‌عنوان مقادیر Snapshot حفظ شوند. تغییرات بعدی کوپن نباید فاکتور صادرشده را تغییر دهد.

### 10.2 مدل داده فاکتور

فاکتور باید تصویر لحظه‌ای مالی (Financial Snapshot) را در زمان صدور خود حفظ کند.

فاکتور نباید قیمت‌های تاریخی را با کوئری‌گرفتن از موجودیت فعلی Course محاسبه کند.

یک فاکتور باید اطلاعات مالی غیرقابل‌تغییر (Immutable) اختصاصی خود را داشته باشد.

حداقل:

```text
شماره فاکتور
تاریخ فاکتور
مشتری
تلفن مشتری
ایمیل مشتری
مرجع سفارش
مرجع پرداخت
اقلام
تعداد
قیمت واحد
تخفیف
کد کوپن (در صورت استفاده)
تخفیف کوپن (در صورت استفاده)
مالیات در جایی که کاربرد دارد
جمع جزء
مبلغ نهایی
وضعیت پرداخت
```

هر قلم فاکتور باید Snapshot قیمت اختصاصی خود را داشته باشد.

برای مثال:

```text
InvoiceItem
    نام محصول/دوره
    تعداد
    UnitPrice
    تخفیف
    TotalPrice
```

تغییرات قیمت دوره پس از صدور فاکتور نباید فاکتور را تغییر دهد.

### 10.3 غیرقابل‌تغییر بودن فاکتور (Invoice Immutability)

پس از نهایی‌شدن/صدور یک فاکتور، محتوای مالی آن نباید از طریق عملیات معمول CRUD تغییر کند.

اصلاحات باید در صورت معرفی چنین فرآیندی در آینده، از طریق یک فرآیند صریح و مستندشده انجام شوند.

سیستم نباید اطلاعات تاریخی فاکتور را در موارد زیر به‌صورت خاموش (Silently) رونویسی کند:

- تغییر قیمت دوره‌ها.
- تغییر اطلاعات کاربر.
- تغییر تخفیف‌ها.
- تغییر نام محصولات.
- تغییر اطلاعات پرداخت.

### 10.4 تولید و گزارش‌گیری فاکتور

پیاده‌سازی تولید فاکتور باید جدا از مدل Domain مالی ارزیابی شود.

موجودیت Domain مربوط به Invoice باید نمایانگر تصویر لحظه‌ای مالی (Financial Snapshot) باشد.

یک کتابخانه گزارش‌گیری/PDF باید مسئول رندر آن Snapshot به یک سند باشد.

سیستم نباید دغدغه‌های PDF/گزارش‌گیری را مستقیماً درون لایه Domain قرار دهد.

معماری:

```text
سفارش / پرداخت
      |
      v
مدل Domain فاکتور
      |
      v
سرویس Application فاکتور
      |
      v
تولیدکننده گزارش فاکتور
      |
      v
فاکتور PDF / قابل‌چاپ
```

#### 10.4.1 کتابخانه‌های کاندید

فناوری‌های گزارش‌گیری/PDF زیر در دات‌نت بررسی شدند:

##### 10.4.1.1 Stimulsoft Reports

Stimulsoft Reports.WEB از ASP.NET، ASP.NET Core، MVC، Razor Pages و طراحی/مشاهده گزارش مبتنی بر مرورگر پشتیبانی می‌کند. مستندات آن همچنین صراحتاً گزارش‌های فاکتور و خروجی‌گرفتن گزارش‌ها به PDF را پوشش می‌دهد.

Stimulsoft همچنین یک پکیج رسمی دات‌نت و نمونه‌هایی برای بارگذاری، رندر و خروجی‌گرفتن گزارش به PDF ارائه می‌دهد.

این کتابخانه همچنین می‌تواند گزارش‌های رندرشده را از طریق یک Endpoint وب API افشا کند، که در صورت نیاز به ارائه تولید فاکتور به‌عنوان یک سرویس مستقل در آینده، مرتبط خواهد بود.

Stimulsoft علاوه‌بر این، پشتیبانی از فرمت‌های مرتبط با فاکتور الکترونیک مانند ZUGFeRD و Factur-X را مستند کرده است.

##### 10.4.1.2 QuestPDF

QuestPDF یک کتابخانه تولید PDF در سی‌شارپ با یک سیستم چیدمان (Layout) مبتنی بر کامپوننت است.

مستندات رسمی آن یک آموزش اختصاصی برای فاکتور ارائه می‌دهد و جداسازی مدل‌های فاکتور/سند از منطق رندر را توصیه می‌کند.

این کتابخانه می‌تواند PDF را مستقیماً به فایل، آرایه بایت یا Stream تولید کند.

##### 10.4.1.3 FastReport .NET

FastReport .NET قابلیت‌های گزارش‌گیری و خروجی PDF را فراهم می‌کند. مستندات رسمی آن شامل یک API خروجی PDF و مستندات جامع گزارش‌گیری دات‌نت است.

#### 10.4.2 معیارهای انتخاب

راه‌حل فاکتور/گزارش‌گیری باید در برابر موارد زیر ارزیابی شود:

| معیار                     | الزام                                     |

#### 10.4.3 ارزیابی پیشنهادی

کاندید فعلی ترجیح‌داده‌شده عبارت است از:

**Stimulsoft Reports.WEB**

دلیل این انتخاب آن است که پروژه از قبل دارای معماری وب ASP.NET Core است و این محصول به‌طور خاص گزارش‌گیری، طراحی گزارش، مشاهده در مرورگر، خروجی PDF و اسناد سبک فاکتور را برای ASP.NET/ASP.NET Core هدف قرار داده است.

با این حال، انتخاب نهایی کتابخانه باید پس از بررسی موارد زیر انجام شود:

- هزینه مجوز.
- رندر فاکتور فارسی/RTL.
- فونت‌های موردنیاز.
- نیازمندی‌های استقرار.
- روند کار قالب گزارش.
- کیفیت خروجی PDF.
- فرمت‌های خروجی موردنیاز.
- نگهداری بلندمدت.
- نیازمندی‌های استفاده تجاری.

QuestPDF باید یک جایگزین قدرتمند باقی بماند، برای زمانی که تیم مدلی مبتنی بر کد برای تولید PDF را به‌جای یک طراح گزارش بصری ترجیح می‌دهد. آموزش رسمی فاکتور آن، این کتابخانه را به‌طور خاص برای این کاربرد مرتبط می‌سازد.

#### 10.4.4 مرز رندر فاکتور

برنامه باید یک انتزاع مانند زیر تعریف کند:

```csharp
public interface IInvoiceRenderer
{
    Task<byte[]> RenderPdfAsync(
        InvoiceDocument document,
        CancellationToken cancellationToken);
}
```

لایه Domain نباید به Stimulsoft، QuestPDF، FastReport یا هر کتابخانه گزارش‌گیری دیگری ارجاع دهد.

لایه Infrastructure باید حاوی پیاده‌سازی مشخص (Concrete) باشد.

برای مثال:

```text
IInvoiceRenderer
       |
       +---- StimulsoftInvoiceRenderer
```

این پیاده‌سازی بعداً می‌تواند بدون تغییر مدل Domain مربوط به Invoice جایگزین شود.

## 11. سرویس پیامک

### 11.1 سرویس شبیه‌سازی درگاه پیامک (SMS)

قابلیت پیامک ساختگی (Fake) باید به‌عنوان یک **پروژه API جداگانه** در کنار برنامه اصلی وایلند پیاده‌سازی شود.

این سرویس باید رفتار یک API واقعی ارائه‌دهنده پیامک را شبیه‌سازی کند.

هدف این است که برنامه اصلی بتواند بدون نیاز به یک ارائه‌دهنده واقعی پیامک، از طریق یک مرز HTTP واقع‌گرایانه با یک API پیامک ارتباط برقرار کند.

#### 11.1.1 ساختار پروژه

راه‌حل (Solution) باید یک پروژه جداگانه، برای مثال به شکل زیر، داشته باشد:

```text
src/
│
├── Project.Domain/
├── Project.Application/
├── Project.Infrastructure/
├── Project.Web/
├── Project.Admin/
│
└── Project.Sms/
```

`Project.Sms` باید یک اپلیکیشن مستقل ASP.NET Core Web API باشد.

این پروژه نباید حاوی منطق کسب‌وکاری وایلند باشد.

#### 11.1.2 API پیامک

این API باید Endpointهایی مشابه رابطی که معمولاً توسط یک پنل/ارائه‌دهنده پیامک فراهم می‌شود ارائه دهد.

حداقل:

```text
POST /api/v1/sms/send
```

درخواست باید حاوی اطلاعاتی معادل موارد زیر باشد:

```json
{
  "to": "09120000000",
  "message": "Your verification code is 123456"
}
```

پاسخ باید حاوی نتیجه‌ای شبیه ارائه‌دهنده واقعی باشد:

```json
{
  "success": true,
  "messageId": "..."
}
```

قرارداد دقیق درخواست/پاسخ باید مستند و نسخه‌بندی شود.

#### 11.1.3 طراحی ارائه‌دهنده-محور

برنامه وایلند باید با یک انتزاع مانند زیر ارتباط برقرار کند:

```csharp
public interface ISmsService
{
    Task<SendSmsResult> SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

پیاده‌سازی Infrastructure باید API پیامک جداگانه را از طریق HTTP فراخوانی کند.

بنابراین:

```text
برنامه وایلند
        |
        v
ISmsService
        |
        v
HTTP Client
        |
        v
Project.Sms API
        |
        v
ذخیره‌سازی In-Memory
```

این کار برنامه اصلی را از پیاده‌سازی ارائه‌دهنده ساختگی مستقل نگه می‌دارد.

#### 11.1.4 پایگاه‌داده In-Memory

API پیامک باید برای پیاده‌سازی اول از یک فروشگاه داده In-Memory استفاده کند.

استثنا: قالب‌های پیامک (`SmsTemplate`) باید مطابق بخش 11.3.5 در پایگاه‌داده پایدار ذخیره شوند؛ ذخیره‌سازی In-Memory برای ثبت درخواست‌ها و پیام‌های پیامک (به‌ویژه در محیط توسعه/تست) استفاده می‌شود.

این سرویس باید حداقل موارد زیر را ذخیره کند:

```text
درخواست‌های پیامک
پیام‌های پیامک
گیرنده
پیام
وضعیت
شناسه پیام (MessageId)
CreatedAt
SentAt
```

پایداری در PostgreSQL برای سرویس شبیه‌سازی پیامک الزامی نیست.

این سرویس باید بدون نیاز به مایگریشن پایگاه‌داده قابل راه‌اندازی مجدد باشد.

#### 11.1.5 داشبورد پیامک

سرویس پیامک باید یک صفحه مدیریتی/داشبورد ساده مبتنی بر HTML فراهم کند.

داشبورد باید به توسعه‌دهندگان امکان بازرسی آسان موارد زیر را بدهد:

- درخواست‌های ورودی API پیامک.
- شماره‌های تلفن گیرنده.
- محتوای پیام‌ها.
- شناسه‌های پیام تولیدشده.
- وضعیت پیامک.
- زمان‌بندی درخواست‌ها.
- زمان‌بندی ارسال.

نمونه:

```text
شبیه‌ساز پیامک
-------------------------------------------------
شناسه پیام | گیرنده | پیام | وضعیت | تاریخ
-------------------------------------------------
12345      | 0912...   | OTP ... | ارسال‌شده   | ...
12346      | 0913...   | OTP ... | ارسال‌شده   | ...
-------------------------------------------------
```

این داشبورد برای توسعه/تست در نظر گرفته شده است و نیازی نیست یک سیستم مدیریتی در سطح Production باشد.

#### 11.1.6 نیازمندی‌های داشبورد پیامک

داشبورد باید از موارد زیر پشتیبانی کند:

- فهرست درخواست‌های پیامک.
- مشاهده یک درخواست پیامک منفرد.
- فیلترکردن ابتدایی بر اساس گیرنده/وضعیت.
- نمایش زمان درخواست.
- نمایش وضعیت پیام.
- نمایش شناسه پیام.

داشبورد می‌تواند از Razor Pages یا MVC استفاده کند.

#### 11.1.7 جایگزینی ارائه‌دهنده واقعی

سرویس ساختگی پیامک باید بدون تغییر منطق کسب‌وکاری لایه Application قابل جایگزینی با یک پیاده‌سازی ارائه‌دهنده واقعی باشد.

نمونه‌های پیاده‌سازی آینده:

```text
FakeSmsService
KavenegarSmsService
OtherProviderSmsService
```

قرارداد HTTP اختصاصی ارائه‌دهنده باید خارج از لایه Domain باقی بماند.

### 11.2 مستندسازی و سازگاری API پیامک

API شبیه‌ساز پیامک باید پس از بررسی مدل API عمومی یک ارائه‌دهنده واقعی موجود پیامک طراحی شود.

پیاده‌سازی باید از مفاهیم رایج ارائه‌دهندگان پیروی کند، مانند:

```text
کلید API / احراز هویت
گیرنده
فرستنده
پیام
شناسه پیام
وضعیت ارائه‌دهنده
وضعیت درخواست
```

شبیه‌ساز نباید به‌صورت غیرضروری پیاده‌سازی خصوصی یک ارائه‌دهنده را کپی کند.

هدف آن بازتولید الگوی یکپارچه‌سازی موردانتظار یک ارائه‌دهنده واقعی پیامک است.

مستندات ارائه‌دهنده انتخاب‌شده باید به‌عنوان یک مرجع خارجی برای پیاده‌سازی نگهداری شود.

### 11.3 توسعه لایه SMS Provider و مدیریت قالب‌های پیامک

#### 11.3.1 هدف و معماری کلی

لایه SMS Provider باید به‌عنوان یک ماژول مستقل و قابل توسعه طراحی و پیاده‌سازی شود تا امکان ارسال پیامک، مدیریت قالب‌های پیامک و ارتباط با ارائه‌دهندگان مختلف پیامک را فراهم کند.

این لایه باید یک API مستقل برای مدیریت و ارسال پیامک ارائه دهد و امکان استفاده از قابلیت‌های آن از طریق یک پکیج مستقل در برنامه اصلی وایلند وجود داشته باشد.

معماری باید به‌گونه‌ای طراحی شود که لایه Application برنامه اصلی به پیاده‌سازی یک ارائه‌دهنده پیامک خاص وابسته نباشد و بتوان بدون تغییر منطق کسب‌وکار، ارائه‌دهنده پیامک را تغییر داد.

نیازمندی‌های اصلی عبارت‌اند از:

- ارائه API مستقل برای سرویس پیامک.
- پشتیبانی از نسخه‌بندی API.
- مدیریت قالب‌های پیامک (SMS Templates).
- تعریف پارامترهای قابل جایگزینی در قالب‌ها.
- اختصاص کد یکتا به هر قالب پیامک.
- ذخیره‌سازی قالب‌ها و اطلاعات مرتبط در پایگاه داده.
- ارائه View برای مدیریت و مشاهده قالب‌ها در لایه SMS.
- ایجاد پکیج مستقل برای استفاده از قابلیت‌های SMS Provider در برنامه اصلی.
- استفاده از Abstraction برای مستقل نگه‌داشتن مصرف‌کننده از پیاده‌سازی ارائه‌دهنده.
- استفاده از Refit برای برقراری ارتباط HTTP در پیاده‌سازی کلاینت API.
- فراهم‌کردن امکان جایگزینی ارائه‌دهنده ساختگی با ارائه‌دهندگان واقعی.

#### 11.3.2 ساختار پروژه و تفکیک مسئولیت‌ها

این پروژه نباید حاوی منطق کسب‌وکاری اختصاصی وایلند باشد.

##### 11.3.2.2 Project.Sms.Provider

این پروژه باید به‌صورت یک پکیج مستقل و قابل استفاده مجدد طراحی شود تا برنامه اصلی بتواند بدون پیاده‌سازی مستقیم ارتباط HTTP، از قابلیت‌های سرویس پیامک استفاده کند.

مسئولیت‌های این پکیج عبارت‌اند از:

#### 11.3.3 ارائه API مستقل توسط SMS Provider

سرویس SMS باید API مستقلی برای مصرف توسط برنامه اصلی و سایر کلاینت‌ها ارائه دهد.

این API باید امکان ارسال پیامک بر اساس قالب و پارامترهای ورودی را فراهم کند.

Endpointهای اصلی پیشنهادی:

| متد      | Endpoint                       | توضیحات                                |
| -------- | ------------------------------ | -------------------------------------- |
| `POST`   | `/api/v1/sms/send`             | ارسال پیامک با استفاده از متن یا قالب  |
| `GET`    | `/api/v1/sms/{messageId}`      | دریافت اطلاعات یک پیامک                |
| `GET`    | `/api/v1/sms/templates`        | دریافت فهرست قالب‌های پیامک            |
| `GET`    | `/api/v1/sms/templates/{code}` | دریافت اطلاعات یک قالب بر اساس کد یکتا |
| `POST`   | `/api/v1/sms/templates`        | ایجاد قالب پیامک                       |
| `PUT`    | `/api/v1/sms/templates/{code}` | ویرایش قالب پیامک                      |
| `DELETE` | `/api/v1/sms/templates/{code}` | حذف قالب پیامک، در صورت مجاز بودن      |

Endpointهای مربوط به مدیریت قالب‌ها باید متناسب با نیازمندی‌های امنیتی، از دسترسی غیرمجاز محافظت شوند.

قرارداد درخواست و پاسخ هر Endpoint باید مستند باشد و در نسخه‌بندی API لحاظ شود.

#### 11.3.4 مدیریت قالب‌های پیامک (SMS Templates)

سرویس SMS باید از قالب‌های قابل استفاده مجدد برای تولید محتوای پیامک پشتیبانی کند.

هر قالب باید شامل یک متن اصلی و مجموعه‌ای از پارامترهای قابل جایگزینی باشد.

برای مثال، قالب زیر را در نظر بگیرید:

**نام قالب:** تأیید شماره تلفن

**کد یکتا:** `SMS-OTP-001`

**متن قالب:**

```text
کد تأیید شما: {{code}}
این کد تا {{expirationMinutes}} دقیقه معتبر است.
```

**پارامترهای قالب:**

```json
{
  "code": "123456",
  "expirationMinutes": 5
}
```

**متن نهایی پیامک:**

```text
کد تأیید شما: 123456
این کد تا 5 دقیقه معتبر است.
```

##### 11.3.4.1 اطلاعات موردنیاز هر قالب

هر قالب پیامک باید حداقل اطلاعات زیر را داشته باشد:

| فیلد          | توضیحات                                  |
| ------------- | ---------------------------------------- |
| `Id`          | شناسه داخلی قالب                         |
| `Code`        | کد یکتای قابل استفاده برای ارجاع به قالب |
| `Name`        | نام قابل نمایش قالب                      |
| `Content`     | متن قالب پیامک                           |
| `Parameters`  | تعریف پارامترهای موردنیاز قالب           |
| `Description` | توضیحات اختیاری                          |
| `IsActive`    | وضعیت فعال یا غیرفعال بودن قالب          |
| `CreatedAt`   | زمان ایجاد قالب                          |
| `UpdatedAt`   | زمان آخرین ویرایش                        |

کد یکتای قالب باید در محدوده موردنظر سیستم، یکتا باشد و برای شناسایی قالب در درخواست‌های API استفاده شود.

##### 11.3.4.2 تعریف پارامترهای قالب

هر قالب باید بتواند پارامترهای موردنیاز خود را تعریف کند.

تعریف هر پارامتر می‌تواند شامل موارد زیر باشد:

- نام پارامتر.
- نوع داده.
- اجباری یا اختیاری بودن.
- مقدار پیش‌فرض، در صورت وجود.
- توضیحات پارامتر.

برای مثال:

```json
{
  "code": {
    "type": "string",
    "required": true,
    "description": "کد تأیید"
  },
  "expirationMinutes": {
    "type": "integer",
    "required": true,
    "description": "مدت اعتبار کد به دقیقه"
  }
}
```

سرویس باید هنگام استفاده از قالب، پارامترهای ارسالی را اعتبارسنجی کند.

در صورت ارسال‌نشدن پارامتر اجباری یا وجود پارامتر موردنیاز در قالب که قابل جایگزینی نیست، درخواست باید با خطای مشخص و مستند رد شود.

##### 11.3.4.3 نحوه ارسال پیامک با قالب

درخواست ارسال پیامک باید امکان ارجاع به قالب از طریق کد یکتای آن و ارسال مقادیر پارامترها را فراهم کند.

نمونه درخواست:

`POST /api/v1/sms/send`

```json
{
  "to": "09120000000",
  "templateCode": "SMS-OTP-001",
  "parameters": {
    "code": "123456",
    "expirationMinutes": 5
  }
}
```

در این حالت، سرویس باید مراحل زیر را اجرا کند:

1. قالب را بر اساس `templateCode` پیدا کند.
2. فعال بودن قالب را بررسی کند.
3. پارامترهای ورودی را اعتبارسنجی کند.
4. مقادیر پارامترها را در متن قالب جایگزین کند.
5. درخواست ارسال پیامک را ثبت کند.
6. پیام تولیدشده را مطابق رفتار ارائه‌دهنده شبیه‌سازی‌شده پردازش کند.
7. نتیجه عملیات را به همراه شناسه پیام برگرداند.

نمونه پاسخ موفق:

```json
{
  "success": true,
  "messageId": "sms_01JABC123XYZ",
  "status": "Sent"
}
```

شناسه پیام باید برای هر پیام تولیدشده یکتا باشد.

**نکته:** ثبت درخواست و ایجاد پیام در سرویس شبیه‌ساز لزوماً به معنای تحویل واقعی پیامک به تلفن گیرنده نیست. وضعیت‌های API باید این تفاوت را به‌روشنی منعکس کنند.

#### 11.3.5 ذخیره‌سازی قالب‌ها و پیامک‌ها

اطلاعات قالب‌های پیامک باید در پایگاه داده ذخیره شوند تا پس از راه‌اندازی مجدد سرویس از بین نروند.

برای پیاده‌سازی اولیه می‌توان از پایگاه داده موجود پروژه یا یک پایگاه داده مستقل برای سرویس SMS استفاده کرد.

ساختار داده‌ها باید حداقل موجودیت‌های زیر را پوشش دهد.

##### 11.3.5.1 موجودیت SmsTemplate

مسئول نگهداری قالب‌های پیامک.

```text
SmsTemplate
-----------
Id
Code
Name
Content
Parameters
Description
IsActive
CreatedAt
UpdatedAt
```

فیلد `Code` باید دارای محدودیت یکتایی در پایگاه داده باشد.

فیلد `Parameters` می‌تواند با توجه به فناوری ذخیره‌سازی، به‌صورت JSON یا ساختاری رابطه‌ای پیاده‌سازی شود.

##### 11.3.5.2 موجودیت SmsRequest

```text

----------

Endpoint

ReceivedAt
ResponseStatus
ErrorCode
ErrorMessage
```

این موجودیت امکان بررسی درخواست‌های ورودی و خطاهای احتمالی را فراهم می‌کند.

در صورت ثبت محتوای کامل درخواست‌ها، اطلاعات حساس باید مطابق سیاست‌های امنیتی سیستم مدیریت یا حذف شوند.

##### 11.3.5.3 موجودیت SmsMessage

مسئول نگهداری اطلاعات پیامک‌های تولیدشده.

```text

----------
Id
MessageId
TemplateCode
Recipient
Message
Status
CreatedAt
SentAt
```

در صورت نیاز می‌توان اطلاعات تکمیلی مانند `ProviderStatus`، `ErrorCode` و `ErrorMessage` را نیز به این موجودیت اضافه کرد.

مقادیر وضعیت باید در قرارداد API تعریف شوند؛ برای مثال:

- `Pending`
- `Sent`
- `Failed`

معنای هر وضعیت باید مشخص باشد. به‌خصوص، وضعیت `Sent` در شبیه‌ساز باید نشان‌دهنده رفتار تعریف‌شده سرویس باشد و نباید به‌عنوان تأیید تحویل واقعی پیامک تفسیر شود.

#### 11.3.7 پکیج مستقل SMS Provider

به همین منظور، باید یک پکیج مستقل با نام پیشنهادی `Project.Sms.Provider` ایجاد شود.

این پکیج باید از طریق Abstractionهای عمومی، امکان استفاده از قابلیت‌های سرویس پیامک را فراهم کند.

##### 11.3.7.1 تعریف Abstraction

پکیج باید یک Interface عمومی برای ارسال پیامک ارائه دهد.

برای مثال:

```csharp
public interface ISmsService
{
    Task<SendSmsResult> SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

برای پشتیبانی از قالب‌ها، می‌توان یک قرارداد مستقل نیز تعریف کرد:

```csharp
public interface ISmsTemplateService
{
    Task<SendSmsResult> SendTemplateAsync(
        string phoneNumber,
        string templateCode,
        IReadOnlyDictionary<string, object> parameters,
        CancellationToken cancellationToken);
}
```

مدل نتیجه ارسال پیامک نیز باید مستقل از پیاده‌سازی باشد:

```csharp
public sealed class SendSmsResult
{
    public bool Success { get; init; }

    public string? MessageId { get; init; }

    public string? Status { get; init; }

    public string? ErrorCode { get; init; }

    public string? ErrorMessage { get; init; }
}
```

این قراردادها نمونه پیشنهادی هستند و باید با قرارداد نهایی API هماهنگ شوند.

قراردادهای عمومی پکیج نباید به مدل‌های داخلی پروژه `Project.Sms` یا مدل‌های اختصاصی یک ارائه‌دهنده خاص وابسته باشند.

##### 11.3.7.2 مسئولیت برنامه اصلی

پس از اضافه‌شدن پکیج، برنامه اصلی باید از طریق Interfaceهای عمومی با سرویس پیامک تعامل کند.

جریان ارتباطی به شکل زیر خواهد بود:

```text
Project.Web / Project.Application
                |
                v
            ISmsService
                |
                v
       SMS Provider Package
                |
                v
          Refit Client
                |
                v
         Project.Sms API
                |
                v
     SMS Application Services
                |
                v
        Database / Storage
```

در این ساختار، برنامه اصلی از جزئیات پیاده‌سازی ارتباط با API مستقل است.

در نتیجه، تغییر آدرس سرویس، تنظیمات ارتباطی یا پیاده‌سازی کلاینت نباید باعث تغییر در منطق کسب‌وکار برنامه اصلی شود.

#### 11.3.8 استفاده از Refit برای ارتباط HTTP

پیاده‌سازی کلاینت API در پکیج `Project.Sms.Provider` باید به‌جای استفاده مستقیم از `HttpClient` برای تعریف و فراخوانی Endpointها، از کتابخانه Refit استفاده کند.

Refit باید قرارداد HTTP سرویس SMS را به‌صورت Interface تعریف کند و عملیات ارسال درخواست را مدیریت کند.

نمونه:

```csharp
using Refit;

public interface ISmsApiClient
{
    [Post("/api/v1/sms/send")]
    Task<ApiResponse<SendSmsApiResponse>> SendAsync(
        [Body] SendSmsApiRequest request,
        CancellationToken cancellationToken);
}
```

مدل‌های `SendSmsApiRequest` و `SendSmsApiResponse` باید در بخش قراردادهای ارتباطی پکیج تعریف شوند.

در صورت تفاوت قرارداد درخواست ارسال متن مستقیم و ارسال با قالب، باید از Endpointها یا قراردادهای متناسب با API نهایی استفاده شود.

##### 11.3.8.1 ثبت کلاینت در Dependency Injection

پکیج باید امکان ثبت سرویس و کلاینت را از طریق یک Extension Method فراهم کند.

برای مثال:

```csharp
services
    .AddRefitClient<ISmsApiClient>()
    .ConfigureHttpClient(client =>
    {
        client.BaseAddress = new Uri(
            configuration["SmsProvider:BaseUrl"]!);
    });
```

آدرس پایه سرویس باید از طریق Configuration دریافت شود و نباید در کد به‌صورت ثابت تعریف شود.

همچنین، تنظیمات احراز هویت، Timeout و سیاست‌های مدیریت خطا باید در صورت نیاز از طریق تنظیمات پکیج قابل پیکربندی باشند.

##### 11.3.8.2 تبدیل قراردادهای API به مدل عمومی

پکیج باید پاسخ دریافتی از Refit را بررسی و به مدل عمومی `SendSmsResult` تبدیل کند.

این تبدیل باید وضعیت‌های زیر را در نظر بگیرد:

- پاسخ موفق API.
- پاسخ ناموفق API.
- خطاهای اعتبارسنجی.
- خطاهای ارتباطی.
- Timeout.
- پاسخ نامعتبر یا غیرقابل پردازش.

منطق کسب‌وکار برنامه اصلی نباید مستقیماً با انواع خطا یا مدل‌های اختصاصی Refit درگیر شود.

**نکته معماری:** Refit در لایه زیرین از `HttpClient` استفاده می‌کند. الزام این بخش، استفاده از Refit برای تعریف و فراخوانی قرارداد HTTP است، نه حذف کامل `HttpClient` از زیرساخت ارتباطی.

#### 11.3.9 استقلال از ارائه‌دهنده پیامک

معماری باید امکان جایگزینی پیاده‌سازی سرویس پیامک را بدون تغییر در منطق کسب‌وکار برنامه اصلی فراهم کند.

پیاده‌سازی‌های احتمالی عبارت‌اند از:

```text
ISmsService
    |
    ├── FakeSmsService
    |
    ├── KavenegarSmsService
    |
    └── OtherProviderSmsService
```

پیاده‌سازی‌های فوق باید از قرارداد عمومی یکسان پیروی کنند؛ با این حال، هر ارائه‌دهنده می‌تواند قرارداد ارتباطی و مدل‌های اختصاصی خود را در لایه Infrastructure داشته باشد.

برای نمونه:

- `FakeSmsService` می‌تواند برای تست یا محیط توسعه استفاده شود.
- `KavenegarSmsService` می‌تواند با API ارائه‌دهنده کاوه‌نگار ارتباط برقرار کند.
- پیاده‌سازی‌های آینده می‌توانند به سایر ارائه‌دهندگان متصل شوند.

در معماری مبتنی بر پکیج، برنامه اصلی فقط به Abstraction وابسته است و انتخاب پیاده‌سازی از طریق Dependency Injection و Configuration انجام می‌شود.

قرارداد HTTP اختصاصی ارائه‌دهندگان نباید به لایه Domain یا منطق کسب‌وکار برنامه اصلی نشت کند.

#### 11.3.10 نسخه‌بندی API پیامک

نسخه‌بندی API سرویس SMS الزامی است و باید از ابتدای پیاده‌سازی در طراحی Endpointها و قراردادهای ارتباطی لحاظ شود.

نسخه‌بندی مسیرمحور به‌عنوان روش اولیه پیشنهاد می‌شود.

برای مثال:

```text
/api/v1/sms/send
/api/v1/sms/templates
/api/v1/sms/templates/{code}
```

در صورت تغییرات ناسازگار در قرارداد API، نسخه جدیدی ارائه خواهد شد:

```text
/api/v2/sms/send
/api/v2/sms/templates
```

##### 11.3.10.1 الزامات نسخه‌بندی

- هر نسخه باید قرارداد درخواست و پاسخ مشخصی داشته باشد.
- تغییرات ناسازگار نباید بدون اعلام نسخه جدید در قرارداد موجود اعمال شوند.
- مستندات هر نسخه باید مستقل و قابل بررسی باشند.
- نسخه مورد استفاده باید در پکیج SMS Provider مشخص باشد.
- ارتقای نسخه API باید بدون وابستگی مستقیم منطق کسب‌وکار به جزئیات نسخه‌بندی انجام شود.
- در صورت پشتیبانی از چند نسخه به‌صورت هم‌زمان، رفتار و دوره پشتیبانی هر نسخه باید مستند شود.

##### 11.3.10.2 هماهنگی نسخه API با پکیج

پکیج `Project.Sms.Provider` باید با نسخه مشخصی از قرارداد API سازگار باشد.

تغییر نسخه API نباید باعث تغییر پنهانی رفتار پکیج شود.

در صورت نیاز به پشتیبانی از نسخه جدید، می‌توان نسخه جدیدی از پکیج یا پیاده‌سازی سازگار با نسخه جدید API ارائه کرد.

نسخه‌بندی API سرویس و نسخه‌بندی پکیج NuGet دو موضوع مستقل هستند و باید جداگانه مدیریت شوند.

#### 11.3.11 امنیت و مدیریت خطا

سرویس SMS و پکیج مصرف‌کننده باید حداقل الزامات امنیتی و مدیریت خطای زیر را رعایت کنند:

- امکان احراز هویت درخواست‌های API از طریق API Key یا روش مناسب دیگر.
- نگهداری اطلاعات احراز هویت در Configuration امن.
- جلوگیری از ثبت کلیدهای API و سایر اطلاعات حساس در لاگ‌ها.
- اعتبارسنجی شماره تلفن، کد قالب و پارامترهای ارسالی.
- بررسی فعال بودن قالب پیش از تولید پیام.
- مدیریت خطاهای ارتباطی و Timeout.
- ارائه پاسخ خطای استاندارد و قابل پردازش.
- ثبت خطاهای عملیاتی برای بررسی و عیب‌یابی.
- جلوگیری از نمایش اطلاعات حساس در داشبورد مدیریتی.

در صورت استفاده از API Key، نحوه ارسال، اعتبارسنجی و مدیریت آن باید در مستندات API مشخص شود.

همچنین، خطاهای شبکه نباید به‌صورت خودکار به‌عنوان شکست قطعی ارسال پیامک تلقی شوند؛ زیرا در برخی شرایط ممکن است سرویس پیامک درخواست را پردازش کرده باشد، اما پاسخ به کلاینت نرسیده باشد. سیاست Retry باید با درنظرگرفتن احتمال ارسال تکراری طراحی شود.

#### 11.3.12 مستندسازی API

قرارداد API سرویس SMS باید مستند و قابل استفاده برای توسعه‌دهندگان باشد.

مستندات باید حداقل شامل موارد زیر باشند:

- معرفی سرویس و کاربرد آن.
- نسخه‌های پشتیبانی‌شده API.
- Endpointهای موجود.
- ساختار درخواست و پاسخ.
- مدل‌های داده.
- نحوه ارسال پیامک با متن مستقیم.
- نحوه ارسال پیامک با استفاده از قالب.
- ساختار تعریف پارامترهای قالب.
- روش احراز هویت.
- فهرست کدهای وضعیت و خطا.
- نمونه درخواست‌ها و پاسخ‌ها.
- محدودیت‌ها و رفتارهای سرویس شبیه‌ساز.

استفاده از OpenAPI/Swagger برای مستندسازی API توصیه می‌شود.

همچنین، مستندات عمومی API ارائه‌دهنده واقعی انتخاب‌شده باید به‌عنوان مرجع خارجی نگهداری شود تا قرارداد شبیه‌ساز از الگوهای رایج صنعت پیروی کند.

هدف، شبیه‌سازی قرارداد عمومی یک ارائه‌دهنده واقعی است؛ نه کپی‌کردن جزئیات داخلی یا پیاده‌سازی خصوصی آن.

#### 11.3.14 معیارهای پذیرش (Acceptance Criteria)

این نیازمندی زمانی تکمیل‌شده محسوب می‌شود که موارد زیر برقرار باشند:

1. سرویس SMS به‌صورت یک پروژه مستقل قابل اجرا باشد.
2. سرویس، API نسخه‌بندی‌شده و مستند ارائه دهد.
3. امکان ارسال پیامک با متن مستقیم وجود داشته باشد.
4. امکان تعریف و استفاده از قالب‌های پیامک فراهم باشد.
5. هر قالب دارای کد یکتا و پارامترهای مشخص باشد.
6. قالب‌ها و اطلاعات پیامک‌ها در پایگاه داده ذخیره شوند.
7. اعتبارسنجی قالب‌ها و پارامترهای ارسالی انجام شود.
8. یک View برای مشاهده و مدیریت قالب‌ها وجود داشته باشد.
9. داشبورد امکان مشاهده درخواست‌ها و پیامک‌های ثبت‌شده را فراهم کند.
10. پکیج مستقل `Project.Sms.Provider` قابل استفاده در برنامه اصلی باشد.
11. پکیج، Abstractionهای عمومی و مستقل از پیاده‌سازی ارائه دهد.
12. ارتباط HTTP پکیج با استفاده از Refit پیاده‌سازی شده باشد.
13. برنامه اصلی بدون فراخوانی مستقیم API پیامک بتواند از طریق پکیج، پیامک ارسال کند.
14. تغییر پیاده‌سازی ارائه‌دهنده پیامک مستلزم تغییر منطق کسب‌وکار برنامه اصلی نباشد.
15. نسخه‌بندی API و سازگاری پکیج با قرارداد API مستند شده باشد.
16. خطاهای API و ارتباطات خارجی به‌صورت قابل پیش‌بینی مدیریت شوند.
17. تست‌های خودکار برای قابلیت‌های اصلی سرویس و پکیج وجود داشته باشند.

#### 11.3.15 تصمیم‌های معماری و نکات اجرایی

برای جلوگیری از ابهام در پیاده‌سازی، تصمیم‌های زیر باید در طراحی نهایی لحاظ شوند:

| ساختار سرویس SMS                 | پروژه مستقل ASP.NET Core Web API                 |

تصمیم نهایی: قالب‌ها در پایگاه‌داده پایدار ذخیره می‌شوند و امکان استفاده از ذخیره‌سازی In-Memory برای ثبت پیامک‌ها در محیط تست همچنان حفظ می‌شود.

### 12.1 بلاگ

#### 12.1.1 دسته‌بندی بلاگ

پلتفرم باید از دسته‌بندی‌های بلاگ پشتیبانی کند.

فیلدهای دسته‌بندی بلاگ:

| فیلد         | الزام               |
| ------------ | ------------------- |
| Id           | شناسه یکتا          |
| Name         | الزامی              |
| LatinName    | الزامی              |

قواعد دسته‌بندی بلاگ:

- دسته‌بندی‌های بلاگ می‌توانند سلسله‌مراتبی باشند؛ حداکثر عمق سه سطحی برای آن‌ها اعمال نمی‌شود، مگر آنکه صراحتاً پیکربندی شود.
- یک دسته‌بندی بلاگ نمی‌تواند والد خودش باشد.
- روابط والد چرخه‌ای ممنوع هستند.
- دسته‌بندی‌های غیرفعال نباید برای دسته‌بندی پست‌های جدید قابل‌انتخاب باشند.
- روابط موجود نباید هنگام غیرفعال شدن یک دسته‌بندی به‌صورت بی‌سروصدا حذف شوند.
- حذف دسته‌بندی بلاگی که توسط یک پست ارجاع داده شده باید جلوگیری یا به‌صراحت مدیریت شود و نباید رابطه پست-دسته‌بندی را به‌صورت یتیم رها کند.
- دسته‌بندی‌های بلاگ از قواعد عمومی Soft Delete و Audit تعریف‌شده در بخش‌های 4.1 و 4.2 پیروی می‌کنند.

## 13. رابط کاربری: وب‌سایت عمومی و پنل مدیریت

### 13.1 وب‌سایت عمومی

وب‌سایت عمومی باید با ASP.NET Core MVC پیاده‌سازی شود.

#### 13.1.1 صفحه اصلی

صفحه اصلی باید از بخش‌های محتوا/دوره درخواست‌شده موجود پشتیبانی کند، از جمله:

- دوره‌های ویژه.
- دوره‌های شگفت‌انگیز.
- سایر بخش‌های دوره موردنیاز محتوای پیکربندی‌شده سایت.
- مقالات اخیر.
- سوالات متداول عمومی در جایی که پیکربندی شده.

#### 13.1.2 لیست دوره‌ها

صفحه لیست دوره‌ها باید دوره‌های منتشرشده را نمایش دهد.

این صفحه باید از کشف دوره آگاه از دسته‌بندی پشتیبانی کند.

حداقل باید موارد زیر را نمایش دهد:

- عنوان دوره.
- تصویر اصلی.
- توضیح کوتاه.
- قیمت.
- تخفیف/قیمت نهایی در صورت وجود.
- وضعیت رایگان/پولی.

#### 13.1.3 جزئیات دوره

صفحه جزئیات دوره باید موارد زیر را نمایش دهد:

- عنوان دوره.
- تصویر اصلی.
- توضیح کوتاه.
- توضیح کامل.
- دسته‌بندی‌ها.
- اطلاعات مدرس.
- قیمت.
- تخفیف.
- ویدیو معرفی.
- بخش‌ها.
- اپیزودها.
- مدت‌زمان اپیزودها.
- اپیزودهای رایگان.
- سوالات متداول دوره.
- وضعیت مشاهده هر اپیزود برای کاربر فعلی (`NotWatched` /`InProgress` /`Watched` /`Locked`).
- خلاصه پیشرفت دوره برای کاربر فعلی (برای مثال تعداد اپیزودهای مشاهده‌شده از کل اپیزودها).

#### 13.1.4 لیست بلاگ

صفحه لیست بلاگ باید پست‌های عمومی بلاگ را نمایش دهد.

#### 13.1.5 جزئیات بلاگ

صفحه مقاله باید موارد زیر را نمایش دهد:

- عنوان.
- توضیح کوتاه.
- محتوا.
- نویسنده.
- تصویر.
- وضعیت انتشار/نمایش.

#### 13.1.6 صفحات احراز هویت

ورود و ثبت‌نام می‌توانند در یک جریان احراز هویت یکپارچه ترکیب شوند.

تجربه احراز هویت باید از موارد زیر پشتیبانی کند:

- OTP تلفنی.
- ورود با گوگل.
- بازیابی رمز عبور در جایی که یک رمز عبور محلی وجود دارد.

#### 13.1.7 فراموشی رمز عبور

سیستم باید یک جریان بازیابی رمز عبور فراهم کند.

مکانیزم بازیابی باید از یک توکن امن و زمان‌محدود یا مکانیزمی معادل استفاده کند.

توکن‌های بازنشانی رمز عبور باید:

- زمان‌محدود باشند.
- تک‌مصرف باشند.
- پس از بازنشانی موفق باطل شوند.

### 13.2 پروفایل کاربر

بخش پروفایل باید شامل موارد زیر باشد:

#### 13.2.1 اطلاعات کاربر

نمایش پروفایل فعلی کاربر و اطلاعات حساب.

#### 13.2.2 ویرایش اطلاعات

کاربران می‌توانند فیلدهای مجاز پروفایل را به‌روزرسانی کنند.

فیلدهای حساس هویتی مانند کد ملی ممکن است نیازمند اعتبارسنجی اضافی باشند یا در صورت معرفی یک مکانیزم تایید، پس از تایید غیرقابل‌ویرایش شوند.

#### 13.2.3 تغییر رمز عبور

کاربران احرازهویت‌شده با رمز عبور محلی باید بتوانند رمز عبور خود را تغییر دهند.

#### 13.2.4 دوره‌های موردعلاقه

نمایش دوره‌های موردعلاقه کاربر.

#### 13.2.5 دوره‌های خریداری‌شده

نمایش دوره‌هایی که کاربر به آن‌ها دسترسی دارد.

#### 13.2.6 تاریخچه پرداخت

نمایش تاریخچه پرداخت کاربر.

#### 13.2.7 فاکتورها

کاربران باید بتوانند فاکتورهای خود را در جایی که توسط لایه ارائه پشتیبانی می‌شود مشاهده/دانلود کنند.

#### 13.2.8 پیشرفت اپیزود

ناحیه پروفایل کاربر می‌تواند پیشرفت مشاهده کاربر در دوره‌ها را نمایش دهد، از جمله:

- درصد پیشرفت هر دوره.
- وضعیت هر اپیزود (`NotWatched` /`InProgress` /`Watched`).
- آخرین اپیزود مشاهده‌شده و زمان آن.

اپیزودهای `Locked` باید به‌صورت قفل‌شده نمایش داده شوند و نباید کنترل‌های مربوط به پیشرفت را در اختیار کاربر قرار دهند.

### 13.3 صفحه سبد خرید

صفحه سبد خرید باید موارد زیر را نمایش دهد:

- دوره.
- تعداد.
- قیمت واحد.
- تخفیف.
- جمع نهایی ردیف.
- جمع جزء (مجموع جمع‌های ردیف‌ها پس از تخفیف‌های سطح دوره).
- تخفیف کوپن، در صورت اعمال کوپن.
- جمع کل سبد خرید (مبلغ قابل پرداخت پس از کسر تخفیف کوپن).

کاربران باید بتوانند اقلام را حذف کنند.

تغییر تعداد باید قواعد خرید دوره را رعایت کند.

صفحه سبد خرید باید به کاربر احرازهویت‌شده اجازه دهد کوپن اعمال کند. باید شامل موارد زیر باشد:

- یک ورودی کد کوپن همراه با عملیات اعمال، که تا زمانی که کوپنی اعمال نشده نمایش داده می‌شود.
- کد کوپن اعمال‌شده همراه با عملیات حذف آن.
- یک پیام روشن زمانی که کدی قابل اعمال نیست.

اعمال یا حذف کوپن باید بلافاصله مجموع‌های نمایش‌داده‌شده را با مقادیر محاسبه‌شده توسط سرور به‌روز کند.

پیام‌های شکست باید به دلایلی محدود شوند که کاربر می‌تواند نسبت به آن‌ها اقدام کند (برای مثال، حداقل مبلغ سفارش رعایت نشده است). هر شکست دیگری (کد ناشناخته، غیرفعال، منقضی، شروع‌نشده یا تمام‌شده) باید از یک پیام عمومی استفاده کند تا کدهای معتبر از طریق حدس زدن قابل کشف نباشند.

تلاش‌های اعمال کوپن باید Rate Limit شوند.

### 13.4 فرآیند پرداخت (Checkout)

فرآیند پرداخت باید دقیقاً شامل سه مرحله مفهومی باشد.

```text
1. اطلاعات
        |
        v
2. پرداخت
        |
        v
3. نتیجه پرداخت
```

#### 13.4.1 مرحله 1 — اطلاعات

سیستم باید اطلاعات موردنیاز مشتری را اعتبارسنجی کند.

شماره تلفن پیش از پرداخت الزامی است.

خلاصه سفارش باید جمع جزء، کد کوپن اعمال‌شده (در صورت وجود)، تخفیف کوپن و مبلغ قابل پرداخت را نمایش دهد.

کاربر باید بتواند در این مرحله با همان قواعد صفحه سبد خرید، کوپن را اعمال، تغییر یا حذف کند. کوپن تا زمانی که سفارش در انتظار در مرحله 2 ایجاد نشده است قابل تغییر است.

#### 13.4.2 مرحله 2 — پرداخت

کاربر باید یکی از مقادیر enum روش پرداخت پشتیبانی‌شده را انتخاب کند.

برنامه باید وضعیت لازم پرداخت/سفارشِ در انتظار را ایجاد کند.

هنگامی که سبد خرید کوپن اعمال‌شده دارد، ایجاد سفارش باید علاوه بر آن موارد زیر را انجام دهد:

- کوپن را در همان لحظه در سمت سرور مجدداً اعتبارسنجی کند (بخش 9.4).
- تخفیف کوپن و مبلغ قابل پرداخت را مجدداً محاسبه کند.
- ارجاع کوپن و مبلغ تخفیف کوپن را به‌صورت Snapshot روی سفارش ذخیره کند.
- یک استفاده از کوپن را به‌صورت اتمیک و داخل تراکنش ایجاد سفارش رزرو کند.

مبلغ پرداخت باید برابر مبلغ قابل پرداخت سفارش پس از کسر تخفیف کوپن باشد.

اگر کوپن هنگام ایجاد سفارش دیگر معتبر نباشد، هیچ سفارش و پرداختی نباید ایجاد شود. کاربر باید همراه با یک پیام و مجموع‌های مجدداً محاسبه‌شده به مرحله 1 بازگردانده شود و باید صراحتاً ادامه دادن را انتخاب کند. سیستم نباید بی‌صدا با قیمت بالاتر ادامه دهد.

پس از ایجاد سفارش در انتظار، کوپن و مبالغ آن ثابت می‌شوند و نباید تغییر کنند.

#### 13.4.3 مرحله 3 — نتیجه پرداخت

سیستم باید موارد زیر را نمایش دهد:

- پرداخت موفق.
- پرداخت ناموفق.

نتیجه باید خلاصه سفارش، شامل کد کوپن و تخفیف کوپن در صورت استفاده از کوپن، را نمایش دهد.

برای پرداخت موفق:

```text
پرداخت موفق
        |
        v
سفارش = پرداخت‌شده
        |
        v
اعطای دسترسی به دوره
        |
        v
ایجاد/نهایی‌سازی فاکتور
```

کل این جریان باید در جایی که عملیات پایگاه‌داده دخیل است، از نظر تراکنشی سازگار باشد.

فاکتور ایجادشده برای یک سفارش پرداخت‌شده باید Snapshot کوپن را مطابق بخش 10.1 حفظ کند.

اگر سفارش `Failed` یا `Cancelled` شود، استفاده از کوپن که برای آن رزرو شده بود باید دقیقاً یک‌بار آزاد شود. سبد خرید، شامل کوپن اعمال‌شده آن، باید برای تلاش مجدد کاربر حفظ شود و کوپن فقط در صورتی اعمال‌شده باقی می‌ماند که همچنان واجد شرایط باشد.

### 13.5 پنل مدیریت

پنل مدیریت باید با Razor Pages پیاده‌سازی شود.

تمام عملیات مدیریتی باید توسط مجوز محافظت شوند.

#### 13.5.1 ماژول‌های موردنیاز مدیریت

پنل باید مدیریت موارد زیر را فراهم کند:

- دسته‌بندی‌ها.
- دوره‌ها.
- بخش‌های دوره.
- اپیزودها.
- پیوست‌های اپیزود.
- سوالات متداول دوره.
- کاربران.
- پروفایل‌های کاربر.
- مدرسان.
- نقش‌ها.
- مجوزها.
- تخصیص مجوز به نقش.
- تخصیص نقش به کاربر.
- سفارش‌ها.
- پرداخت‌ها.
- کوپن‌ها.
- پست‌های بلاگ.
- سوالات متداول عمومی.
- تنظیمات سایت.

#### 13.5.2 مدیریت کوپن

پنل مدیریت باید مدیریت کوپن را با محافظت مجوزهای `coupon.view`، `coupon.create`، `coupon.edit` و `coupon.delete` فراهم کند.

لیست کوپن‌ها باید کد، نوع، مقدار، میزان استفاده (`UsedCount` /`UsageLimit`)، تاریخ شروع، تاریخ پایان، `IsActive` و یک وضعیت مشتق‌شده (فعال، زمان‌بندی‌شده، منقضی‌شده، تمام‌شده یا غیرفعال) را نمایش دهد. باید جستجو بر اساس کد و فیلتر بر اساس وضعیت را پشتیبانی کند.

فیلدهای فرم کوپن:

| فیلد           | الزام                                                                        |
| -------------- | ---------------------------------------------------------------------------- |
| Code           | الزامی؛ Trim می‌شود؛ یکتا، با مقایسه بدون حساسیت به حروف                     |
| Type           | الزامی؛ Percentage یا FixedAmount                                            |
| Value          | الزامی؛ Percentage: بزرگ‌تر از 0 و کوچک‌تر از 100؛ FixedAmount: بزرگ‌تر از 0 |
| MinOrderAmount | اختیاری؛ منفی نباشد                                                          |
| UsageLimit     | اختیاری؛ خالی یعنی نامحدود؛ در صورت مقداردهی بزرگ‌تر از 0                    |
| UsedCount      | فقط‌خواندنی                                                                  |
| StartDate      | الزامی                                                                       |
| EndDate        | الزامی؛ بعد از StartDate                                                     |
| IsActive       | الزامی                                                                       |

قواعد مدیریت کوپن:

- `UsedCount` هرگز نباید به‌صورت دستی ویرایش شود.
- `UsageLimit` نباید کمتر از `UsedCount` فعلی تنظیم شود.
- ویرایش، غیرفعال‌سازی یا حذف یک کوپن نباید سفارش‌ها یا فاکتورهای موجود را تغییر دهد (بخش 9.4).
- غیرفعال‌سازی کوپن روش عادی توقف استفاده از آن است. حذف کوپن حذف نرم (Soft Delete) است و کوپنی که توسط هر سفارشی استفاده شده باشد هرگز نباید به‌صورت فیزیکی حذف شود.
- جزئیات سفارش در ماژول سفارش‌ها باید کد کوپن و مبلغ تخفیف کوپن را نمایش دهد.
- فیلدهای حسابرسی باید توسط سرور مقداردهی شوند و هرگز از سمت کلاینت ارائه نشوند.

### 13.6 نیازمندی‌های CRUD

در جایی که یک موجودیت به‌عنوان قابل‌مدیریت اداری تعریف شده، پنل مدیریت باید عملیات مناسب زیر را فراهم کند:

- ایجاد (Create).
- خواندن/لیست (Read/List).
- به‌روزرسانی (Update).
- حذف (Delete).

عملیات CRUD باید موارد زیر را رعایت کنند:

- اعتبارسنجی.
- مجوزدهی.
- یکپارچگی ارجاعی (Referential Integrity).
- محدودیت‌های موجودیت سیستمی.
- زمان‌مهرهای حسابرسی (Audit Timestamps).

عملیات حذفی که می‌توانند داده‌های تاریخی/مالی مهم را از بین ببرند، باید از یک قاعده کسب‌وکاری مناسب استفاده کنند و نه صرفاً یک حذف فیزیکی کورکورانه.

برای مثال، سفارش‌های پرداخت‌شده و پرداخت‌های موفق نباید از طریق CRUD عادی مدیریت به‌صورت فیزیکی حذف شوند.

### 13.7 مدیریت خطا

وب‌سایت عمومی و پنل مدیریت باید از موارد زیر پشتیبانی کنند:

#### 13.7.1 HTTP 400

برای ورودی نامعتبر کلاینت/برنامه، در جایی که مرتبط است.

#### 13.7.2 HTTP 403

هنگامی نمایش داده می‌شود که یک کاربر احرازهویت‌شده فاقد مجوز موردنیاز باشد.

#### 13.7.3 HTTP 404

هنگامی نمایش داده می‌شود که یک منبع درخواستی وجود نداشته باشد یا به‌صورت عمومی قابل‌دسترسی نباشد.

#### 13.7.4 HTTP 500

برای خطاهای غیرمنتظره سمت سرور نمایش داده می‌شود.

جزئیات استثنای داخلی، Stack Trace، خطاهای پایگاه‌داده و اسرار (Secrets) هرگز نباید به کاربران نهایی نمایش داده شوند.

تمام خطاهای غیرمنتظره باید با اطلاعات همبستگی (Correlation) مناسب لاگ شوند.

## 14. مشاهده‌پذیری (Observability)

### 14.1 مشاهده‌پذیری (Observability)

سیستم باید موارد زیر را فراهم کند:

- لاگ‌ها.
- ردیابی‌های توزیع‌شده.
- متریک‌ها.

پشته هدف به شرح زیر است:

```text
برنامه
    |
    +-- Serilog
    |
    +-- OpenTelemetry
           |
           +-- لاگ‌ها   -> Loki
           +-- ردیابی‌ها -> Tempo
           +-- متریک‌ها  -> Prometheus
                            |
                            v
                         Grafana
```

Grafana باید داشبوردهای یکپارچه برای مشاهده‌پذیری عملیاتی و کسب‌وکاری فراهم کند.

### 14.2 نیازمندی‌های ثبت لاگ

لاگ‌ها باید ساختاریافته باشند.

حداقل، لاگ‌های درخواست مرتبط باید شامل موارد زیر باشند:

- زمان (Timestamp).
- سطح (Level).
- پیام (Message).
- استثنا، در صورت وجود.
- شناسه ردیابی (Trace ID).
- شناسه Span، در صورت موجود بودن.
- شناسه کاربر، در صورت موجود بودن.
- متد HTTP.
- مسیر درخواست.
- کد وضعیت.
- مدت‌زمان.

مقادیر حساس نباید لاگ شوند.

سیستم نباید موارد زیر را لاگ کند:

- رمزهای عبور.
- مقادیر OTP در محیط Production.
- توکن‌های احراز هویت.
- اسرار مربوط به پرداخت.
- اطلاعات کامل حساس شخصی.

سرویس پیامک ساختگی فقط می‌تواند OTPها را در محیط‌های توسعه/تست لاگ کند.

### 14.3 نیازمندی‌های ردیابی توزیع‌شده

OpenTelemetry باید عملیات مرتبط برنامه را Instrument کند.

ردیابی‌ها باید موارد زیر را پوشش دهند:

- درخواست‌های HTTP ورودی.
- عملیات پایگاه‌داده.
- عملیات Redis.
- فراخوانی‌های سرویس خارجی.
- عملیات احراز هویت.
- عملیات پرداخت.

شناسه‌های ردیابی باید با لاگ‌های برنامه همبسته (Correlated) شوند.

### 14.4 نیازمندی‌های متریک

سیستم باید متریک‌های برنامه و کسب‌وکاری را در معرض دید قرار دهد.

#### 14.4.1 متریک‌های پیش‌فرض/سیستمی

حداقل:

- تعداد درخواست.
- مدت‌زمان درخواست.
- درخواست‌های فعال، در جایی که پشتیبانی می‌شود.
- توزیع وضعیت HTTP.
- نرخ خطا.
- متریک‌های فرآیند/Runtime.
- شاخص‌های عملکرد پایگاه‌داده.
- شاخص‌های عملکرد Redis، در جایی که موجود است.

#### 14.4.2 متریک‌های کسب‌وکاری

سیستم باید موارد زیر را در معرض دید قرار دهد:

- بازدید دوره.
- خریدها.
- پرداخت‌های موفق.
- پرداخت‌های ناموفق.
- تعداد ثبت‌نام.
- نرخ تبدیل، در جایی که قابل‌محاسبه است.

#### 14.4.3 متریک‌های عملیات کند

سیستم باید عملیات کند را قابل‌مشاهده کند، از جمله:

- درخواست‌های HTTP کند.
- کوئری‌های پایگاه‌داده کند.
- فراخوانی‌های سرویس خارجی کند.

آستانه‌ها باید پیکربندی‌محور باشند.

### 14.5 داشبوردهای Grafana

پروژه باید حداقل داشبوردهایی برای موارد زیر فراهم کند:

#### 14.5.1 برنامه

- نرخ درخواست.
- زمان پاسخ.
- نرخ خطا.
- HTTP 4xx.
- HTTP 5xx.

#### 14.5.2 کسب‌وکار

- بازدید دوره.
- خریدها.
- پرداخت‌های موفق.
- پرداخت‌های ناموفق.
- نرخ تبدیل.

#### 14.5.3 لاگ‌ها

- لاگ‌های خطا.
- لاگ‌های هشدار.
- لاگ‌های برنامه.

#### 14.5.4 ردیابی‌ها

- درخواست‌های کند.
- درخواست‌های ناموفق.
- جزئیات ردیابی.

Prometheus باید به‌عنوان بک‌اند متریک، Loki به‌عنوان بک‌اند لاگ، و Tempo به‌عنوان بک‌اند ردیابی عمل کنند.

## 15. امنیت و الزامات غیرعملکردی

### 15.1 نیازمندی‌های امنیتی

#### 15.1.1 امنیت رمز عبور

رمزهای عبور باید با استفاده از یک مکانیزم هش کردن مدرن به‌صورت امن هش شوند.

رمزهای عبور به‌صورت متن ساده هرگز نباید ذخیره شوند.

#### 15.1.2 امنیت احراز هویت

توکن‌ها/کوکی‌های احراز هویت باید:

- در برابر دستکاری محافظت شوند.
- در محیط Production از تنظیمات کوکی امن استفاده کنند.
- زمان انقضای مناسب داشته باشند.
- از خروج/باطل‌سازی بر اساس مکانیزم احراز هویت انتخابی پشتیبانی کنند.

#### 15.1.3 مجوزدهی

تمام عملیات محافظت‌شده باید سمت سرور مجاز شوند.

پنهان کردن یک دکمه در رابط کاربری Admin هرگز نباید کافی برای مجوزدهی در نظر گرفته شود.

#### 15.1.4 اعتبارسنجی ورودی

تمام ورودی‌های خارجی باید اعتبارسنجی شوند.

این شامل موارد زیر است:

- ورودی فرم.
- پارامترهای Query.
- پارامترهای Route.
- بارگذاری فایل.
- نتایج پرداخت.
- پاسخ‌های OAuth.

#### 15.1.5 محتوای HTML

محتوای ویرایشگر HTML باید پاک‌سازی (Sanitize) شود.

#### 15.1.6 بارگذاری فایل

پیوست‌ها باید بر اساس موارد زیر اعتبارسنجی شوند:

- پسوند.
- نوع محتوا، در صورت امکان.
- اندازه.
- تعداد.
- قواعد ذخیره‌سازی.

فایل‌های بارگذاری‌شده نباید به‌طور خودکار به محتوای قابل‌اجرا تبدیل شوند.

### 15.2 نیازمندی‌های غیرعملکردی

#### 15.2.1 عملکرد (Performance)

برنامه باید:

- از I/O ناهمگام (Asynchronous) استفاده کند.
- از فراخوانی‌های Blocking خودداری کند.
- برای لیست‌های احتمالاً بزرگ Admin/عمومی از صفحه‌بندی (Pagination) استفاده کند.
- از کوئری‌های N+1 پایگاه‌داده خودداری کند.
- کوئری‌های کند پایگاه‌داده را پایش کند.
- درخواست‌های HTTP کند را پایش کند.

#### 15.2.2 مقیاس‌پذیری (Scalability)

برنامه باید تا حد امکان در لایه وب‌سرور Stateless باقی بماند.

وضعیت Session/سبد خرید نباید به حافظه محلی سرور وابسته باشد.

Redis باید برای وضعیت موقت مشترک استفاده شود.

#### 15.2.3 قابلیت نگهداری (Maintainability)

کدبیس باید:

- مرزهای Clean Architecture را رعایت کند.
- دغدغه‌های Domain، Application، Infrastructure و Presentation را جدا کند.
- از تزریق وابستگی استفاده کند.
- برای قواعد مهم کسب‌وکاری از تست‌های خودکار استفاده کند.
- از تکرار منطق کسب‌وکاری خودداری کند.

#### 15.2.4 قابلیت‌اطمینان (Reliability)

عملیات حیاتی باید در جایی که امکان تکرار درخواست وجود دارد، Idempotent باشند.

پردازش پرداخت به‌طور خاص باید Idempotent باشد.

#### 15.2.5 امنیت

برنامه باید از پیش‌فرض‌های امن برای موارد زیر پیروی کند:

- احراز هویت.
- مجوزدهی.
- ذخیره‌سازی رمز عبور.
- بارگذاری فایل.
- رندر HTML.
- اسرار (Secrets).
- ثبت لاگ.
- اعتبارسنجی ورودی.

## 16. تست، معیارهای پذیرش و تعریف انجام‌شده

### 16.1 نیازمندی‌های تست

پروژه باید شامل موارد زیر باشد:

#### 16.1.1 تست‌های واحد (Unit Tests)

برای:

- قیمت‌گذاری.
- محاسبات تخفیف.
- اعتبارسنجی سلسله‌مراتب دسته‌بندی.
- قواعد دسترسی دوره.
- محاسبات سفارش.
- ارزیابی مجوز.
- انتقال‌های وضعیت پرداخت.

#### 16.1.2 تست‌های یکپارچگی (Integration Tests)

برای:

- پایداری داده در PostgreSQL.
- رفتار Repository.
- تراکنش‌های Unit of Work.
- عملیات سبد خرید Redis.
- جریان‌های احراز هویت.
- پردازش نتیجه پرداخت.

#### 16.1.3 تست‌های سرتاسری (End-to-End Tests)

برای جریان‌های حیاتی:

```text
ثبت‌نام/ورود
       ↓
مرور دوره
       ↓
افزودن به سبد خرید
       ↓
پرداخت (Checkout)
       ↓
پرداخت
       ↓
دسترسی به دوره
       ↓
فاکتور
```

### 16.2 معیارهای پذیرش — جریان‌های اصلی

#### 16.2.1 خرید دوره

موارد زیر باید صادق باشند:

1. یک کاربر می‌تواند دوره‌های منتشرشده را مرور کند.
2. یک دوره پولی می‌تواند به سبد خرید Redis اضافه شود.
3. فرآیند پرداخت نیازمند شماره تلفن است.
4. سرور قیمت سفارش را محاسبه می‌کند.
5. یک سفارش ایجاد می‌شود.
6. یک رکورد پرداخت ایجاد می‌شود.
7. یک پرداخت موفق، سفارش را به `Paid` تغییر می‌دهد.
8. کاربر دسترسی به دوره را دریافت می‌کند.
9. یک فاکتور در دسترس قرار می‌گیرد.
10. پردازش مجدد نتیجه یکسان پرداخت، دسترسی یا وضعیت فاکتور را تکراری نمی‌کند.

#### 16.2.2 نقش‌های پویا

موارد زیر باید صادق باشند:

1. یک مدیر مجاز می‌تواند یک نقش ایجاد کند.
2. مدیر می‌تواند نقش را ویرایش کند.
3. مدیر می‌تواند مجوزها را تخصیص دهد.
4. مدیر می‌تواند نقش را به کاربران تخصیص دهد.
5. کاربر مجوزهای نقش را دریافت می‌کند.
6. مجوزدهی بر پایه کلیدهای مجوز است.
7. مدیر می‌تواند نقش را در صورتی که به‌عنوان نقش سیستمی محافظت‌نشده باشد حذف کند.

#### 16.2.3 ساختار دوره

موارد زیر باید صادق باشند:

1. یک دوره می‌تواند شامل چندین بخش باشد.
2. یک بخش می‌تواند شامل چندین اپیزود باشد.
3. بخش‌ها مرتب‌شده هستند.
4. اپیزودها مرتب‌شده هستند.
5. مدت‌زمان اپیزود در دسترس است.
6. یک دوره پولی می‌تواند شامل چندین اپیزود رایگان باشد.
7. اپیزودهای غیررایگان نیازمند مالکیت دوره هستند.

#### 16.2.4 پرداخت با کوپن

موارد زیر باید صادق باشند:

1. یک کد کوپن می‌تواند روی سبد خریدی که شامل دوره‌های پولی است اعمال شود.
2. سرور تخفیف کوپن و مبلغ قابل پرداخت را محاسبه می‌کند؛ مبالغ ارائه‌شده از سمت کلاینت نادیده گرفته می‌شوند.
3. یک کد ناشناخته، غیرفعال، منقضی، شروع‌نشده، تمام‌شده یا کمتر از حداقل مبلغ با یک پیام رد می‌شود.
4. کاربر می‌تواند کوپن اعمال‌شده را از سبد خرید حذف کند.
5. کوپن هنگام ایجاد سفارش مجدداً اعتبارسنجی می‌شود و یک کوپن نامعتبر مانع ایجاد سفارش می‌شود.
6. سفارش ارجاع کوپن و Snapshot تخفیف کوپن را ذخیره می‌کند و مبلغ پرداخت برابر مبلغ قابل پرداخت است.
7. پرداخت‌های هم‌زمان نمی‌توانند `UsedCount` را از `UsageLimit` بالاتر ببرند.
8. یک سفارش `Failed` یا `Cancelled` استفاده رزروشده کوپن خود را دقیقاً یک‌بار آزاد می‌کند.
9. فاکتور یک سفارش پرداخت‌شده کد کوپن و تخفیف کوپن را نمایش می‌دهد.
10. پردازش مجدد نتیجه یکسان پرداخت، `UsedCount` را تغییر نمی‌دهد.
11. یک سفارش `Pending` که از زمان انقضای خود می‌گذرد لغو می‌شود و استفاده رزروشده کوپن آن آزاد می‌شود.
12. نتیجه پرداخت موفقی که پس از انقضا برسد ثبت و برای بررسی علامت‌گذاری می‌شود و به‌صورت خودکار دسترسی اعطا نمی‌کند.
13. یک مدیر می‌تواند کوپن‌ها را ایجاد، ویرایش، غیرفعال و حذف نرم کند و نمی‌تواند مقدار نامعتبر یا سقف استفاده کمتر از میزان استفاده فعلی تنظیم کند.

### 16.3 تعریف انجام‌شده (Definition of Done)

یک ویژگی زمانی کامل در نظر گرفته می‌شود که:

1. نیازمندی‌های Domain پیاده‌سازی شده باشند.
2. Command/Queryهای Application پیاده‌سازی شده باشند.
3. اعتبارسنجی پیاده‌سازی شده باشد.
4. عملیات خواندن از مرز Repository خواندن استفاده کنند.
5. عملیات نوشتن از مرز Repository نوشتن (و در جایی که لازم است Unit of Work) استفاده کنند.
6. Repositoryهای خواندن از Dapper استفاده کنند.
7. Repositoryهای نوشتن از EF Core استفاده کنند.
8. هیچ Repository عمومی معرفی نشده باشد.
9. فیلدهای الزامی حسابرسی پر شده باشند.
10. Soft Delete در جایی که کاربرد دارد پیاده‌سازی شده باشد.
11. احراز هویت از مکانیزم مبتنی بر Cookie استفاده کند.
12. مجوزدهی بر پایه Permission باشد.
13. محدودیت‌های موردنیاز Persistence وجود داشته باشند.
14. رابط کاربری موردنیاز پیاده‌سازی شده باشد.
15. یکپارچه‌سازی پیامک در جایی که کاربرد دارد از مرز API خارجی پیامک استفاده کند.
16. رندر فاکتور پشت یک انتزاع ایزوله شده باشد.
17. Snapshotهای مالی حفظ شده باشند.
18. مدیریت خطا پیاده‌سازی شده باشد.
19. لاگ‌ها و تله‌متری مرتبط وجود داشته باشند.
20. تست‌های خودکار قواعد کسب‌وکاری مهم را پوشش دهند.
21. هیچ مرز معماری‌ای دور زده نشده باشد.
22. هیچ اطلاعات حساسی از طریق لاگ‌ها، Cookieها یا رابط کاربری فاش نشود.
23. پیاده‌سازی از تمام قواعد کسب‌وکاری الزامی تعریف‌شده در این SRS پیروی کند.

## 17. قواعد، اصول کلیدی و جمع‌بندی

### 17.1 خلاصه قواعد کسب‌وکاری صریح

قواعد زیر الزامی هستند و بر نیازمندی‌های قبلی متعارض اولویت دارند:

#### 17.1.1 دامنه و داده

1. سلسله‌مراتب دسته‌بندی نمی‌تواند از سه سطح فراتر رود.
2. اسلاگ‌های دوره یکتا هستند.
3. اسلاگ‌های بلاگ یکتا هستند.
4. شماره‌های تلفن در صورت وجود یکتا هستند.
5. ایمیل‌ها در صورت وجود یکتا هستند.
6. پیوست‌های دوره دارای محدودیت تعداد و اندازه هستند.
7. محدودیت‌های پیوست پیکربندی‌محور هستند.

#### 17.1.2 حذف و حسابرسی

1. Soft Delete راهبرد پیش‌فرض حذف است.
2. Hard Delete فقط برای استثناهای صراحتاً مستندشده مجاز است.
3. موجودیت‌های Soft-Deletable باید در جایی که کاربرد دارد شامل `IsDeleted`، `DeletedAt` و `DeletedBy` باشند.
4. موجودیت‌های کسب‌وکاری باید در جایی که کاربرد دارد شامل `CreatedAt`، `CreatedBy`، `UpdatedAt` و `UpdatedBy` باشند.
5. کوئری‌های عادی باید رکوردهای Soft-Delete‌شده را حذف کنند.
6. رکوردهای مالی نباید از طریق مدیریت عادی به‌صورت فیزیکی حذف شوند.

#### 17.1.3 احراز هویت و مجوزدهی

1. رمزهای عبور هرگز به‌صورت متن ساده ذخیره نمی‌شوند.
2. نقش‌ها پویا هستند.
3. مجوزها پویا هستند.
4. نقش‌ها مجوز دریافت می‌کنند.
5. مجوزدهی از مجوزها استفاده می‌کند، نه نام‌های نقش Hard-code شده.
6. نقش‌ها/مجوزهای سیستمی در برابر تغییرات مخرب محافظت می‌شوند.
7. احراز هویت مرورگر باید مبتنی بر Cookie باشد.
8. JWT نباید مکانیزم اصلی احراز هویت مرورگر باشد.
9. احراز هویت گوگل باید یک Session محلی احرازهویت‌شده مبتنی بر Cookie برقرار کند.
10. کاربران احرازهویت‌شده از طریق گوگل باید پیش از پرداخت شماره تلفن ارائه دهند.
11. عملیات مدیریتی باید توسط مجوز محافظت شوند.

#### 17.1.4 قیمت‌گذاری و دسترسی به محتوا

1. وضعیت رایگان بودن دوره/محصول باید از یک `Price` قابل‌Null مشتق شود.
2. `IsFree` نباید در پایگاه‌داده ذخیره شود.
3. اپیزودهای رایگان دوره‌های پولی بدون خرید کل دوره قابل‌مشاهده هستند.
4. اپیزودهای غیررایگان پولی نیازمند مالکیت دوره هستند.
5. محتوای عمومی باید وضعیت نمایش خود را رعایت کند.

#### 17.1.5 سبد خرید، سفارش، پرداخت و فاکتور

1. سبدهای خرید در Redis ذخیره می‌شوند.
2. قیمت‌های سفارش تصویر لحظه‌ای (Snapshot) می‌شوند.
3. پردازش پرداخت Idempotent است.
4. پرداخت موفق دسترسی به دوره را اعطا می‌کند.
5. یکپارچه‌سازی واقعی ارائه‌دهنده پرداخت الزامی نیست.
6. داده فاکتور باید تصاویر لحظه‌ای مالی تاریخی را حفظ کند.
7. فاکتورهای نهایی‌شده نباید از طریق عملیات معمول CRUD تغییر کنند.
8. رندر فاکتور باید پشت یک انتزاع ایزوله شود.
9. لایه Domain نباید به کتابخانه‌های گزارش‌گیری/PDF ارجاع دهد.
10. Stimulsoft Reports.WEB کاندید فعلی ترجیح‌داده‌شده فاکتور/گزارش‌گیری است.
11. QuestPDF و FastReport .NET باید به‌عنوان جایگزین‌های مستندشده باقی بمانند.

#### 17.1.6 پیامک

1. یکپارچه‌سازی واقعی سرویس پیامک الزامی نیست.
2. ارائه‌دهنده ساختگی پیامک باید یک پروژه API جداگانه باشد.
3. API پیامک باید از یک فروشگاه داده In-Memory استفاده کند (به‌جز قالب‌های پیامک که پایدار ذخیره می‌شوند).
4. API پیامک باید یک HTTP API شبیه ارائه‌دهنده واقعی افشا کند.
5. API پیامک باید یک داشبورد HTML برای بازرسی درخواست‌های پیامک فراهم کند.
6. سرویس ساختگی پیامک باید با یک پیاده‌سازی ارائه‌دهنده واقعی قابل جایگزینی باشد.

#### 17.1.7 معماری و Persistence

1. انتزاع‌های Repository (جداشده برای خواندن و نوشتن) و Unit of Work باید برای دسترسی به Persistence استفاده شوند.
2. Repositoryهای خواندن و نوشتن باید جدا شوند.
3. Repositoryهای خواندن باید از Dapper استفاده کنند.
4. Repositoryهای نوشتن باید از Entity Framework Core استفاده کنند.
5. یک Repository عمومی نباید پیاده‌سازی شود.
6. `DbContext` باید درون Infrastructure باقی بماند.
7. Controllerها، Razor Pageها و Handlerهای Application نباید مستقیماً به `DbContext` دسترسی داشته باشند.
8. منطق کسب‌وکاری متعلق به لایه‌های Application/Domain است.

#### 17.1.8 خطا و مشاهده‌پذیری

1. خطاهای غیرمنتظره سرور باید لاگ شوند و نباید جزئیات حساس را فاش کنند؛ تمام اطلاعات حساس باید از لاگ‌ها و Cookieهای احراز هویت مستثنی بمانند.
2. لاگ‌ها، ردیابی‌ها و متریک‌ها باید از طریق زیرساخت مشاهده‌پذیری در دسترس باشند.
3. Grafana باید داشبوردهای مشاهده‌پذیری یکپارچه فراهم کند.

### 17.2 اصول پیاده‌سازی

پیاده‌سازی باید از این اصول پیروی کند:

#### 17.2.1 معماری و کد

- قواعد کسب‌وکاری را بین MVC، Razor Pages و سرویس‌های Application تکرار نکنید.
- `DbContext` را خارج از Infrastructure افشا نکنید.
- از Unit of Work برای مرزهای پایدار و سازگار Persistence استفاده کنید.
- قواعد صریح Domain/Application را به رفتار ضمنی ترجیح دهید.
- مسیرهای Persistence خواندن و نوشتن را از هم جدا کنید.
- از Dapper برای Repositoryهای خواندن‌محور استفاده کنید.
- از EF Core برای Repositoryهای نوشتن‌محور استفاده کنید.
- یک Repository عمومی معرفی نکنید.
- یکپارچه‌سازی‌های خارجی را پشت انتزاع نگه دارید.
- جزئیات پیاده‌سازی اختصاصی ارائه‌دهنده را پشت انتزاع نگه دارید.

#### 17.2.2 امنیت و احراز هویت

- از ASP.NET Core Identity استفاده نکنید.
- نقش‌ها را به‌عنوان مکانیزم مجوزدهی Hard-code نکنید.
- مجوزها را در منطق ارائه (Presentation) Hard-code نکنید.
- رمزهای عبور را به‌صورت متن ساده ذخیره نکنید.
- استثناهای داخلی را به کاربران فاش نکنید.
- HTML پاک‌سازی‌نشده را نمایش ندهید.
- از احراز هویت امن مبتنی بر Cookie برای مرورگر استفاده کنید.
- پیکربندی و اسرار را خارج از کد منبع نگه دارید.
- اجازه ندهید فیلدهای حسابرسی توسط کلاینت ارائه شوند.

#### 17.2.3 داده و حذف

- سبدهای خرید را به‌عنوان وضعیت اصلی سبد در PostgreSQL ذخیره نکنید.
- عمق دسته‌بندی فراتر از سه سطح را مجاز نکنید.
- Soft Delete را بر حذف فیزیکی ترجیح دهید.
- اطلاعات حسابرسی را برای تغییرات مدیریتی حفظ کنید.
- یک فیلد افزونه `IsFree` را ذخیره نکنید.
- وضعیت رایگان بودن را از `Price` قابل‌Null مشتق کنید.
- Snapshotهای مالی غیرقابل‌تغییر را در فاکتورها حفظ کنید.
- رکوردهای مالی تاریخی را به‌صورت فیزیکی حذف نکنید.

#### 17.2.4 پرداخت، پیامک و فاکتور

- به قیمت‌های سمت کلاینت اعتماد نکنید.
- پردازش نتیجه پرداخت را Idempotent کنید.
- شبیه‌ساز پیامک را خارج از پردازه اصلی برنامه نگه دارید.
- شبیه‌ساز پیامک را به‌عنوان یک وابستگی خارجی HTTP در نظر بگیرید.
- وضعیت شبیه‌ساز پیامک را در حافظه ذخیره کنید.
- یک داشبورد ساده HTML برای بازرسی پیامک فراهم کنید.
- رندر فاکتور را مستقل از لایه Domain نگه دارید.
- وابستگی‌های کتابخانه گزارش‌گیری را در جایی که امکان دارد خارج از مدل‌های کسب‌وکاری Domain و Application نگه دارید.

### 17.3 نتیجه‌گیری

این SRS دامنه پیاده‌سازی اول پلتفرم دوره‌های آنلاین را تعریف می‌کند.

این سیستم عمداً حول موارد زیر طراحی شده است:

```text
Clean Architecture
        +
CQRS / MediatR
        +
Repository / Unit of Work
        +
Result Pattern
        +
PostgreSQL
        +
Redis
        +
مجوزدهی سفارشی بر پایه Permission
        +
Serilog / OpenTelemetry
        +
Loki / Tempo / Prometheus
        +
Grafana
```

سیستم باید بدون معرفی ویژگی‌های غیرضروری خارج از دامنه تعریف‌شده، قابل‌توسعه باقی بماند. نقش‌ها و مجوزهای پویا یک نیازمندی محوری هستند، در حالی که ارائه‌دهندگان پرداخت و پیامک عمداً انتزاع شده‌اند تا یکپارچه‌سازی‌های واقعی بعداً بدون تغییر مدل اصلی کسب‌وکار قابل‌افزودن باشند.
