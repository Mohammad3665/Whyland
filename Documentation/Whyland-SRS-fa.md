# مشخصات نیازمندی‌های نرم‌افزار (SRS)

## وایلند — پلتفرم آموزشی

**نام پروژه:** Whyland (وایلند)

**نوع پروژه:** آموزشی / پلتفرم دوره‌های آنلاین

**هدف پروژه:** پروژه تمرینی و نمونه‌کار (پورتفولیو)

**نسخه سند:** 1.0

**وضعیت:** پیش‌نویس آماده برای پیاده‌سازی

**زبان اصلی سند:** انگلیسی

---

## 1. هدف

این سند نیازمندی‌های عملکردی و غیرعملکردی یک پلتفرم آموزش آنلاین را تعریف می‌کند که به کاربران امکان می‌دهد دوره‌های آنلاین را کشف کنند، خریداری کنند و به آن‌ها دسترسی داشته باشند.

این پلتفرم شامل موارد زیر است:

1. یک وب‌سایت عمومی پیاده‌سازی‌شده با ASP.NET Core MVC.
2. یک پنل مدیریت پیاده‌سازی‌شده با ASP.NET Core Razor Pages.
3. یک سیستم احراز هویت و مجوزدهی سفارشی بدون استفاده از ASP.NET Core Identity.
4. یک پایگاه‌داده رابطه‌ای PostgreSQL.
5. Redis برای ذخیره‌سازی سبد خرید و کش.
6. یک زیرساخت مشاهده‌پذیری (Observability) مبتنی بر Serilog، OpenTelemetry، Grafana Loki، Grafana Tempo و Prometheus.

هدف از این SRS ارائه نیازمندی‌هایی با دقت کافی است تا پلتفرم وایلند بدون تکیه بر فرضیات کسب‌وکاری مستندنشده قابل پیاده‌سازی باشد. وایلند به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود تا معماری نرم‌افزاری تولید-محور، توسعه بک‌اند، توسعه وب، مجوزدهی، پایداری داده‌ها (Persistence)، پرداخت و مشاهده‌پذیری را نشان دهد.

## 2. بستر پروژه

وایلند یک پلتفرم آموزشی است که به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود. اگرچه هدف اصلی این پروژه یادگیری و نمایش مهارت‌های مهندسی است، اما معماری و نیازمندی‌های آن باید تا جای ممکن از رویه‌های تولید-محور پیروی کند.

پیاده‌سازی باید جداسازی روشن دغدغه‌ها (Separation of Concerns)، کد قابل نگهداری، قواعد کسب‌وکاری واقع‌گرایانه، احراز هویت و مجوزدهی امن، پردازش قابل‌اعتماد سفارش/پرداخت، و مشاهده‌پذیری کامل برنامه را نشان دهد.

## 3. دامنه پروژه

### 3.1 در دامنه پروژه

سیستم باید موارد زیر را فراهم کند:

- دسته‌بندی‌های سلسله‌مراتبی دوره با حداکثر عمق سه سطح.
- ایجاد و مدیریت دوره.
- بخش‌ها (Sections) و اپیزودهای دوره.
- اپیزودهای پیش‌نمایش رایگان برای دوره‌های پولی.
- پیوست‌های اپیزود با محدودیت‌های قابل‌پیکربندی.
- سوالات متداول اختصاصی هر دوره.
- بلاگ عمومی.
- سوالات متداول عمومی.
- کاربران پویا.
- نقش‌های پویا.
- مجوزهای پویا.
- تخصیص مجوز بر پایه نقش.
- احراز هویت با شماره تلفن.
- یک سرویس پیامک ساختگی (Fake) برای توسعه/تست.
- احراز هویت با گوگل.
- الزام دریافت شماره تلفن قبل از خرید.
- مدیریت پروفایل کاربر.
- پروفایل مدرسان.
- علاقه‌مندی‌های دوره (Favorites).
- دسترسی به دوره‌های خریداری‌شده.
- سبدهای خرید مبتنی بر Redis.
- سفارش‌ها و اقلام سفارش.
- روش‌های پرداخت که با یک enum نمایش داده می‌شوند.
- رکوردهای پرداخت.
- فاکتورها.
- تنظیمات پویای سایت.
- صفحات عمومی MVC.
- پنل مدیریت Razor Pages.
- مجوزدهی بر پایه Permission.
- ثبت لاگ ساختاریافته.
- ردیابی توزیع‌شده (Distributed Tracing).
- متریک‌ها.
- داشبوردهای Grafana.
- مدیریت خطاهای 403، 404 و 500.

### 3.2 خارج از دامنه پروژه

موارد زیر صراحتاً خارج از دامنه پیاده‌سازی اول هستند:

- یکپارچه‌سازی با سرویس واقعی پیامک.
- یکپارچه‌سازی واقعی با پرداخت گوگل.
- یکپارچه‌سازی واقعی با درگاه بانکی.
- یکپارچه‌سازی واقعی با زرین‌پال.
- یکپارچه‌سازی واقعی با اسنپ‌پی.
- پردازش تسویه‌حساب/پرداخت به مدرسان.
- یادداشت‌های شخصی کاربر روی اپیزودها.
- اپلیکیشن موبایل بومی (Native).
- یک فرانت‌اند SPA جداگانه.
- ASP.NET Core Identity.

ارائه‌دهندگان پرداخت فقط باید از طریق انتزاع/enum روش پرداخت و یک مرز (Boundary) مناسب در سطح برنامه نمایش داده شوند. پیاده‌سازی واقعی ارائه‌دهندگان در این نسخه الزامی نیست.

## 5. معماری سطح‌بالا

برنامه باید از معماری Clean Architecture پیروی کند.

```text
+--------------------------+
| اپلیکیشن عمومی MVC        |
+------------+-------------+
             |
+------------v-------------+
| لایه Application          |
| CQRS / MediatR            |
| قواعد کسب‌وکاری            |
| Result Pattern             |
+------------+-------------+
             |
+------------v-------------+
| لایه Domain               |
| Entities / Value Objects  |
| قواعد Domain               |
+------------+-------------+
             |
+------------v-------------+
| لایه Infrastructure       |
| EF Core / PostgreSQL      |
| Redis                     |
| احراز هویت                |
| پیامک / سرویس‌های خارجی    |
| مشاهده‌پذیری               |
+--------------------------+

+--------------------------+
| Admin Razor Pages         |
+------------+-------------+
             |
             v
      لایه Application
```

لایه‌های ارائه (Presentation) نباید مستقیماً قواعد کسب‌وکاری را پیاده‌سازی کنند یا به دغدغه‌های Infrastructure که متعلق به لایه‌های Application/Infrastructure هستند دسترسی مستقیم داشته باشند.

## 7. نیازمندی‌های Repository و Unit of Work

### 7.1 الگوی Repository

دسترسی به پایداری داده‌ها (Persistence) باید از طریق Repository انتزاع شود.

Repositoryها باید حول Aggregate Rootها و عملیات معنادار Domain تعریف شوند، نه با ایجاد یک Repository غیرضروری برای هر جدول پایگاه‌داده.

نمونه‌ها:

```text
ICourseRepository
ICategoryRepository
IUserRepository
IRoleRepository
IPermissionRepository
IOrderRepository
IPaymentRepository
IBlogPostRepository
```

Repositoryها باید:

- کوئری‌های اختصاصی پایداری داده را کپسوله کنند.
- مدل‌های Domain/Application متناسب با لایه را بازگردانند.
- از افشای `DbContext` به Handlerهای Application خودداری کنند.
- از نشت جزئیات پیاده‌سازی اختصاصی EF Core به Domain خودداری کنند.
- از عملیات ناهمگام (Asynchronous) پشتیبانی کنند.
- از Cancellation Token پشتیبانی کنند.

### 7.2 Unit of Work

لایه Persistence باید یک انتزاع Unit of Work پیاده‌سازی کند.

نمونه:

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken cancellationToken);
}
```

`DbContext` مربوط به EF Core باید رفتار Unit of Work را پیاده‌سازی کند.

یک دستور (Command) واحد در برنامه که چندین موجودیت مرتبط را تغییر می‌دهد باید از یک مرز تراکنشی واحد Unit of Work در جایی که سازگاری (Consistency) لازم است استفاده کند.

نمونه:

```text
ایجاد سفارش
    |
    +-- ایجاد سفارش
    +-- ایجاد اقلام سفارش
    +-- خالی‌کردن/مصرف سبد خرید
    +-- ذخیره تغییرات
```

این عملیات نباید منجر به یک سفارش به‌صورت ناقص ذخیره‌شده شوند.

### 7.3 قواعد تراکنش

در جایی که چندین تغییر پایگاه‌داده باید با هم موفق یا ناموفق شوند، باید از یک تراکنش پایگاه‌داده استفاده شود.

فراخوانی‌های سرویس خارجی نباید به‌اشتباه درون تراکنش‌های پایگاه‌داده طولانی‌مدت قرار گیرند.

Callbackهای پرداخت باید Idempotent (بی‌اثر در تکرار) باشند.

### 7.4 محدودیت‌های Repository

موارد زیر باید کنار گذاشته شوند:

- Repository عمومی صرفاً برای انتزاع CRUD.
- افشای `IQueryable` از Repositoryها در جایی که موجب نشت دغدغه‌های Persistence می‌شود.
- دسترسی مستقیم به `DbContext` از Controllerها، Razor Pageها یا Handlerهای MediatR.
- پیاده‌سازی قواعد کسب‌وکاری درون پیکربندی‌های EF Core.

## 9. مدیریت دسته‌بندی

### 9.1 فیلدها

یک دسته‌بندی باید شامل موارد زیر باشد:

| فیلد | الزام |
|---|---|
| Id | شناسه یکتا |
| Name | الزامی |
| LatinName | الزامی |
| DisplayOrder | عدد صحیح الزامی |
| ParentId | قابل‌تهی (Nullable) |
| IsActive | بولین الزامی |
| CreatedAt | الزامی |
| UpdatedAt | الزامی |

### 9.2 سلسله‌مراتب

دسته‌بندی‌ها باید حداکثر سه سطح را پشتیبانی کنند.

نمونه:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
```

مورد زیر نامعتبر است:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
            └── جنگو پیشرفته
```

برنامه باید ایجاد یا ویرایشی که منجر به تولید سطح چهارم می‌شود را رد کند.

### 9.3 قواعد

- یک دسته‌بندی باید هویت یکتا داشته باشد.
- یک دسته‌بندی می‌تواند صفر یا یک والد داشته باشد.
- یک دسته‌بندی ریشه دارای `ParentId = null` است.
- یک دسته‌بندی نمی‌تواند والد خودش باشد.
- روابط والد چرخه‌ای (Circular) ممنوع هستند.
- دسته‌بندی‌های غیرفعال نباید برای دسته‌بندی دوره‌های جدید قابل‌انتخاب باشند.
- روابط موجود نباید هنگام غیرفعال شدن یک دسته‌بندی به‌صورت بی‌سروصدا حذف شوند.
- حذف یک دسته‌بندی که توسط یک دوره ارجاع داده شده باید یا جلوگیری یا به‌صراحت مدیریت شود؛ پیاده‌سازی نباید روابط دوره-دسته‌بندی را به‌صورت یتیم و بی‌سروصدا رها کند.

## 10. مدیریت دوره

### 10.1 فیلدهای دوره

| فیلد | الزام |
|---|---|
| Id | شناسه یکتا |
| Name | الزامی |
| LatinName | الزامی |
| ShortDescription | الزامی |
| Description | اختیاری/الزامی بر اساس قواعد اعتبارسنجی؛ از محتوای ویرایشگر HTML پشتیبانی می‌کند |
| Slug | الزامی و یکتا |
| MainImage | اختیاری |
| IsFree | الزامی |
| Price | برای دوره‌های پولی الزامی |
| DiscountType | None / Percentage / FixedAmount |
| DiscountValue | زمانی که تخفیف فعال است الزامی |
| IsSaleActive | الزامی |
| DisplayStatus | Draft / Published / Hidden |
| IsFeatured | الزامی |
| IsAmazing | الزامی |
| IntroductionVideo | اختیاری |
| CreatedAt | الزامی |
| UpdatedAt | الزامی |

### 10.2 توضیحات

توضیحات کامل باید از محتوای ویرایشگر HTML پشتیبانی کند.

سیستم باید HTML را بر اساس یک allowlist صریح، پیش از نمایش عمومی پاک‌سازی (Sanitize) کند.

HTML خام و کنترل‌نشده توسط کاربر نباید مستقیماً رندر شود.

### 10.3 Slug

اسلاگ دوره باید:

- یکتا باشد.
- امن برای URL باشد.
- مگر با تغییر صریح، پایدار بماند.
- برای URLهای عمومی دوره استفاده شود.

### 10.4 قیمت‌گذاری

قیمت دوره‌ها باید از یک نوع پولی سازگار با اعشار (Decimal) استفاده کند.

`float` و `double` نباید برای مقادیر پولی استفاده شوند.

برای یک دوره رایگان:

```text
IsFree = true
```

سیستم نباید برای دسترسی به دوره نیازمند پرداخت باشد.

برای یک دوره پولی:

```text
IsFree = false
Price > 0
```

### 10.5 تخفیف

انواع تخفیف پشتیبانی‌شده:

```text
None
Percentage
FixedAmount
```

تخفیف‌های درصدی باید در بازه زیر باشند:

```text
0 <= DiscountValue <= 100
```

تخفیف‌های ثابت نباید قیمت نهایی را منفی کنند.

قیمت نهایی قابل‌پرداخت باید به‌صورت متمرکز در لایه Application/Domain محاسبه شود.

### 10.6 وضعیت فروش

`IsSaleActive` کنترل می‌کند که آیا دوره در حال حاضر قابل‌خرید است یا خیر.

یک دوره می‌تواند منتشرشده باشد اما در حال حاضر قابل‌خرید نباشد.

سیستم نباید وضعیت فروش را از وضعیت نمایش استنتاج کند.

### 10.7 وضعیت نمایش

مقادیر پشتیبانی‌شده:

```text
Draft (پیش‌نویس)
Published (منتشرشده)
Hidden (پنهان)
```

فقط دوره‌های منتشرشده باید به‌عنوان لیست عادی دوره‌ها به‌صورت عمومی قابل‌کشف باشند.

دوره‌های پیش‌نویس و پنهان نباید به‌صورت عمومی در معرض دید قرار گیرند.

### 10.8 ویژه و شگفت‌انگیز

دوره‌ها می‌توانند به این شکل علامت‌گذاری شوند:

- ویژه (Featured).
- شگفت‌انگیز (Amazing).

این پرچم‌ها متناظر با بخش‌های نمایشی خاصی هستند که قبلاً درخواست شده‌اند.

سیستم نباید برای انتشار یک دوره، تنظیم این پرچم‌ها را الزامی کند.

## 20. احراز هویت

این پلتفرم نباید از ASP.NET Core Identity استفاده کند.

احراز هویت باید با استفاده از مدل اختصاصی کاربر، اعتبارنامه، نقش و مجوز خود برنامه پیاده‌سازی شود.

### 20.1 احراز هویت با شماره تلفن

سیستم باید از احراز هویت مبتنی بر شماره تلفن پشتیبانی کند.

جریان پایه:

```text
وارد کردن شماره تلفن
        |
        v
درخواست کد یک‌بارمصرف (OTP)
        |
        v
سرویس پیامک ساختگی
        |
        v
وارد کردن کد یک‌بارمصرف
        |
        v
اعتبارسنجی کد یک‌بارمصرف
        |
        v
احراز هویت کاربر
```

کد یک‌بارمصرف (OTP) باید:

- زمان انقضای قابل‌پیکربندی داشته باشد.
- حداکثر تعداد تلاش اعتبارسنجی قابل‌پیکربندی داشته باشد.
- پس از اعتبارسنجی موفق، باطل شود.
- در صورت ذخیره‌سازی، به‌صورت متن ساده ذخیره نشود.
- نرخ‌محدود (Rate Limited) باشد.

### 20.2 سرویس پیامک ساختگی

یک اینترفیس ساده باید تعریف شود:

```csharp
public interface ISmsService
{
    Task SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

پیاده‌سازی محیط توسعه نباید پیامک واقعی ارسال کند.

این پیاده‌سازی می‌تواند:

- کد OTP را لاگ کند.
- آن را به‌صورت موقت برای اهداف تست ذخیره کند.
- یک نتیجه تحویل موفق بازگرداند.

سرویس ساختگی باید بدون تغییر منطق کسب‌وکاری Application قابل‌جایگزینی باشد.

## 21. احراز هویت با گوگل

احراز هویت Google OAuth/OpenID Connect باید پشتیبانی شود.

یک کاربر احرازهویت‌شده با گوگل باید بتواند یک حساب User محلی ایجاد کند یا به آن دسترسی داشته باشد.

حساب محلی باید از طریق یک رکورد ورود خارجی (External Login) مناسب به هویت خارجی گوگل متصل شود.

احراز هویت گوگل نباید جایگزین موجودیت User محلی شود.

## 23. نقش‌ها

نقش‌ها باید کاملاً پویا باشند.

پنل مدیریت باید عملیات CRUD برای نقش‌ها را فراهم کند.

### 23.1 فیلدهای نقش

| فیلد | الزام |
|---|---|
| Id | شناسه یکتا |
| Name | الزامی و یکتا |
| Title | الزامی |

### 23.2 CRUD نقش پویا

مدیرانی که مجوز مناسب را دارند باید بتوانند:

- نقش ایجاد کنند.
- نقش‌ها را مشاهده کنند.
- نقش‌ها را ویرایش کنند.
- نقش‌ها را حذف کنند.
- مجوزها را به نقش‌ها تخصیص دهند.
- نقش‌ها را به کاربران تخصیص دهند.

سیستم نباید نقش‌های کسب‌وکاری مانند `Admin`، `Teacher` یا `User` را به‌عنوان تنها نقش‌های موجود Hard-code کند.

نقش‌های سیستمی می‌توانند توسط برنامه Seed شوند اما همچنان باید توسط همان موجودیت Role نمایش داده شوند.

### 23.3 نقش‌های سیستمی

`IsSystem = true` به این معناست که نقش مورد نیاز برنامه است یا توسط قواعد برنامه محافظت می‌شود.

برنامه باید از حذف تصادفی یا تغییر مخرب نقش‌های سیستمی جلوگیری کند.

## 27. مجوزدهی بر پایه Permission

سیستم باید عملیات مدیریتی را با استفاده از کلیدهای مجوز (Permission Key) مجاز کند، نه با بررسی نام نقش‌ها.

نادرست:

```text
if user.Role == "Admin"
```

مفهوم درست:

```text
if user.HasPermission("course.create")
```

این الزام به این دلیل است که نقش‌ها پویا هستند.

نیازمندی‌های مجوزدهی باید سمت سرور اعمال شوند و نباید صرفاً به نمایان بودن/نبودن عناصر رابط کاربری تکیه کنند.

## 30. سبد خرید

سبد خرید باید در Redis ذخیره شود.

نباید به‌عنوان منبع اصلی سبد خرید در PostgreSQL پایدار (Persist) شود.

### 30.1 قلم سبد خرید

هر قلم سبد خرید باید شامل موارد زیر باشد:

```text
CourseId
Quantity
```

یک دوره نباید بیش از یک‌بار در یک سبد خرید ظاهر شود.

از آنجا که محصول یک حق دسترسی (Entitlement) به دوره است، قاعده کسب‌وکاری معمولاً باید تعداد را به یک عدد در هر دوره محدود کند.

اگر API مقداری بزرگ‌تر از مقدار مجاز دریافت کند، باید آن را بر اساس یک قاعده مستندشده واحد رد یا نرمال (Normalize) کند. پیاده‌سازی باید از یک رفتار یکسان و پایدار استفاده کند.

### 30.2 کلید سبد خرید

کلید Redis باید با کاربر احرازهویت‌شده مرتبط باشد.

نمونه:

```text
cart:{userId}
```

پایداری سبد خرید کاربران احرازهویت‌نشده در این نسخه الزامی نیست، مگر آنکه صراحتاً بعداً اضافه شود.

## 35. Idempotency پرداخت

پردازش نتیجه پرداخت باید Idempotent باشد.

اگر نتیجه پرداخت یکسان چندین بار دریافت شود، سیستم نباید:

- پرداخت‌های تکراری ایجاد کند.
- ثبت‌نام‌های (Enrollment) تکراری ایجاد کند.
- فاکتورهای تکراری ایجاد کند.
- در وضعیت برنامه، از کاربر چندین‌بار هزینه دریافت کند.

در جایی که قابل‌اعمال است باید از یک شناسه پایدار پرداخت/ارائه‌دهنده استفاده شود.

## 45. نیازمندی‌های CRUD

در جایی که یک موجودیت به‌عنوان قابل‌مدیریت اداری تعریف شده، پنل مدیریت باید عملیات مناسب زیر را فراهم کند:

- ایجاد (Create).
- خواندن/لیست (Read/List).
- به‌روزرسانی (Update).
- حذف (Delete).

عملیات CRUD باید موارد زیر را رعایت کنند:

- اعتبارسنجی.
- مجوزدهی.
- یکپارچگی ارجاعی (Referential Integrity).
- محدودیت‌های موجودیت سیستمی.
- زمان‌مهرهای حسابرسی (Audit Timestamps).

عملیات حذفی که می‌توانند داده‌های تاریخی/مالی مهم را از بین ببرند، باید از یک قاعده کسب‌وکاری مناسب استفاده کنند و نه صرفاً یک حذف فیزیکی کورکورانه.

برای مثال، سفارش‌های پرداخت‌شده و پرداخت‌های موفق نباید از طریق CRUD عادی مدیریت به‌صورت فیزیکی حذف شوند.

## 46. مدیریت خطا

وب‌سایت عمومی و پنل مدیریت باید از موارد زیر پشتیبانی کنند:

### 46.1 HTTP 400

برای ورودی نامعتبر کلاینت/برنامه، در جایی که مرتبط است.

### 46.2 HTTP 403

هنگامی نمایش داده می‌شود که یک کاربر احرازهویت‌شده فاقد مجوز موردنیاز باشد.

### 46.3 HTTP 404

هنگامی نمایش داده می‌شود که یک منبع درخواستی وجود نداشته باشد یا به‌صورت عمومی قابل‌دسترسی نباشد.

### 46.4 HTTP 500

برای خطاهای غیرمنتظره سمت سرور نمایش داده می‌شود.

جزئیات استثنای داخلی، Stack Trace، خطاهای پایگاه‌داده و اسرار (Secrets) هرگز نباید به کاربران نهایی نمایش داده شوند.

تمام خطاهای غیرمنتظره باید با اطلاعات همبستگی (Correlation) مناسب لاگ شوند.

## 48. نیازمندی‌های ثبت لاگ

لاگ‌ها باید ساختاریافته باشند.

حداقل، لاگ‌های درخواست مرتبط باید شامل موارد زیر باشند:

- زمان (Timestamp).
- سطح (Level).
- پیام (Message).
- استثنا، در صورت وجود.
- شناسه ردیابی (Trace ID).
- شناسه Span، در صورت موجود بودن.
- شناسه کاربر، در صورت موجود بودن.
- متد HTTP.
- مسیر درخواست.
- کد وضعیت.
- مدت‌زمان.

مقادیر حساس نباید لاگ شوند.

سیستم نباید موارد زیر را لاگ کند:

- رمزهای عبور.
- مقادیر OTP در محیط Production.
- توکن‌های احراز هویت.
- اسرار مربوط به پرداخت.
- اطلاعات کامل حساس شخصی.

سرویس پیامک ساختگی فقط می‌تواند OTPها را در محیط‌های توسعه/تست لاگ کند.

- درخواست‌های کند.
- درخواست‌های ناموفق.
- جزئیات ردیابی.

Prometheus باید به‌عنوان بک‌اند متریک، Loki به‌عنوان بک‌اند لاگ، و Tempo به‌عنوان بک‌اند ردیابی عمل کنند.

## 52. نیازمندی‌های امنیتی

### 52.1 امنیت رمز عبور

رمزهای عبور باید با استفاده از یک مکانیزم هش کردن مدرن به‌صورت امن هش شوند.

رمزهای عبور به‌صورت متن ساده هرگز نباید ذخیره شوند.

### 52.2 امنیت احراز هویت

توکن‌ها/کوکی‌های احراز هویت باید:

- در برابر دستکاری محافظت شوند.
- در محیط Production از تنظیمات کوکی امن استفاده کنند.
- زمان انقضای مناسب داشته باشند.
- از خروج/باطل‌سازی بر اساس مکانیزم احراز هویت انتخابی پشتیبانی کنند.

### 52.3 مجوزدهی

تمام عملیات محافظت‌شده باید سمت سرور مجاز شوند.

پنهان کردن یک دکمه در رابط کاربری Admin هرگز نباید کافی برای مجوزدهی در نظر گرفته شود.

### 52.4 اعتبارسنجی ورودی

تمام ورودی‌های خارجی باید اعتبارسنجی شوند.

این شامل موارد زیر است:

- ورودی فرم.
- پارامترهای Query.
- پارامترهای Route.
- بارگذاری فایل.
- نتایج پرداخت.
- پاسخ‌های OAuth.

### 52.5 محتوای HTML

محتوای ویرایشگر HTML باید پاک‌سازی (Sanitize) شود.

### 52.6 بارگذاری فایل

پیوست‌ها باید بر اساس موارد زیر اعتبارسنجی شوند:

- پسوند.
- نوع محتوا، در صورت امکان.
- اندازه.
- تعداد.
- قواعد ذخیره‌سازی.

فایل‌های بارگذاری‌شده نباید به‌طور خودکار به محتوای قابل‌اجرا تبدیل شوند.

## 53. یکپارچگی داده

پایگاه‌داده باید محدودیت‌های مناسب را اعمال کند، از جمله:

- فیلدهای الزامی.
- فیلدهای یکتا.
- کلیدهای خارجی.
- روابط ترکیبی یکتا.
- نمایش‌های معتبر enum در جایی که مرتبط است.

Invariantهای مهم کسب‌وکاری باید در لایه Application/Domain اعمال شوند و صرفاً به اعتبارسنجی رابط کاربری تکیه نکنند.

## 54. همزمانی (Concurrency)

عملیاتی که می‌توانند به‌صورت همزمان فعال شوند باید طوری طراحی شوند که از وضعیت ناسازگار جلوگیری شود.

نمونه‌های مهم:

- دو Callback پرداخت برای یک تراکنش یکسان.
- دو درخواست Checkout برای یک سبد خرید یکسان.
- درخواست‌های علاقه‌مندی تکراری.
- تخصیص همزمان مجوز به نقش.
- پردازش همزمان سفارش.

محدودیت‌های یکتای پایگاه‌داده و Idempotency در سطح برنامه باید در جایی که لازم است با هم استفاده شوند.

## 55. کش

Redis باید برای موارد زیر استفاده شود:

- سبدهای خرید.
- وضعیت موقت OTP در صورت لزوم.
- ورودی‌های کش برنامه که صراحتاً پیکربندی شده‌اند.

داده‌های کش‌شده باید یک سیاست انقضا داشته باشند.

داده‌های حیاتی کسب‌وکاری پایدارشده نباید فقط در Redis وجود داشته باشند.

## 59. Result Pattern

عملیات Application باید از یک Result Pattern استفاده کنند، نه استفاده از استثناها به‌عنوان مکانیزم عادی برای خطاهای کسب‌وکاری موردانتظار.

خطاهای موردانتظار می‌توانند شامل موارد زیر باشند:

- دوره یافت نشد.
- محدودیت سلسله‌مراتب دسته‌بندی رد شده.
- کاربر غیرفعال.
- مجوز رد شده.
- شماره تلفن الزامی.
- تخفیف نامعتبر.
- دوره برای فروش در دسترس نیست.
- دسترسی ناکافی به دوره.
- وضعیت پرداخت نامعتبر.

خطاهای غیرمنتظره زیرساختی/سیستمی همچنان باید از مدیریت استثنا و مدیریت خطای متمرکز استفاده کنند.

## 60. CQRS و MediatR

Commandها باید وضعیت را تغییر دهند.

Queryها باید داده را بدون تغییر وضعیت کسب‌وکاری بازیابی کنند.

MediatR باید به‌عنوان مکانیزم Dispatch برنامه برای Commandها و Queryها، در جایی که مرتبط است، استفاده شود.

دغدغه‌های میان‌بُرشی (Cross-Cutting) مانند:

- اعتبارسنجی.
- ثبت لاگ.
- اندازه‌گیری عملکرد.
- مدیریت تراکنش، در جایی که مرتبط است.

می‌توانند از طریق Pipeline Behaviorهای MediatR پیاده‌سازی شوند.

اعتبارسنجی کسب‌وکاری و اعتبارسنجی Command.

Invariantهایی که همیشه باید برقرار باشند.

### پایگاه‌داده

محدودیت‌های نهایی یکپارچگی.

## 62. قواعد دسترسی عمومی

وب‌سایت عمومی باید فقط محتوا را بر اساس وضعیت آن در معرض دید قرار دهد.

نمونه‌ها:

```text
دوره:
    منتشرشده -> عمومی
    پیش‌نویس -> غیرعمومی
    پنهان    -> غیرعمومی

بلاگ:
    منتشرشده/نمایش-فعال -> عمومی
    در غیر این صورت      -> غیرعمومی
```

محتوای دوره پولی، به‌جز اپیزودهای صراحتاً رایگان، نیازمند مالکیت دوره است.

## 63. قواعد دسترسی دوره

یک کاربر می‌تواند به یک دوره دسترسی داشته باشد اگر:

```text
Course.IsFree = true
```

یا:

```text
کاربر مالک دوره است
```

یا، برای یک دوره پولی:

```text
Episode.IsFree = true
```

دسترسی پیش‌نمایش رایگان نباید مالکیت کل دوره را اعطا کند.

## 68. داده‌های سیستمی اولیه موردنیاز

- نقش‌های سیستمی اولیه.
- مجوزهای سیستمی اولیه.
- تخصیص‌های اولیه مجوز به نقش.
- تنظیمات سیستمی موردنیاز.

## 69. نیازمندی‌های غیرعملکردی

### 69.1 عملکرد (Performance)

برنامه باید:

- از I/O ناهمگام (Asynchronous) استفاده کند.
- از فراخوانی‌های Blocking خودداری کند.
- برای لیست‌های احتمالاً بزرگ Admin/عمومی از صفحه‌بندی (Pagination) استفاده کند.
- از کوئری‌های N+1 پایگاه‌داده خودداری کند.
- کوئری‌های کند پایگاه‌داده را پایش کند.
- درخواست‌های HTTP کند را پایش کند.

### 69.2 مقیاس‌پذیری (Scalability)

برنامه باید تا حد امکان در لایه وب‌سرور Stateless باقی بماند.

وضعیت Session/سبد خرید نباید به حافظه محلی سرور وابسته باشد.

Redis باید برای وضعیت موقت مشترک استفاده شود.

### 69.3 قابلیت نگهداری (Maintainability)

کدبیس باید:

- مرزهای Clean Architecture را رعایت کند.
- دغدغه‌های Domain، Application، Infrastructure و Presentation را جدا کند.
- از تزریق وابستگی استفاده کند.
- برای قواعد مهم کسب‌وکاری از تست‌های خودکار استفاده کند.
- از تکرار منطق کسب‌وکاری خودداری کند.

### 69.4 قابلیت‌اطمینان (Reliability)

عملیات حیاتی باید در جایی که امکان تکرار درخواست وجود دارد، Idempotent باشند.

پردازش پرداخت به‌طور خاص باید Idempotent باشد.

### 69.5 امنیت

برنامه باید از پیش‌فرض‌های امن برای موارد زیر پیروی کند:

- احراز هویت.
- مجوزدهی.
- ذخیره‌سازی رمز عبور.
- بارگذاری فایل.
- رندر HTML.
- اسرار (Secrets).
- ثبت لاگ.
- اعتبارسنجی ورودی.

## 71. معیارهای پذیرش — جریان‌های اصلی

### 71.1 خرید دوره

موارد زیر باید صادق باشند:

1. یک کاربر می‌تواند دوره‌های منتشرشده را مرور کند.
2. یک دوره پولی می‌تواند به سبد خرید Redis اضافه شود.
3. فرآیند پرداخت نیازمند شماره تلفن است.
4. سرور قیمت سفارش را محاسبه می‌کند.
5. یک سفارش ایجاد می‌شود.
6. یک رکورد پرداخت ایجاد می‌شود.
7. یک پرداخت موفق، سفارش را به `Paid` تغییر می‌دهد.
8. کاربر دسترسی به دوره را دریافت می‌کند.
9. یک فاکتور در دسترس قرار می‌گیرد.
10. پردازش مجدد نتیجه یکسان پرداخت، دسترسی یا وضعیت فاکتور را تکراری نمی‌کند.

### 71.2 نقش‌های پویا

موارد زیر باید صادق باشند:

1. یک مدیر مجاز می‌تواند یک نقش ایجاد کند.
2. مدیر می‌تواند نقش را ویرایش کند.
3. مدیر می‌تواند مجوزها را تخصیص دهد.
4. مدیر می‌تواند نقش را به کاربران تخصیص دهد.
5. کاربر مجوزهای نقش را دریافت می‌کند.
6. مجوزدهی بر پایه کلیدهای مجوز است.
7. مدیر می‌تواند نقش را در صورتی که به‌عنوان نقش سیستمی محافظت‌نشده باشد حذف کند.

### 71.3 ساختار دوره

موارد زیر باید صادق باشند:

1. یک دوره می‌تواند شامل چندین بخش باشد.
2. یک بخش می‌تواند شامل چندین اپیزود باشد.
3. بخش‌ها مرتب‌شده هستند.
4. اپیزودها مرتب‌شده هستند.
5. مدت‌زمان اپیزود در دسترس است.
6. یک دوره پولی می‌تواند شامل چندین اپیزود رایگان باشد.
7. اپیزودهای غیررایگان نیازمند مالکیت دوره هستند.

## 72. خلاصه قواعد کسب‌وکاری صریح

قواعد زیر الزامی هستند:

1. سلسله‌مراتب دسته‌بندی نمی‌تواند از سه سطح فراتر رود.
2. اسلاگ‌های دوره یکتا هستند.
3. اسلاگ‌های بلاگ یکتا هستند.
4. شماره‌های تلفن در صورت وجود یکتا هستند.
5. ایمیل‌ها در صورت وجود یکتا هستند.
6. رمزهای عبور هرگز به‌صورت متن ساده ذخیره نمی‌شوند.
7. نقش‌ها پویا هستند.
8. مجوزها پویا هستند.
9. نقش‌ها مجوز دریافت می‌کنند.
10. مجوزدهی از مجوزها استفاده می‌کند، نه نام‌های نقش Hard-code شده.
11. نقش‌ها/مجوزهای سیستمی در برابر تغییرات مخرب محافظت می‌شوند.
12. سبدهای خرید در Redis ذخیره می‌شوند.
13. قیمت‌های سفارش تصویر لحظه‌ای (Snapshot) می‌شوند.
14. پردازش پرداخت Idempotent است.
15. پرداخت موفق دسترسی به دوره را اعطا می‌کند.
16. اپیزودهای رایگان دوره‌های پولی بدون خرید کل دوره قابل‌مشاهده هستند.
17. اپیزودهای غیررایگان پولی نیازمند مالکیت دوره هستند.
18. کاربران احرازهویت‌شده از طریق گوگل باید پیش از پرداخت شماره تلفن ارائه دهند.
19. یکپارچه‌سازی واقعی سرویس پیامک الزامی نیست.
20. یکپارچه‌سازی واقعی ارائه‌دهنده پرداخت الزامی نیست.
21. پیوست‌های دوره دارای محدودیت تعداد و اندازه هستند.
22. محدودیت‌های پیوست پیکربندی‌محور هستند.
23. محتوای عمومی باید وضعیت نمایش خود را رعایت کند.
24. عملیات مدیریتی باید توسط مجوز محافظت شوند.
25. خطاهای غیرمنتظره سرور باید لاگ شوند و نباید جزئیات حساس را فاش کنند.
26. لاگ‌ها، ردیابی‌ها و متریک‌ها باید از طریق زیرساخت مشاهده‌پذیری در دسترس باشند.
27. Grafana باید داشبوردهای مشاهده‌پذیری یکپارچه فراهم کند.
28. انتزاع‌های Repository و Unit of Work باید برای دسترسی به Persistence استفاده شوند.
29. Controllerها و Razor Pageها نباید مستقیماً به `DbContext` مربوط به EF Core دسترسی داشته باشند.
30. منطق کسب‌وکاری متعلق به لایه‌های Application/Domain است.

## 74. اصول پیاده‌سازی

پیاده‌سازی باید از این اصول پیروی کند:

- از ASP.NET Core Identity استفاده نکنید.
- نقش‌ها را به‌عنوان مکانیزم مجوزدهی Hard-code نکنید.
- مجوزها را در منطق ارائه (Presentation) Hard-code نکنید.
- سبدهای خرید را به‌عنوان وضعیت اصلی سبد در PostgreSQL ذخیره نکنید.
- به قیمت‌های سمت کلاینت اعتماد نکنید.
- رمزهای عبور را به‌صورت متن ساده ذخیره نکنید.
- استثناهای داخلی را به کاربران فاش نکنید.
- HTML پاک‌سازی‌نشده را نمایش ندهید.
- عمق دسته‌بندی فراتر از سه سطح را مجاز نکنید.
- قواعد کسب‌وکاری را بین MVC، Razor Pages و سرویس‌های Application تکرار نکنید.
- `DbContext` را خارج از Infrastructure افشا نکنید.
- از یک Repository عمومی صرفاً به‌خاطر داشتن یک Repository استفاده نکنید.
- از Unit of Work برای مرزهای پایدار و سازگار Persistence استفاده کنید.
- پردازش نتیجه پرداخت را Idempotent کنید.
- یکپارچه‌سازی‌های خارجی را پشت انتزاع نگه دارید.
- پیکربندی و اسرار را خارج از کد منبع نگه دارید.
- قواعد صریح Domain/Application را به رفتار ضمنی ترجیح دهید.

## 75. تعریف انجام‌شده (Definition of Done)

یک ویژگی زمانی کامل در نظر گرفته می‌شود که:

1. مدل Domain آن در جایی که لازم است پیاده‌سازی شده باشد.
2. Command/Query مربوط در Application پیاده‌سازی شده باشد.
3. اعتبارسنجی پیاده‌سازی شده باشد.
4. مجوزدهی در جایی که لازم است پیاده‌سازی شده باشد.
5. Persistence از طریق مرز Repository/Unit of Work پیاده‌سازی شده باشد.
6. محدودیت‌های موردنیاز پایگاه‌داده وجود داشته باشند.
7. رابط کاربری وب‌سایت عمومی یا پنل مدیریت به‌صورت مقتضی پیاده‌سازی شده باشد.
8. مدیریت خطا پیاده‌سازی شده باشد.
9. لاگ‌ها و تله‌متری مرتبط وجود داشته باشند.
10. تست‌های خودکار، قواعد کسب‌وکاری مهم را پوشش دهند.
11. ویژگی از مرزهای معماری عبور نکند.
12. هیچ اطلاعات حساسی از طریق لاگ‌ها یا رابط کاربری فاش نشود.
13. ویژگی از قواعد کسب‌وکاری تعریف‌شده در این سند پیروی کند.

## 76. نتیجه‌گیری

این SRS دامنه پیاده‌سازی اول پلتفرم دوره‌های آنلاین را تعریف می‌کند.

این سیستم عمداً حول موارد زیر طراحی شده است:

```text
Clean Architecture
        +
CQRS / MediatR
        +
Repository / Unit of Work
        +
Result Pattern
        +
PostgreSQL
        +
Redis
        +
مجوزدهی سفارشی بر پایه Permission
        +
Serilog / OpenTelemetry
        +
Loki / Tempo / Prometheus
        +
Grafana
```

سیستم باید بدون معرفی ویژگی‌های غیرضروری خارج از دامنه تعریف‌شده، قابل‌توسعه باقی بماند. نقش‌ها و مجوزهای پویا یک نیازمندی محوری هستند، در حالی که ارائه‌دهندگان پرداخت و پیامک عمداً انتزاع شده‌اند تا یکپارچه‌سازی‌های واقعی بعداً بدون تغییر مدل اصلی کسب‌وکار قابل‌افزودن باشند.
