# مشخصات نیازمندی‌های نرم‌افزار (SRS)

## وایلند — پلتفرم آموزشی

**نام پروژه:** Whyland (وایلند)

**نوع پروژه:** آموزشی / پلتفرم دوره‌های آنلاین

**هدف پروژه:** پروژه تمرینی و نمونه‌کار (پورتفولیو)

**نسخه سند:** 1.0

**وضعیت:** پیش‌نویس آماده برای پیاده‌سازی

**زبان اصلی سند:** انگلیسی

---

## 1. هدف

این سند نیازمندی‌های عملکردی و غیرعملکردی یک پلتفرم آموزش آنلاین را تعریف می‌کند که به کاربران امکان می‌دهد دوره‌های آنلاین را کشف کنند، خریداری کنند و به آن‌ها دسترسی داشته باشند.

این پلتفرم شامل موارد زیر است:

1. یک وب‌سایت عمومی پیاده‌سازی‌شده با ASP.NET Core MVC.
2. یک پنل مدیریت پیاده‌سازی‌شده با ASP.NET Core Razor Pages.
3. یک سیستم احراز هویت و مجوزدهی سفارشی بدون استفاده از ASP.NET Core Identity.
4. یک پایگاه‌داده رابطه‌ای PostgreSQL.
5. Redis برای ذخیره‌سازی سبد خرید و کش.
6. یک زیرساخت مشاهده‌پذیری (Observability) مبتنی بر Serilog، OpenTelemetry، Grafana Loki، Grafana Tempo و Prometheus.

هدف از این SRS ارائه نیازمندی‌هایی با دقت کافی است تا پلتفرم وایلند بدون تکیه بر فرضیات کسب‌وکاری مستندنشده قابل پیاده‌سازی باشد. وایلند به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود تا معماری نرم‌افزاری تولید-محور، توسعه بک‌اند، توسعه وب، مجوزدهی، پایداری داده‌ها (Persistence)، پرداخت و مشاهده‌پذیری را نشان دهد.

## 2. بستر پروژه

وایلند یک پلتفرم آموزشی است که به‌عنوان یک پروژه تمرینی و نمونه‌کار توسعه داده می‌شود. اگرچه هدف اصلی این پروژه یادگیری و نمایش مهارت‌های مهندسی است، اما معماری و نیازمندی‌های آن باید تا جای ممکن از رویه‌های تولید-محور پیروی کند.

پیاده‌سازی باید جداسازی روشن دغدغه‌ها (Separation of Concerns)، کد قابل نگهداری، قواعد کسب‌وکاری واقع‌گرایانه، احراز هویت و مجوزدهی امن، پردازش قابل‌اعتماد سفارش/پرداخت، و مشاهده‌پذیری کامل برنامه را نشان دهد.

## 3. دامنه پروژه

### 3.1 در دامنه پروژه

سیستم باید موارد زیر را فراهم کند:

- دسته‌بندی‌های سلسله‌مراتبی دوره با حداکثر عمق سه سطح.
- ایجاد و مدیریت دوره.
- بخش‌ها (Sections) و اپیزودهای دوره.
- اپیزودهای پیش‌نمایش رایگان برای دوره‌های پولی.
- پیوست‌های اپیزود با محدودیت‌های قابل‌پیکربندی.
- سوالات متداول اختصاصی هر دوره.
- بلاگ عمومی.
- سوالات متداول عمومی.
- کاربران پویا.
- نقش‌های پویا.
- مجوزهای پویا.
- تخصیص مجوز بر پایه نقش.
- احراز هویت با شماره تلفن.
- یک سرویس پیامک ساختگی (Fake) برای توسعه/تست.
- احراز هویت با گوگل.
- الزام دریافت شماره تلفن قبل از خرید.
- مدیریت پروفایل کاربر.
- پروفایل مدرسان.
- علاقه‌مندی‌های دوره (Favorites).
- دسترسی به دوره‌های خریداری‌شده.
- سبدهای خرید مبتنی بر Redis.
- سفارش‌ها و اقلام سفارش.
- روش‌های پرداخت که با یک enum نمایش داده می‌شوند.
- رکوردهای پرداخت.
- فاکتورها.
- کوپن‌های تخفیف قابل‌اعمال در سبد خرید و فرآیند پرداخت.
- تنظیمات پویای سایت.
- صفحات عمومی MVC.
- پنل مدیریت Razor Pages.
- مجوزدهی بر پایه Permission.
- ثبت لاگ ساختاریافته.
- ردیابی توزیع‌شده (Distributed Tracing).
- متریک‌ها.
- داشبوردهای Grafana.
- مدیریت خطاهای 403، 404 و 500.

### 3.2 خارج از دامنه پروژه

موارد زیر صراحتاً خارج از دامنه پیاده‌سازی اول هستند:

- یکپارچه‌سازی با سرویس واقعی پیامک.
- یکپارچه‌سازی واقعی با پرداخت گوگل.
- یکپارچه‌سازی واقعی با درگاه بانکی.
- یکپارچه‌سازی واقعی با زرین‌پال.
- یکپارچه‌سازی واقعی با اسنپ‌پی.
- پردازش تسویه‌حساب/پرداخت به مدرسان.
- یادداشت‌های شخصی کاربر روی اپیزودها.
- اپلیکیشن موبایل بومی (Native).
- یک فرانت‌اند SPA جداگانه.
- ASP.NET Core Identity.

ارائه‌دهندگان پرداخت فقط باید از طریق انتزاع/enum روش پرداخت و یک مرز (Boundary) مناسب در سطح برنامه نمایش داده شوند. پیاده‌سازی واقعی ارائه‌دهندگان در این نسخه الزامی نیست.

## 5. معماری سطح‌بالا

برنامه باید از معماری Clean Architecture پیروی کند.

```text
+--------------------------+
| اپلیکیشن عمومی MVC        |
+------------+-------------+
             |
+------------v-------------+
| لایه Application          |
| CQRS / MediatR            |
| قواعد کسب‌وکاری            |
| Result Pattern             |
+------------+-------------+
             |
+------------v-------------+
| لایه Domain               |
| Entities / Value Objects  |
| قواعد Domain               |
+------------+-------------+
             |
+------------v-------------+
| لایه Infrastructure       |
| EF Core / PostgreSQL      |
| Redis                     |
| احراز هویت                |
| پیامک / سرویس‌های خارجی    |
| مشاهده‌پذیری               |
+--------------------------+

+--------------------------+
| Admin Razor Pages         |
+------------+-------------+
             |
             v
      لایه Application
```

لایه‌های ارائه (Presentation) نباید مستقیماً قواعد کسب‌وکاری را پیاده‌سازی کنند یا به دغدغه‌های Infrastructure که متعلق به لایه‌های Application/Infrastructure هستند دسترسی مستقیم داشته باشند.

## 7. نیازمندی‌های Repository و Unit of Work

### 7.1 الگوی Repository

دسترسی به پایداری داده‌ها (Persistence) باید از طریق Repository انتزاع شود.

Repositoryها باید حول Aggregate Rootها و عملیات معنادار Domain تعریف شوند، نه با ایجاد یک Repository غیرضروری برای هر جدول پایگاه‌داده.

نمونه‌ها:

```text
ICourseRepository
ICategoryRepository
IUserRepository
IRoleRepository
IPermissionRepository
IOrderRepository
IPaymentRepository
IBlogPostRepository
```

Repositoryها باید:

- کوئری‌های اختصاصی پایداری داده را کپسوله کنند.
- مدل‌های Domain/Application متناسب با لایه را بازگردانند.
- از افشای `DbContext` به Handlerهای Application خودداری کنند.
- از نشت جزئیات پیاده‌سازی اختصاصی EF Core به Domain خودداری کنند.
- از عملیات ناهمگام (Asynchronous) پشتیبانی کنند.
- از Cancellation Token پشتیبانی کنند.

### 7.2 Unit of Work

لایه Persistence باید یک انتزاع Unit of Work پیاده‌سازی کند.

نمونه:

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken cancellationToken);
}
```

`DbContext` مربوط به EF Core باید رفتار Unit of Work را پیاده‌سازی کند.

یک دستور (Command) واحد در برنامه که چندین موجودیت مرتبط را تغییر می‌دهد باید از یک مرز تراکنشی واحد Unit of Work در جایی که سازگاری (Consistency) لازم است استفاده کند.

نمونه:

```text
ایجاد سفارش
    |
    +-- ایجاد سفارش
    +-- ایجاد اقلام سفارش
    +-- خالی‌کردن/مصرف سبد خرید
    +-- ذخیره تغییرات
```

این عملیات نباید منجر به یک سفارش به‌صورت ناقص ذخیره‌شده شوند.

### 7.3 قواعد تراکنش

در جایی که چندین تغییر پایگاه‌داده باید با هم موفق یا ناموفق شوند، باید از یک تراکنش پایگاه‌داده استفاده شود.

فراخوانی‌های سرویس خارجی نباید به‌اشتباه درون تراکنش‌های پایگاه‌داده طولانی‌مدت قرار گیرند.

Callbackهای پرداخت باید Idempotent (بی‌اثر در تکرار) باشند.

### 7.4 محدودیت‌های Repository

موارد زیر باید کنار گذاشته شوند:

- Repository عمومی صرفاً برای انتزاع CRUD.
- افشای `IQueryable` از Repositoryها در جایی که موجب نشت دغدغه‌های Persistence می‌شود.
- دسترسی مستقیم به `DbContext` از Controllerها، Razor Pageها یا Handlerهای MediatR.
- پیاده‌سازی قواعد کسب‌وکاری درون پیکربندی‌های EF Core.

## 9. مدیریت دسته‌بندی

### 9.1 فیلدها

یک دسته‌بندی باید شامل موارد زیر باشد:

| فیلد | الزام |
|---|---|
| Id | شناسه یکتا |
| Name | الزامی |
| LatinName | الزامی |
| DisplayOrder | عدد صحیح الزامی |
| ParentId | قابل‌تهی (Nullable) |
| IsActive | بولین الزامی |
| CreatedAt | الزامی |
| UpdatedAt | الزامی |

### 9.2 سلسله‌مراتب

دسته‌بندی‌ها باید حداکثر سه سطح را پشتیبانی کنند.

نمونه:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
```

مورد زیر نامعتبر است:

```text
توسعه وب
    └── بک‌اند
        └── جنگو
            └── جنگو پیشرفته
```

برنامه باید ایجاد یا ویرایشی که منجر به تولید سطح چهارم می‌شود را رد کند.

### 9.3 قواعد

- یک دسته‌بندی باید هویت یکتا داشته باشد.
- یک دسته‌بندی می‌تواند صفر یا یک والد داشته باشد.
- یک دسته‌بندی ریشه دارای `ParentId = null` است.
- یک دسته‌بندی نمی‌تواند والد خودش باشد.
- روابط والد چرخه‌ای (Circular) ممنوع هستند.
- دسته‌بندی‌های غیرفعال نباید برای دسته‌بندی دوره‌های جدید قابل‌انتخاب باشند.
- روابط موجود نباید هنگام غیرفعال شدن یک دسته‌بندی به‌صورت بی‌سروصدا حذف شوند.
- حذف یک دسته‌بندی که توسط یک دوره ارجاع داده شده باید یا جلوگیری یا به‌صراحت مدیریت شود؛ پیاده‌سازی نباید روابط دوره-دسته‌بندی را به‌صورت یتیم و بی‌سروصدا رها کند.

## 10. مدیریت دوره

### 10.1 فیلدهای دوره

| فیلد | الزام |
|---|---|
| Id | شناسه یکتا |
| Name | الزامی |
| LatinName | الزامی |
| ShortDescription | الزامی |
| Description | اختیاری/الزامی بر اساس قواعد اعتبارسنجی؛ از محتوای ویرایشگر HTML پشتیبانی می‌کند |
| Slug | الزامی و یکتا |
| MainImage | اختیاری |
| IsFree | الزامی |
| Price | برای دوره‌های پولی الزامی |
| DiscountType | None / Percentage / FixedAmount |
| DiscountValue | زمانی که تخفیف فعال است الزامی |
| IsSaleActive | الزامی |
| DisplayStatus | Draft / Published / Hidden |
| IsFeatured | الزامی |
| IsAmazing | الزامی |
| IntroductionVideo | اختیاری |
| CreatedAt | الزامی |
| UpdatedAt | الزامی |

### 10.2 توضیحات

توضیحات کامل باید از محتوای ویرایشگر HTML پشتیبانی کند.

سیستم باید HTML را بر اساس یک allowlist صریح، پیش از نمایش عمومی پاک‌سازی (Sanitize) کند.

HTML خام و کنترل‌نشده توسط کاربر نباید مستقیماً رندر شود.

### 10.3 Slug

اسلاگ دوره باید:

- یکتا باشد.
- امن برای URL باشد.
- مگر با تغییر صریح، پایدار بماند.
- برای URLهای عمومی دوره استفاده شود.

### 10.4 قیمت‌گذاری

قیمت دوره‌ها باید از یک نوع پولی سازگار با اعشار (Decimal) استفاده کند.

`float` و `double` نباید برای مقادیر پولی استفاده شوند.

برای یک دوره رایگان:

```text
IsFree = true
```

سیستم نباید برای دسترسی به دوره نیازمند پرداخت باشد.

برای یک دوره پولی:

```text
IsFree = false
Price > 0
```

### 10.5 تخفیف

انواع تخفیف پشتیبانی‌شده:

```text
None
Percentage
FixedAmount
```

تخفیف‌های درصدی باید در بازه زیر باشند:

```text
0 <= DiscountValue <= 100
```

تخفیف‌های ثابت نباید قیمت نهایی را منفی کنند.

قیمت نهایی قابل‌پرداخت باید به‌صورت متمرکز در لایه Application/Domain محاسبه شود.

### 10.6 وضعیت فروش

`IsSaleActive` کنترل می‌کند که آیا دوره در حال حاضر قابل‌خرید است یا خیر.

یک دوره می‌تواند منتشرشده باشد اما در حال حاضر قابل‌خرید نباشد.

سیستم نباید وضعیت فروش را از وضعیت نمایش استنتاج کند.

### 10.7 وضعیت نمایش

مقادیر پشتیبانی‌شده:

```text
Draft (پیش‌نویس)
Published (منتشرشده)
Hidden (پنهان)
```

فقط دوره‌های منتشرشده باید به‌عنوان لیست عادی دوره‌ها به‌صورت عمومی قابل‌کشف باشند.

دوره‌های پیش‌نویس و پنهان نباید به‌صورت عمومی در معرض دید قرار گیرند.

## 20. احراز هویت

این پلتفرم نباید از ASP.NET Core Identity استفاده کند.

احراز هویت باید با استفاده از مدل اختصاصی کاربر، اعتبارنامه، نقش و مجوز خود برنامه پیاده‌سازی شود.

### 20.1 احراز هویت با شماره تلفن

سیستم باید از احراز هویت مبتنی بر شماره تلفن پشتیبانی کند.

جریان پایه:

```text
وارد کردن شماره تلفن
        |
        v
درخواست کد یک‌بارمصرف (OTP)
        |
        v
سرویس پیامک ساختگی
        |
        v
وارد کردن کد یک‌بارمصرف
        |
        v
اعتبارسنجی کد یک‌بارمصرف
        |
        v
احراز هویت کاربر
```

کد یک‌بارمصرف (OTP) باید:

- زمان انقضای قابل‌پیکربندی داشته باشد.
- حداکثر تعداد تلاش اعتبارسنجی قابل‌پیکربندی داشته باشد.
- پس از اعتبارسنجی موفق، باطل شود.
- در صورت ذخیره‌سازی، به‌صورت متن ساده ذخیره نشود.
- نرخ‌محدود (Rate Limited) باشد.

### 20.2 سرویس پیامک ساختگی

یک اینترفیس ساده باید تعریف شود:

```csharp
public interface ISmsService
{
    Task SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

پیاده‌سازی محیط توسعه نباید پیامک واقعی ارسال کند.

این پیاده‌سازی می‌تواند:

- کد OTP را لاگ کند.
- آن را به‌صورت موقت برای اهداف تست ذخیره کند.
- یک نتیجه تحویل موفق بازگرداند.

سرویس ساختگی باید بدون تغییر منطق کسب‌وکاری Application قابل‌جایگزینی باشد.

## 21. احراز هویت با گوگل

احراز هویت Google OAuth/OpenID Connect باید پشتیبانی شود.

یک کاربر احرازهویت‌شده با گوگل باید بتواند یک حساب User محلی ایجاد کند یا به آن دسترسی داشته باشد.

حساب محلی باید از طریق یک رکورد ورود خارجی (External Login) مناسب به هویت خارجی گوگل متصل شود.

احراز هویت گوگل نباید جایگزین موجودیت User محلی شود.

### 23.2 CRUD نقش پویا

مدیرانی که مجوز مناسب را دارند باید بتوانند:

- نقش‌ها را مشاهده کنند.

## 30. سبد خرید

سبد خرید باید در Redis ذخیره شود.

نباید به‌عنوان منبع اصلی سبد خرید در PostgreSQL پایدار (Persist) شود.

### 30.1 قلم سبد خرید

هر قلم سبد خرید باید شامل موارد زیر باشد:

```text
CourseId
Quantity
```

یک دوره نباید بیش از یک‌بار در یک سبد خرید ظاهر شود.

از آنجا که محصول یک حق دسترسی (Entitlement) به دوره است، قاعده کسب‌وکاری معمولاً باید تعداد را به یک عدد در هر دوره محدود کند.

اگر API مقداری بزرگ‌تر از مقدار مجاز دریافت کند، باید آن را بر اساس یک قاعده مستندشده واحد رد یا نرمال (Normalize) کند. پیاده‌سازی باید از یک رفتار یکسان و پایدار استفاده کند.

### 30.2 کلید سبد خرید

کلید Redis باید با کاربر احرازهویت‌شده مرتبط باشد.

نمونه:

```text
cart:{userId}
```

پایداری سبد خرید کاربران احرازهویت‌نشده در این نسخه الزامی نیست، مگر آنکه صراحتاً بعداً اضافه شود.

### 30.3 کوپن اعمال‌شده

یک سبد خرید حداکثر می‌تواند یک کوپن اعمال‌شده داشته باشد.

علاوه بر اقلام، سبد خرید ذخیره‌شده در Redis باید یک کد کوپن اختیاری نیز حمل کند:

```text
cart:{userId}
    Items      : CourseId, Quantity
    CouponCode : اختیاری
```

فقط کد کوپن باید در سبد خرید ذخیره شود. مبالغ تخفیف حاصل از کوپن هرگز نباید به‌عنوان مقادیر قابل‌اعتماد ذخیره شوند و هرگز نباید از مرورگر پذیرفته شوند. سرور باید هر بار که سبد خرید یا خلاصه پرداخت خوانده می‌شود، آن‌ها را مجدداً محاسبه کند.

کد کوپن باید در موارد زیر از سبد خرید حذف شود:

- کاربر آن را حذف کند.
- سبد خرید خالی شود یا پس از خرید موفق پاک شود.

اگر کوپن اعمال‌شده در حالی که هنوز در سبد خرید است واجد شرایط بودن را از دست بدهد (برای مثال منقضی شود، سقف استفاده آن تکمیل شود، یا پس از حذف یک قلم، جمع جزء واجد شرایط از حداقل مبلغ سفارش کمتر شود)، سرور باید تخفیف آن را از تمام مجموع‌ها کنار بگذارد و به کاربر اطلاع دهد که کوپن دیگر قابل اعمال نیست. سبد خرید هرگز نباید تخفیفی را که معتبر نیست نمایش دهد.

قواعد واجد شرایط بودن و محاسبه در بخش ۹۵ تعریف شده‌اند.

## 32. وضعیت سفارش

enum وضعیت اولیه باید شامل موارد زیر باشد:

```text
Pending (در انتظار)
Paid (پرداخت‌شده)
Cancelled (لغوشده)
Failed (ناموفق)
```

انتقال‌های وضعیت باید توسط قواعد کسب‌وکاری برنامه کنترل شوند.

یک سفارش نباید صرفاً به این دلیل که یک کلاینت موفقیت را گزارش می‌دهد، به `Paid` تغییر یابد.

### 32.1 انقضای سفارش در انتظار (Pending Order Expiration)

یک سفارش `Pending` نباید برای همیشه در حالت انتظار باقی بماند.

هنگامی که یک سفارش به‌صورت `Pending` ایجاد می‌شود، `ExpiresAt` باید برابر زمان ایجاد به‌علاوه مدت انقضای پیکربندی‌شده (`PendingOrderExpirationMinutes`) مقداردهی شود.

یک Job پس‌زمینه باید به‌صورت دوره‌ای سفارش‌های `Pending` را که `ExpiresAt` آن‌ها گذشته است پردازش کند. برای هر سفارش، باید:

- وضعیت سفارش را به `Cancelled` تغییر دهد.
- رکورد پرداخت `Pending` آن را به `Cancelled` تغییر دهد.
- استفاده رزروشده کوپن را دقیقاً یک‌بار آزاد کند (بخش ۹۵).

انتقال از وضعیت `Pending` باید یک به‌روزرسانی شرطی و اتمیک باشد تا انقضا نتواند با نتیجه پرداختی که همان سفارش را `Paid` می‌کند دچار رقابت (Race) شود. هر انتقالی که زودتر اعمال شود نهایی است.

Job باید Idempotent باشد و زمانی که چند نمونه برنامه هم‌زمان آن را اجرا می‌کنند ایمن باشد.

اگر نتیجه پرداخت موفق برای سفارشی برسد که پیش‌تر با انقضا لغو شده است، سیستم نباید آن را بی‌صدا نادیده بگیرد و نباید به‌صورت خودکار دسترسی دوره اعطا کند یا فاکتور صادر کند. باید نتیجه پرداخت را به‌صورت Idempotent ثبت کند، آن را به‌عنوان خطا همراه با اطلاعات همبستگی (Correlation) لاگ کند و آن را در ماژول‌های سفارش‌ها و پرداخت‌ها برای بررسی مدیریتی قابل شناسایی کند.

انقضای سفارش باید با لاگ ساختاریافته ثبت شود.

## 35. Idempotency پرداخت

پردازش نتیجه پرداخت باید Idempotent باشد.

اگر نتیجه پرداخت یکسان چندین بار دریافت شود، سیستم نباید:

- پرداخت‌های تکراری ایجاد کند.
- ثبت‌نام‌های (Enrollment) تکراری ایجاد کند.
- فاکتورهای تکراری ایجاد کند.
- در وضعیت برنامه، از کاربر چندین‌بار هزینه دریافت کند.

در جایی که قابل‌اعمال است باید از یک شناسه پایدار پرداخت/ارائه‌دهنده استفاده شود.

## 42. صفحه سبد خرید

صفحه سبد خرید باید موارد زیر را نمایش دهد:

- دوره.
- تعداد.
- قیمت واحد.
- تخفیف.
- جمع نهایی ردیف.
- جمع جزء (مجموع جمع‌های ردیف‌ها پس از تخفیف‌های سطح دوره).
- تخفیف کوپن، در صورت اعمال کوپن.
- جمع کل سبد خرید (مبلغ قابل پرداخت پس از کسر تخفیف کوپن).

کاربران باید بتوانند اقلام را حذف کنند.

تغییر تعداد باید قواعد خرید دوره را رعایت کند.

صفحه سبد خرید باید به کاربر احرازهویت‌شده اجازه دهد کوپن اعمال کند. باید شامل موارد زیر باشد:

- یک ورودی کد کوپن همراه با عملیات اعمال، که تا زمانی که کوپنی اعمال نشده نمایش داده می‌شود.
- کد کوپن اعمال‌شده همراه با عملیات حذف آن.
- یک پیام روشن زمانی که کدی قابل اعمال نیست.

اعمال یا حذف کوپن باید بلافاصله مجموع‌های نمایش‌داده‌شده را با مقادیر محاسبه‌شده توسط سرور به‌روز کند.

پیام‌های شکست باید به دلایلی محدود شوند که کاربر می‌تواند نسبت به آن‌ها اقدام کند (برای مثال، حداقل مبلغ سفارش رعایت نشده است). هر شکست دیگری (کد ناشناخته، غیرفعال، منقضی، شروع‌نشده یا تمام‌شده) باید از یک پیام عمومی استفاده کند تا کدهای معتبر از طریق حدس زدن قابل کشف نباشند.

تلاش‌های اعمال کوپن باید Rate Limit شوند.

## 43. فرآیند پرداخت (Checkout)

فرآیند پرداخت باید دقیقاً شامل سه مرحله مفهومی باشد.

```text
1. اطلاعات
        |
        v
2. پرداخت
        |
        v
3. نتیجه پرداخت
```

### 43.1 مرحله ۱ — اطلاعات

سیستم باید اطلاعات موردنیاز مشتری را اعتبارسنجی کند.

شماره تلفن پیش از پرداخت الزامی است.

خلاصه سفارش باید جمع جزء، کد کوپن اعمال‌شده (در صورت وجود)، تخفیف کوپن و مبلغ قابل پرداخت را نمایش دهد.

کاربر باید بتواند در این مرحله با همان قواعد صفحه سبد خرید، کوپن را اعمال، تغییر یا حذف کند. کوپن تا زمانی که سفارش در انتظار در مرحله ۲ ایجاد نشده است قابل تغییر است.

### 43.2 مرحله ۲ — پرداخت

کاربر باید یکی از مقادیر enum روش پرداخت پشتیبانی‌شده را انتخاب کند.

برنامه باید وضعیت لازم پرداخت/سفارشِ در انتظار را ایجاد کند.

هنگامی که سبد خرید کوپن اعمال‌شده دارد، ایجاد سفارش باید علاوه بر آن موارد زیر را انجام دهد:

- کوپن را در همان لحظه در سمت سرور مجدداً اعتبارسنجی کند (بخش ۹۵).
- تخفیف کوپن و مبلغ قابل پرداخت را مجدداً محاسبه کند.
- ارجاع کوپن و مبلغ تخفیف کوپن را به‌صورت Snapshot روی سفارش ذخیره کند.
- یک استفاده از کوپن را به‌صورت اتمیک و داخل تراکنش ایجاد سفارش رزرو کند.

مبلغ پرداخت باید برابر مبلغ قابل پرداخت سفارش پس از کسر تخفیف کوپن باشد.

اگر کوپن هنگام ایجاد سفارش دیگر معتبر نباشد، هیچ سفارش و پرداختی نباید ایجاد شود. کاربر باید همراه با یک پیام و مجموع‌های مجدداً محاسبه‌شده به مرحله ۱ بازگردانده شود و باید صراحتاً ادامه دادن را انتخاب کند. سیستم نباید بی‌صدا با قیمت بالاتر ادامه دهد.

پس از ایجاد سفارش در انتظار، کوپن و مبالغ آن ثابت می‌شوند و نباید تغییر کنند.

### 43.3 مرحله ۳ — نتیجه پرداخت

سیستم باید موارد زیر را نمایش دهد:

- پرداخت موفق.
- پرداخت ناموفق.

نتیجه باید خلاصه سفارش، شامل کد کوپن و تخفیف کوپن در صورت استفاده از کوپن، را نمایش دهد.

برای پرداخت موفق:

```text
پرداخت موفق
        |
        v
سفارش = پرداخت‌شده
        |
        v
اعطای دسترسی به دوره
        |
        v
ایجاد/نهایی‌سازی فاکتور
```

کل این جریان باید در جایی که عملیات پایگاه‌داده دخیل است، از نظر تراکنشی سازگار باشد.

فاکتور ایجادشده برای یک سفارش پرداخت‌شده باید Snapshot کوپن را مطابق بخش ۳۶ حفظ کند.

اگر سفارش `Failed` یا `Cancelled` شود، استفاده از کوپن که برای آن رزرو شده بود باید دقیقاً یک‌بار آزاد شود. سبد خرید، شامل کوپن اعمال‌شده آن، باید برای تلاش مجدد کاربر حفظ شود و کوپن فقط در صورتی اعمال‌شده باقی می‌ماند که همچنان واجد شرایط باشد.

## 44. پنل مدیریت

پنل مدیریت باید با Razor Pages پیاده‌سازی شود.

تمام عملیات مدیریتی باید توسط مجوز محافظت شوند.

### 44.1 ماژول‌های موردنیاز مدیریت

پنل باید مدیریت موارد زیر را فراهم کند:

- دسته‌بندی‌ها.
- دوره‌ها.
- بخش‌های دوره.
- اپیزودها.
- پیوست‌های اپیزود.
- سوالات متداول دوره.
- کاربران.
- پروفایل‌های کاربر.
- مدرسان.
- نقش‌ها.
- مجوزها.
- تخصیص مجوز به نقش.
- تخصیص نقش به کاربر.
- سفارش‌ها.
- پرداخت‌ها.
- کوپن‌ها.
- پست‌های بلاگ.
- سوالات متداول عمومی.
- تنظیمات سایت.

### 44.2 مدیریت کوپن

پنل مدیریت باید مدیریت کوپن را با محافظت مجوزهای `coupon.view`، `coupon.create`، `coupon.edit` و `coupon.delete` فراهم کند.

لیست کوپن‌ها باید کد، نوع، مقدار، میزان استفاده (`UsedCount` / `UsageLimit`)، تاریخ شروع، تاریخ پایان، `IsActive` و یک وضعیت مشتق‌شده (فعال، زمان‌بندی‌شده، منقضی‌شده، تمام‌شده یا غیرفعال) را نمایش دهد. باید جستجو بر اساس کد و فیلتر بر اساس وضعیت را پشتیبانی کند.

فیلدهای فرم کوپن:

| فیلد | الزام |
|---|---|
| Code | الزامی؛ Trim می‌شود؛ یکتا، با مقایسه بدون حساسیت به حروف |
| Type | الزامی؛ Percentage یا FixedAmount |
| Value | الزامی؛ Percentage: بزرگ‌تر از 0 و کوچک‌تر از 100؛ FixedAmount: بزرگ‌تر از 0 |
| MinOrderAmount | اختیاری؛ منفی نباشد |
| UsageLimit | اختیاری؛ خالی یعنی نامحدود؛ در صورت مقداردهی بزرگ‌تر از 0 |
| UsedCount | فقط‌خواندنی |
| StartDate | الزامی |
| EndDate | الزامی؛ بعد از StartDate |
| IsActive | الزامی |

قواعد مدیریت کوپن:

- `UsedCount` هرگز نباید به‌صورت دستی ویرایش شود.
- `UsageLimit` نباید کمتر از `UsedCount` فعلی تنظیم شود.
- ویرایش، غیرفعال‌سازی یا حذف یک کوپن نباید سفارش‌ها یا فاکتورهای موجود را تغییر دهد (بخش ۹۵).
- غیرفعال‌سازی کوپن روش عادی توقف استفاده از آن است. حذف کوپن حذف نرم (Soft Delete) است و کوپنی که توسط هر سفارشی استفاده شده باشد هرگز نباید به‌صورت فیزیکی حذف شود.
- جزئیات سفارش در ماژول سفارش‌ها باید کد کوپن و مبلغ تخفیف کوپن را نمایش دهد.
- فیلدهای حسابرسی باید توسط سرور مقداردهی شوند و هرگز از سمت کلاینت ارائه نشوند.

## 45. نیازمندی‌های CRUD

در جایی که یک موجودیت به‌عنوان قابل‌مدیریت اداری تعریف شده، پنل مدیریت باید عملیات مناسب زیر را فراهم کند:

- ایجاد (Create).
- خواندن/لیست (Read/List).
- به‌روزرسانی (Update).
- حذف (Delete).

عملیات CRUD باید موارد زیر را رعایت کنند:

- اعتبارسنجی.
- مجوزدهی.
- یکپارچگی ارجاعی (Referential Integrity).
- محدودیت‌های موجودیت سیستمی.
- زمان‌مهرهای حسابرسی (Audit Timestamps).

عملیات حذفی که می‌توانند داده‌های تاریخی/مالی مهم را از بین ببرند، باید از یک قاعده کسب‌وکاری مناسب استفاده کنند و نه صرفاً یک حذف فیزیکی کورکورانه.

برای مثال، سفارش‌های پرداخت‌شده و پرداخت‌های موفق نباید از طریق CRUD عادی مدیریت به‌صورت فیزیکی حذف شوند.

## 46. مدیریت خطا

وب‌سایت عمومی و پنل مدیریت باید از موارد زیر پشتیبانی کنند:

### 46.1 HTTP 400

برای ورودی نامعتبر کلاینت/برنامه، در جایی که مرتبط است.

### 46.2 HTTP 403

هنگامی نمایش داده می‌شود که یک کاربر احرازهویت‌شده فاقد مجوز موردنیاز باشد.

### 46.3 HTTP 404

هنگامی نمایش داده می‌شود که یک منبع درخواستی وجود نداشته باشد یا به‌صورت عمومی قابل‌دسترسی نباشد.

### 46.4 HTTP 500

برای خطاهای غیرمنتظره سمت سرور نمایش داده می‌شود.

جزئیات استثنای داخلی، Stack Trace، خطاهای پایگاه‌داده و اسرار (Secrets) هرگز نباید به کاربران نهایی نمایش داده شوند.

تمام خطاهای غیرمنتظره باید با اطلاعات همبستگی (Correlation) مناسب لاگ شوند.

## 47. مشاهده‌پذیری (Observability)

سیستم باید موارد زیر را فراهم کند:

Grafana باید داشبوردهای یکپارچه برای مشاهده‌پذیری عملیاتی و کسب‌وکاری فراهم کند.

## 48. نیازمندی‌های ثبت لاگ

لاگ‌ها باید ساختاریافته باشند.

حداقل، لاگ‌های درخواست مرتبط باید شامل موارد زیر باشند:

- زمان (Timestamp).
- سطح (Level).
- پیام (Message).
- استثنا، در صورت وجود.
- شناسه ردیابی (Trace ID).
- شناسه Span، در صورت موجود بودن.
- شناسه کاربر، در صورت موجود بودن.
- متد HTTP.
- مسیر درخواست.
- کد وضعیت.
- مدت‌زمان.

مقادیر حساس نباید لاگ شوند.

سیستم نباید موارد زیر را لاگ کند:

- رمزهای عبور.
- مقادیر OTP در محیط Production.
- توکن‌های احراز هویت.
- اسرار مربوط به پرداخت.
- اطلاعات کامل حساس شخصی.

سرویس پیامک ساختگی فقط می‌تواند OTPها را در محیط‌های توسعه/تست لاگ کند.

## 52. نیازمندی‌های امنیتی

### 52.1 امنیت رمز عبور

رمزهای عبور باید با استفاده از یک مکانیزم هش کردن مدرن به‌صورت امن هش شوند.

رمزهای عبور به‌صورت متن ساده هرگز نباید ذخیره شوند.

### 52.2 امنیت احراز هویت

توکن‌ها/کوکی‌های احراز هویت باید:

- در برابر دستکاری محافظت شوند.
- در محیط Production از تنظیمات کوکی امن استفاده کنند.
- زمان انقضای مناسب داشته باشند.
- از خروج/باطل‌سازی بر اساس مکانیزم احراز هویت انتخابی پشتیبانی کنند.

### 52.3 مجوزدهی

تمام عملیات محافظت‌شده باید سمت سرور مجاز شوند.

پنهان کردن یک دکمه در رابط کاربری Admin هرگز نباید کافی برای مجوزدهی در نظر گرفته شود.

### 52.4 اعتبارسنجی ورودی

تمام ورودی‌های خارجی باید اعتبارسنجی شوند.

این شامل موارد زیر است:

- ورودی فرم.
- پارامترهای Query.
- پارامترهای Route.
- بارگذاری فایل.
- نتایج پرداخت.
- پاسخ‌های OAuth.

### 52.5 محتوای HTML

محتوای ویرایشگر HTML باید پاک‌سازی (Sanitize) شود.

### 52.6 بارگذاری فایل

پیوست‌ها باید بر اساس موارد زیر اعتبارسنجی شوند:

- پسوند.
- نوع محتوا، در صورت امکان.
- اندازه.
- تعداد.
- قواعد ذخیره‌سازی.

فایل‌های بارگذاری‌شده نباید به‌طور خودکار به محتوای قابل‌اجرا تبدیل شوند.

## 54. همزمانی (Concurrency)

عملیاتی که می‌توانند به‌صورت همزمان فعال شوند باید طوری طراحی شوند که از وضعیت ناسازگار جلوگیری شود.

نمونه‌های مهم:

- دو Callback پرداخت برای یک تراکنش یکسان.
- دو درخواست Checkout برای یک سبد خرید یکسان.
- درخواست‌های علاقه‌مندی تکراری.
- تخصیص همزمان مجوز به نقش.
- پردازش همزمان سفارش.
- استفاده همزمان از کوپن.
- رقابت انقضای سفارش در انتظار با نتیجه پرداخت.

محدودیت‌های یکتای پایگاه‌داده و Idempotency در سطح برنامه باید در جایی که لازم است با هم استفاده شوند.

## 59. Result Pattern

عملیات Application باید از یک Result Pattern استفاده کنند، نه استفاده از استثناها به‌عنوان مکانیزم عادی برای خطاهای کسب‌وکاری موردانتظار.

خطاهای موردانتظار می‌توانند شامل موارد زیر باشند:

- دوره یافت نشد.
- محدودیت سلسله‌مراتب دسته‌بندی رد شده.
- کاربر غیرفعال.
- مجوز رد شده.
- شماره تلفن الزامی.
- تخفیف نامعتبر.
- دوره برای فروش در دسترس نیست.
- دسترسی ناکافی به دوره.
- وضعیت پرداخت نامعتبر.

خطاهای غیرمنتظره زیرساختی/سیستمی همچنان باید از مدیریت استثنا و مدیریت خطای متمرکز استفاده کنند.

## 60. CQRS و MediatR

Commandها باید وضعیت را تغییر دهند.

Queryها باید داده را بدون تغییر وضعیت کسب‌وکاری بازیابی کنند.

MediatR باید به‌عنوان مکانیزم Dispatch برنامه برای Commandها و Queryها، در جایی که مرتبط است، استفاده شود.

دغدغه‌های میان‌بُرشی (Cross-Cutting) مانند:

- اعتبارسنجی.
- ثبت لاگ.
- اندازه‌گیری عملکرد.
- مدیریت تراکنش، در جایی که مرتبط است.

می‌توانند از طریق Pipeline Behaviorهای MediatR پیاده‌سازی شوند.

## 61. اعتبارسنجی

اعتبارسنجی باید در چند سطح وجود داشته باشد:

### Application

اعتبارسنجی کسب‌وکاری و اعتبارسنجی Command.

### Domain

Invariantهایی که همیشه باید برقرار باشند.

### پایگاه‌داده

محدودیت‌های نهایی یکپارچگی.

## 62. قواعد دسترسی عمومی

وب‌سایت عمومی باید فقط محتوا را بر اساس وضعیت آن در معرض دید قرار دهد.

نمونه‌ها:

```text
دوره:
    منتشرشده -> عمومی
    پیش‌نویس -> غیرعمومی
    پنهان    -> غیرعمومی

بلاگ:
    منتشرشده/نمایش-فعال -> عمومی
    در غیر این صورت      -> غیرعمومی
```

محتوای دوره پولی، به‌جز اپیزودهای صراحتاً رایگان، نیازمند مالکیت دوره است.

## 63. قواعد دسترسی دوره

یک کاربر می‌تواند به یک دوره دسترسی داشته باشد اگر:

```text
Course.IsFree = true
```

یا:

```text
کاربر مالک دوره است
```

یا، برای یک دوره پولی:

```text
Episode.IsFree = true
```

دسترسی پیش‌نمایش رایگان نباید مالکیت کل دوره را اعطا کند.

## 69. نیازمندی‌های غیرعملکردی

### 69.1 عملکرد (Performance)

برنامه باید:

- از I/O ناهمگام (Asynchronous) استفاده کند.
- از فراخوانی‌های Blocking خودداری کند.
- برای لیست‌های احتمالاً بزرگ Admin/عمومی از صفحه‌بندی (Pagination) استفاده کند.
- از کوئری‌های N+1 پایگاه‌داده خودداری کند.
- کوئری‌های کند پایگاه‌داده را پایش کند.
- درخواست‌های HTTP کند را پایش کند.

### 69.2 مقیاس‌پذیری (Scalability)

برنامه باید تا حد امکان در لایه وب‌سرور Stateless باقی بماند.

وضعیت Session/سبد خرید نباید به حافظه محلی سرور وابسته باشد.

Redis باید برای وضعیت موقت مشترک استفاده شود.

### 69.3 قابلیت نگهداری (Maintainability)

کدبیس باید:

- مرزهای Clean Architecture را رعایت کند.
- دغدغه‌های Domain، Application، Infrastructure و Presentation را جدا کند.
- از تزریق وابستگی استفاده کند.
- برای قواعد مهم کسب‌وکاری از تست‌های خودکار استفاده کند.
- از تکرار منطق کسب‌وکاری خودداری کند.

### 69.4 قابلیت‌اطمینان (Reliability)

عملیات حیاتی باید در جایی که امکان تکرار درخواست وجود دارد، Idempotent باشند.

پردازش پرداخت به‌طور خاص باید Idempotent باشد.

### 69.5 امنیت

برنامه باید از پیش‌فرض‌های امن برای موارد زیر پیروی کند:

- احراز هویت.
- مجوزدهی.
- ذخیره‌سازی رمز عبور.
- بارگذاری فایل.
- رندر HTML.
- اسرار (Secrets).
- ثبت لاگ.
- اعتبارسنجی ورودی.

## 71. معیارهای پذیرش — جریان‌های اصلی

### 71.1 خرید دوره

موارد زیر باید صادق باشند:

1. یک کاربر می‌تواند دوره‌های منتشرشده را مرور کند.
2. یک دوره پولی می‌تواند به سبد خرید Redis اضافه شود.
3. فرآیند پرداخت نیازمند شماره تلفن است.
4. سرور قیمت سفارش را محاسبه می‌کند.
5. یک سفارش ایجاد می‌شود.
6. یک رکورد پرداخت ایجاد می‌شود.
7. یک پرداخت موفق، سفارش را به `Paid` تغییر می‌دهد.
8. کاربر دسترسی به دوره را دریافت می‌کند.
9. یک فاکتور در دسترس قرار می‌گیرد.
10. پردازش مجدد نتیجه یکسان پرداخت، دسترسی یا وضعیت فاکتور را تکراری نمی‌کند.

### 71.2 نقش‌های پویا

موارد زیر باید صادق باشند:

1. یک مدیر مجاز می‌تواند یک نقش ایجاد کند.
2. مدیر می‌تواند نقش را ویرایش کند.
3. مدیر می‌تواند مجوزها را تخصیص دهد.
4. مدیر می‌تواند نقش را به کاربران تخصیص دهد.
5. کاربر مجوزهای نقش را دریافت می‌کند.
6. مجوزدهی بر پایه کلیدهای مجوز است.
7. مدیر می‌تواند نقش را در صورتی که به‌عنوان نقش سیستمی محافظت‌نشده باشد حذف کند.

### 71.3 ساختار دوره

موارد زیر باید صادق باشند:

1. یک دوره می‌تواند شامل چندین بخش باشد.
2. یک بخش می‌تواند شامل چندین اپیزود باشد.
3. بخش‌ها مرتب‌شده هستند.
4. اپیزودها مرتب‌شده هستند.
5. مدت‌زمان اپیزود در دسترس است.
6. یک دوره پولی می‌تواند شامل چندین اپیزود رایگان باشد.
7. اپیزودهای غیررایگان نیازمند مالکیت دوره هستند.

### 71.4 پرداخت با کوپن

موارد زیر باید صادق باشند:

1. یک کد کوپن می‌تواند روی سبد خریدی که شامل دوره‌های پولی است اعمال شود.
2. سرور تخفیف کوپن و مبلغ قابل پرداخت را محاسبه می‌کند؛ مبالغ ارائه‌شده از سمت کلاینت نادیده گرفته می‌شوند.
3. یک کد ناشناخته، غیرفعال، منقضی، شروع‌نشده، تمام‌شده یا کمتر از حداقل مبلغ با یک پیام رد می‌شود.
4. کاربر می‌تواند کوپن اعمال‌شده را از سبد خرید حذف کند.
5. کوپن هنگام ایجاد سفارش مجدداً اعتبارسنجی می‌شود و یک کوپن نامعتبر مانع ایجاد سفارش می‌شود.
6. سفارش ارجاع کوپن و Snapshot تخفیف کوپن را ذخیره می‌کند و مبلغ پرداخت برابر مبلغ قابل پرداخت است.
7. پرداخت‌های هم‌زمان نمی‌توانند `UsedCount` را از `UsageLimit` بالاتر ببرند.
8. یک سفارش `Failed` یا `Cancelled` استفاده رزروشده کوپن خود را دقیقاً یک‌بار آزاد می‌کند.
9. فاکتور یک سفارش پرداخت‌شده کد کوپن و تخفیف کوپن را نمایش می‌دهد.
10. پردازش مجدد نتیجه یکسان پرداخت، `UsedCount` را تغییر نمی‌دهد.
11. یک سفارش `Pending` که از زمان انقضای خود می‌گذرد لغو می‌شود و استفاده رزروشده کوپن آن آزاد می‌شود.
12. نتیجه پرداخت موفقی که پس از انقضا برسد ثبت و برای بررسی علامت‌گذاری می‌شود و به‌صورت خودکار دسترسی اعطا نمی‌کند.
13. یک مدیر می‌تواند کوپن‌ها را ایجاد، ویرایش، غیرفعال و حذف نرم کند و نمی‌تواند مقدار نامعتبر یا سقف استفاده کمتر از میزان استفاده فعلی تنظیم کند.

## 72. خلاصه قواعد کسب‌وکاری صریح

قواعد زیر الزامی هستند:

1. سلسله‌مراتب دسته‌بندی نمی‌تواند از سه سطح فراتر رود.
2. اسلاگ‌های دوره یکتا هستند.
3. اسلاگ‌های بلاگ یکتا هستند.
4. شماره‌های تلفن در صورت وجود یکتا هستند.
5. ایمیل‌ها در صورت وجود یکتا هستند.
6. رمزهای عبور هرگز به‌صورت متن ساده ذخیره نمی‌شوند.
7. نقش‌ها پویا هستند.
8. مجوزها پویا هستند.
9. نقش‌ها مجوز دریافت می‌کنند.
10. مجوزدهی از مجوزها استفاده می‌کند، نه نام‌های نقش Hard-code شده.
11. نقش‌ها/مجوزهای سیستمی در برابر تغییرات مخرب محافظت می‌شوند.
12. سبدهای خرید در Redis ذخیره می‌شوند.
13. قیمت‌های سفارش تصویر لحظه‌ای (Snapshot) می‌شوند.
14. پردازش پرداخت Idempotent است.
15. پرداخت موفق دسترسی به دوره را اعطا می‌کند.
16. اپیزودهای رایگان دوره‌های پولی بدون خرید کل دوره قابل‌مشاهده هستند.
17. اپیزودهای غیررایگان پولی نیازمند مالکیت دوره هستند.
18. کاربران احرازهویت‌شده از طریق گوگل باید پیش از پرداخت شماره تلفن ارائه دهند.
19. یکپارچه‌سازی واقعی سرویس پیامک الزامی نیست.
20. یکپارچه‌سازی واقعی ارائه‌دهنده پرداخت الزامی نیست.
21. پیوست‌های دوره دارای محدودیت تعداد و اندازه هستند.
22. محدودیت‌های پیوست پیکربندی‌محور هستند.
23. محتوای عمومی باید وضعیت نمایش خود را رعایت کند.
24. عملیات مدیریتی باید توسط مجوز محافظت شوند.
25. خطاهای غیرمنتظره سرور باید لاگ شوند و نباید جزئیات حساس را فاش کنند.
26. لاگ‌ها، ردیابی‌ها و متریک‌ها باید از طریق زیرساخت مشاهده‌پذیری در دسترس باشند.
27. Grafana باید داشبوردهای مشاهده‌پذیری یکپارچه فراهم کند.
28. انتزاع‌های Repository و Unit of Work باید برای دسترسی به Persistence استفاده شوند.
29. Controllerها و Razor Pageها نباید مستقیماً به `DbContext` مربوط به EF Core دسترسی داشته باشند.
30. منطق کسب‌وکاری متعلق به لایه‌های Application/Domain است.

## 74. اصول پیاده‌سازی

پیاده‌سازی باید از این اصول پیروی کند:

- از ASP.NET Core Identity استفاده نکنید.
- نقش‌ها را به‌عنوان مکانیزم مجوزدهی Hard-code نکنید.
- مجوزها را در منطق ارائه (Presentation) Hard-code نکنید.
- سبدهای خرید را به‌عنوان وضعیت اصلی سبد در PostgreSQL ذخیره نکنید.
- به قیمت‌های سمت کلاینت اعتماد نکنید.
- رمزهای عبور را به‌صورت متن ساده ذخیره نکنید.
- استثناهای داخلی را به کاربران فاش نکنید.
- HTML پاک‌سازی‌نشده را نمایش ندهید.
- عمق دسته‌بندی فراتر از سه سطح را مجاز نکنید.
- قواعد کسب‌وکاری را بین MVC، Razor Pages و سرویس‌های Application تکرار نکنید.
- `DbContext` را خارج از Infrastructure افشا نکنید.
- از یک Repository عمومی صرفاً به‌خاطر داشتن یک Repository استفاده نکنید.
- از Unit of Work برای مرزهای پایدار و سازگار Persistence استفاده کنید.
- پردازش نتیجه پرداخت را Idempotent کنید.
- یکپارچه‌سازی‌های خارجی را پشت انتزاع نگه دارید.
- پیکربندی و اسرار را خارج از کد منبع نگه دارید.
- قواعد صریح Domain/Application را به رفتار ضمنی ترجیح دهید.

## 75. تعریف انجام‌شده (Definition of Done)

یک ویژگی زمانی کامل در نظر گرفته می‌شود که:

1. مدل Domain آن در جایی که لازم است پیاده‌سازی شده باشد.
2. Command/Query مربوط در Application پیاده‌سازی شده باشد.
3. اعتبارسنجی پیاده‌سازی شده باشد.
4. مجوزدهی در جایی که لازم است پیاده‌سازی شده باشد.
5. Persistence از طریق مرز Repository/Unit of Work پیاده‌سازی شده باشد.
6. محدودیت‌های موردنیاز پایگاه‌داده وجود داشته باشند.
7. رابط کاربری وب‌سایت عمومی یا پنل مدیریت به‌صورت مقتضی پیاده‌سازی شده باشد.
8. مدیریت خطا پیاده‌سازی شده باشد.
9. لاگ‌ها و تله‌متری مرتبط وجود داشته باشند.
10. تست‌های خودکار، قواعد کسب‌وکاری مهم را پوشش دهند.
11. ویژگی از مرزهای معماری عبور نکند.
12. هیچ اطلاعات حساسی از طریق لاگ‌ها یا رابط کاربری فاش نشود.
13. ویژگی از قواعد کسب‌وکاری تعریف‌شده در این سند پیروی کند.

## 77. راهبرد حذف داده (Data Deletion Strategy)

برنامه باید به‌صورت پیش‌فرض از **Soft Delete** استفاده کند.

حذف فیزیکی (Physical Delete) نباید برای موجودیت‌های عادی برنامه استفاده شود، مگر در صورتی که یک نیازمندی فنی یا کسب‌وکاری مشخص صراحتاً حذف دائمی را الزامی کند.

### 77.1 فیلدهای Soft Delete

موجودیت‌هایی که از حذف پشتیبانی می‌کنند باید شامل موارد زیر باشند:

| فیلد | الزام |
|---|---|
| IsDeleted | بولین الزامی |
| DeletedAt | زمان (Nullable) |
| DeletedBy | شناسه کاربر (Nullable) |

در جایی که مناسب باشد، موجودیت‌ها باید همچنین شامل موارد زیر باشند:

| فیلد | الزام |
|---|---|
| CreatedBy | شناسه کاربر، Nullable/الزامی بسته به چرخه حیات موجودیت |
| UpdatedBy | شناسه کاربر، Nullable/الزامی بسته به چرخه حیات موجودیت |

فیلدهای حسابرسی (Audit) باید معمولاً شامل موارد زیر باشند:

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
IsDeleted
DeletedAt
DeletedBy
```

### 77.2 رفتار پیش‌فرض کوئری‌ها

موجودیت‌های Soft-Delete‌شده نباید توسط کوئری‌های عادی برنامه بازگردانده شوند.

لایه Infrastructure باید این رفتار را در جایی که مناسب است از طریق Global Query Filter‌های EF Core پیاده‌سازی کند.

کوئری‌ای که صراحتاً به رکوردهای حذف‌شده نیاز دارد باید به‌صورت آشکار وارد این رفتار شود (Opt-in).

### 77.3 حذف دائمی

حذف فیزیکی (Hard Delete) فقط برای موجودیت‌هایی مجاز است که حذف دائمی آن‌ها صراحتاً توجیه‌پذیر باشد.

نمونه‌ها می‌توانند شامل موارد زیر باشند:

* رکوردهای فنی موقت.
* رکوردهای مصرفی توسعه/تست.
* داده‌ای که طبق یک قاعده مستندشده کسب‌وکاری/حریم‌خصوصی صراحتاً باید به‌طور دائمی حذف شود.

رکوردهای مالی مانند پرداخت‌های موفق، سفارش‌های پرداخت‌شده و فاکتورهای صادرشده نباید از طریق عملیات مدیریتی عادی به‌صورت فیزیکی حذف شوند.

## 78. فیلدهای حسابرسی (Audit Fields)

برنامه باید اطلاعات حسابرسی ایجاد و تغییر را نگهداری کند.

حداقل، موجودیت‌های کسب‌وکاری‌ای که نیازمند قابلیت حسابرسی هستند باید شامل موارد زیر باشند:

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
```

در جایی که یک عملیات نمایانگر حذف باشد:

```text
DeletedAt
DeletedBy
IsDeleted
```

### 78.1 CreatedBy

`CreatedBy` باید به کاربری اشاره کند که مسئول ایجاد رکورد است، در جایی که عملیات توسط یک کاربر احرازهویت‌شده انجام می‌شود.

برای رکوردهای تولیدشده توسط سیستم، می‌توان از یک هویت سیستمی مستندشده یا مقدار Nullable استفاده کرد.

### 78.2 UpdatedBy

`UpdatedBy` باید به کاربری اشاره کند که مسئول آخرین تغییر است.

### 78.3 DeletedBy

`DeletedBy` باید به کاربری اشاره کند که عملیات Soft-Delete را انجام داده است.

برنامه نباید به مقادیر ارسالی از سمت کلاینت برای این فیلدها اعتماد کند.

اطلاعات حسابرسی باید توسط لایه سرور/Application/Infrastructure پر شوند.

## 79. معماری Repository

معماری Repository باید مسئولیت‌های **خواندن (Read)** و **نوشتن (Write)** را صراحتاً از هم جدا کند.

یک Repository عمومی و واحد نباید استفاده شود.

برنامه باید از Repositoryهای صریح که حول نیازمندی‌های واقعی کسب‌وکار طراحی شده‌اند استفاده کند.

### 79.1 Repositoryهای نوشتن (Write)

Repositoryهای نوشتن باید مسئول عملیاتی باشند که وضعیت برنامه را تغییر می‌دهند.

نمونه‌ها:

```text
ICourseWriteRepository
ICategoryWriteRepository
IUserWriteRepository
IRoleWriteRepository
IPermissionWriteRepository
IOrderWriteRepository
IPaymentWriteRepository
IInvoiceWriteRepository
```

Repositoryهای نوشتن باید از **Entity Framework Core** استفاده کنند.

EF Core باید مسئول موارد زیر باشد:

* درج (Insert).
* به‌روزرسانی (Update).
* حذف نرم (Soft Delete).
* تغییرات روابط.
* ردیابی تغییرات (Change Tracking) در جایی که لازم است.
* پایداری تراکنشی.

### 79.2 Repositoryهای خواندن (Read)

Repositoryهای خواندن باید مسئول بازیابی داده باشند.

نمونه‌ها:

```text
ICourseReadRepository
ICategoryReadRepository
IUserReadRepository
IRoleReadRepository
IPermissionReadRepository
IOrderReadRepository
IPaymentReadRepository
IInvoiceReadRepository
```

Repositoryهای خواندن باید از **Dapper** استفاده کنند.

Dapper باید برای کوئری‌های خواندن‌محور، در جایی که Projection مستقیم SQL بازیابی داده ساده‌تر یا کارآمدتری فراهم می‌کند، ترجیح داده شود.

Repositoryهای خواندن باید به‌جای افشای غیرضروری موجودیت‌های EF Core، DTO/مدل‌های خواندن اختصاصی برنامه را بازگردانند.

### 79.3 عدم استفاده از Repository عمومی

برنامه نباید یک Repository عمومی مانند موارد زیر را صرفاً برای ارائه عملیات CRUD پیاده‌سازی کند:

```csharp
IGenericRepository<T>
```

Repositoryها باید صریح و مبتنی بر Use-Case باشند.

برای مثال:

```csharp
public interface ICourseReadRepository
{
    Task<CourseDetailsDto?> GetDetailsAsync(
        Guid courseId,
        CancellationToken cancellationToken);
}
```

و:

```csharp
public interface ICourseWriteRepository
{
    Task AddAsync(
        Course course,
        CancellationToken cancellationToken);

    Task<Course?> GetForUpdateAsync(
        Guid courseId,
        CancellationToken cancellationToken);
}
```

انتزاع Repository باید نمایانگر عملیات معنادار برنامه باشد، نه صرفاً یک پوشش (Wrapper) روی APIهای پایگاه‌داده.

## 80. قواعد پایداری داده Read/Write

پیاده‌سازی Persistence باید از قواعد زیر پیروی کند:

```text
                    Application
                         |
              +----------+----------+
              |                     |
              v                     v
       Read Repositories     Write Repositories
              |                     |
              v                     v
           Dapper                EF Core
              |                     |
              +----------+----------+
                         |
                     PostgreSQL
```

### 80.1 عملیات خواندن

کوئری‌ها باید:

* از Dapper از طریق Repositoryهای خواندن استفاده کنند.
* Projectionهای صریح SQL را ترجیح دهند.
* DTO/مدل‌های خواندن را بازگردانند.
* از بارگذاری کامل گراف Aggregate در جایی که فقط یک Projection لازم است خودداری کنند.
* از Pagination برای نتایج بزرگ پشتیبانی کنند.

### 80.2 عملیات نوشتن

دستورها (Commands) باید:

* از EF Core از طریق Repositoryهای نوشتن استفاده کنند.
* قواعد کسب‌وکاری را در لایه Application/Domain اعمال کنند.
* در جایی که چندین تغییر باید به‌صورت سازگار ذخیره شوند از Unit of Work استفاده کنند.
* در جایی که Atomicity لازم است از تراکنش استفاده کنند.

### 80.3 مرز DbContext

`DbContext` باید یک جزئیات پیاده‌سازی Infrastructure باقی بماند.

Controllerها، Razor Pageها و Handlerهای Application نباید مستقیماً به `DbContext` دسترسی داشته باشند.

## 81. مدل قیمت‌گذاری محصول

در جایی که Domain حاوی مفهوم `Product` باشد، مدل قیمت‌گذاری باید تغییر کند.

سیستم نباید یک ستون جداگانه `IsFree` را در پایگاه‌داده ذخیره کند.

در عوض:

```text
Price = null
```

نمایانگر یک محصول رایگان است.

یک قیمت غیر-null نمایانگر یک محصول پولی است.

### 81.1 فیلدهای محصول

مدل باید از موارد زیر استفاده کند:

```csharp
public decimal? Price { get; private set; }
```

به‌جای الزام موارد زیر:

```csharp
public bool IsFree { get; set; }
```

### 81.2 خصیصه IsFree

مدل Domain می‌تواند موارد زیر را افشا کند:

```csharp
public bool IsFree => Price is null;
```

`IsFree` یک خصیصه مشتق‌شده (Derived) از Domain است و نباید در پایگاه‌داده ذخیره شود.

از نظر مفهومی:

```text
Price = null
    => IsFree = true

Price > 0
    => IsFree = false
```

### 81.3 قواعد قیمت‌گذاری

محصولی با:

```text
Price = null
```

رایگان است.

محصولی با:

```text
Price > 0
```

پولی است.

محصولات پولی با قیمت صفر نباید برای نمایش محصولات رایگان استفاده شوند، مگر آنکه یک نیازمندی کسب‌وکاری مستندشده جداگانه صراحتاً چنین وضعیتی را معرفی کند.

### 81.4 اعمال روی دوره (Course)

از آنجا که `Course` در حال حاضر نمایانگر محصول آموزشی قابل‌خرید است، همین قاعده قیمت‌گذاری باید برای Course اعمال شود، مگر آنکه یک Aggregate جداگانه `Product` معرفی شود.

بنابراین، نیازمندی قبلی:

```text
IsFree = الزامی
Price = الزامی برای دوره‌های پولی
```

باید با موارد زیر جایگزین شود:

```text
Price = Nullable
IsFree = خصیصه مشتق‌شده و ذخیره‌نشده
```

قاعده دسترسی به شکل زیر تبدیل می‌شود:

```text
Course.Price == null
    => دوره رایگان است

Course.Price != null
    => دوره پولی است
```

همین قاعده باید در جایی که مرتبط است برای رفتار پیش‌نمایش رایگان در سطح اپیزود نیز اعمال شود.

## 82. احراز هویت مبتنی بر Cookie

احراز هویت باید **مبتنی بر Cookie** باشد.

برنامه نباید از توکن‌های JWT Bearer به‌عنوان مکانیزم اصلی احراز هویت مرورگر استفاده کند.

### 82.1 مکانیزم احراز هویت

پس از احراز هویت موفق، سرور باید یک Cookie احراز هویت صادر کند.

مرورگر باید Cookie احراز هویت را به‌طور خودکار همراه درخواست‌های بعدی ارسال کند.

از نظر مفهومی:

```text
ورود / تایید OTP
        |
        v
سرور هویت را اعتبارسنجی می‌کند
        |
        v
Cookie احراز هویت
        |
        v
درخواست‌های احرازهویت‌شده مرورگر
```

### 82.2 امنیت Cookie

Cookieهای احراز هویت باید از تنظیمات امن Production استفاده کنند، از جمله در جایی که مناسب است:

```text
HttpOnly = true
Secure = true
SameSite = مقدار محدودکننده مناسب
```

رفتار دقیق SameSite باید متناسب با نیازمندی‌های احراز هویت و ورود خارجی برنامه انتخاب شود.

### 82.3 وضعیت احراز هویت

هویت کاربر احرازهویت‌شده باید از طریق Claimها درون Cookie احراز هویت نمایش داده شود.

Cookie نباید به‌صورت غیرضروری حاوی اطلاعات حساس باشد.

رمزهای عبور، OTPها، اسرار پرداخت و سایر مقادیر حساس هرگز نباید درون Cookieهای احراز هویت ذخیره شوند.

### 82.4 خروج (Logout)

خروج باید Session/Cookie احرازهویت‌شده را طبق مکانیزم پیکربندی‌شده احراز هویت Cookie باطل کند.

### 82.5 احراز هویت گوگل

احراز هویت گوگل باید همچنان از جریان مناسب OAuth/OpenID Connect خارجی استفاده کند.

پس از احراز هویت خارجی موفق، برنامه باید Session احرازهویت‌شده مبتنی بر Cookie محلی خود را برقرار کند.

توکن‌های دسترسی/هویت گوگل نباید به‌عنوان مکانیزم عادی احراز هویت مرورگر برنامه استفاده شوند.

## 83. سرویس شبیه‌سازی درگاه پیامک (SMS)

قابلیت پیامک ساختگی (Fake) باید به‌عنوان یک **پروژه API جداگانه** در کنار برنامه اصلی وایلند پیاده‌سازی شود.

این سرویس باید رفتار یک API واقعی ارائه‌دهنده پیامک را شبیه‌سازی کند.

هدف این است که برنامه اصلی بتواند بدون نیاز به یک ارائه‌دهنده واقعی پیامک، از طریق یک مرز HTTP واقع‌گرایانه با یک API پیامک ارتباط برقرار کند.

### 83.1 ساختار پروژه

راه‌حل (Solution) باید یک پروژه جداگانه، برای مثال به شکل زیر، داشته باشد:

```text
src/
│
├── Project.Domain/
├── Project.Application/
├── Project.Infrastructure/
├── Project.Web/
├── Project.Admin/
│
└── Project.Sms/
```

`Project.Sms` باید یک اپلیکیشن مستقل ASP.NET Core Web API باشد.

این پروژه نباید حاوی منطق کسب‌وکاری وایلند باشد.

### 83.2 API پیامک

این API باید Endpointهایی مشابه رابطی که معمولاً توسط یک پنل/ارائه‌دهنده پیامک فراهم می‌شود ارائه دهد.

حداقل:

```text
POST /api/v1/sms/send
```

درخواست باید حاوی اطلاعاتی معادل موارد زیر باشد:

```json
{
  "to": "09120000000",
  "message": "Your verification code is 123456"
}
```

پاسخ باید حاوی نتیجه‌ای شبیه ارائه‌دهنده واقعی باشد:

```json
{
  "success": true,
  "messageId": "..."
}
```

قرارداد دقیق درخواست/پاسخ باید مستند و نسخه‌بندی شود.

### 83.3 طراحی ارائه‌دهنده-محور

برنامه وایلند باید با یک انتزاع مانند زیر ارتباط برقرار کند:

```csharp
public interface ISmsService
{
    Task<SendSmsResult> SendAsync(
        string phoneNumber,
        string message,
        CancellationToken cancellationToken);
}
```

پیاده‌سازی Infrastructure باید API پیامک جداگانه را از طریق HTTP فراخوانی کند.

بنابراین:

```text
برنامه وایلند
        |
        v
ISmsService
        |
        v
HTTP Client
        |
        v
Project.Sms API
        |
        v
ذخیره‌سازی In-Memory
```

این کار برنامه اصلی را از پیاده‌سازی ارائه‌دهنده ساختگی مستقل نگه می‌دارد.

### 83.4 پایگاه‌داده In-Memory

API پیامک باید برای پیاده‌سازی اول از یک فروشگاه داده In-Memory استفاده کند.

این سرویس باید حداقل موارد زیر را ذخیره کند:

```text
درخواست‌های پیامک
پیام‌های پیامک
گیرنده
پیام
وضعیت
شناسه پیام (MessageId)
CreatedAt
SentAt
```

پایداری در PostgreSQL برای سرویس شبیه‌سازی پیامک الزامی نیست.

این سرویس باید بدون نیاز به مایگریشن پایگاه‌داده قابل راه‌اندازی مجدد باشد.

### 83.5 داشبورد پیامک

سرویس پیامک باید یک صفحه مدیریتی/داشبورد ساده مبتنی بر HTML فراهم کند.

داشبورد باید به توسعه‌دهندگان امکان بازرسی آسان موارد زیر را بدهد:

* درخواست‌های ورودی API پیامک.
* شماره‌های تلفن گیرنده.
* محتوای پیام‌ها.
* شناسه‌های پیام تولیدشده.
* وضعیت پیامک.
* زمان‌بندی درخواست‌ها.
* زمان‌بندی ارسال.

نمونه:

```text
شبیه‌ساز پیامک
-------------------------------------------------
شناسه پیام | گیرنده | پیام | وضعیت | تاریخ
-------------------------------------------------
12345      | 0912...   | OTP ... | ارسال‌شده   | ...
12346      | 0913...   | OTP ... | ارسال‌شده   | ...
-------------------------------------------------
```

این داشبورد برای توسعه/تست در نظر گرفته شده است و نیازی نیست یک سیستم مدیریتی در سطح Production باشد.

### 83.6 نیازمندی‌های داشبورد پیامک

داشبورد باید از موارد زیر پشتیبانی کند:

* فهرست درخواست‌های پیامک.
* مشاهده یک درخواست پیامک منفرد.
* فیلترکردن ابتدایی بر اساس گیرنده/وضعیت.
* نمایش زمان درخواست.
* نمایش وضعیت پیام.
* نمایش شناسه پیام.

داشبورد می‌تواند از Razor Pages یا MVC استفاده کند.

### 83.7 جایگزینی ارائه‌دهنده واقعی

سرویس ساختگی پیامک باید بدون تغییر منطق کسب‌وکاری لایه Application قابل جایگزینی با یک پیاده‌سازی ارائه‌دهنده واقعی باشد.

نمونه‌های پیاده‌سازی آینده:

```text

KavenegarSmsService
OtherProviderSmsService
```

قرارداد HTTP اختصاصی ارائه‌دهنده باید خارج از لایه Domain باقی بماند.

## 85. تولید و گزارش‌گیری فاکتور

پیاده‌سازی تولید فاکتور باید جدا از مدل Domain مالی ارزیابی شود.

موجودیت Domain مربوط به Invoice باید نمایانگر تصویر لحظه‌ای مالی (Financial Snapshot) باشد.

یک کتابخانه گزارش‌گیری/PDF باید مسئول رندر آن Snapshot به یک سند باشد.

سیستم نباید دغدغه‌های PDF/گزارش‌گیری را مستقیماً درون لایه Domain قرار دهد.

معماری:

```text
سفارش / پرداخت
      |
      v
مدل Domain فاکتور
      |
      v
سرویس Application فاکتور
      |
      v
تولیدکننده گزارش فاکتور
      |
      v
فاکتور PDF / قابل‌چاپ
```

### 85.1 کتابخانه‌های کاندید

فناوری‌های گزارش‌گیری/PDF زیر در دات‌نت بررسی شدند:

**Stimulsoft Reports**

Stimulsoft Reports.WEB از ASP.NET، ASP.NET Core، MVC، Razor Pages و طراحی/مشاهده گزارش مبتنی بر مرورگر پشتیبانی می‌کند. مستندات آن همچنین صراحتاً گزارش‌های فاکتور و خروجی‌گرفتن گزارش‌ها به PDF را پوشش می‌دهد.

Stimulsoft همچنین یک پکیج رسمی دات‌نت و نمونه‌هایی برای بارگذاری، رندر و خروجی‌گرفتن گزارش به PDF ارائه می‌دهد.

این کتابخانه همچنین می‌تواند گزارش‌های رندرشده را از طریق یک Endpoint وب API افشا کند، که در صورت نیاز به ارائه تولید فاکتور به‌عنوان یک سرویس مستقل در آینده، مرتبط خواهد بود.

Stimulsoft علاوه‌بر این، پشتیبانی از فرمت‌های مرتبط با فاکتور الکترونیک مانند ZUGFeRD و Factur-X را مستند کرده است.

**QuestPDF**

QuestPDF یک کتابخانه تولید PDF در سی‌شارپ با یک سیستم چیدمان (Layout) مبتنی بر کامپوننت است.

مستندات رسمی آن یک آموزش اختصاصی برای فاکتور ارائه می‌دهد و جداسازی مدل‌های فاکتور/سند از منطق رندر را توصیه می‌کند.

این کتابخانه می‌تواند PDF را مستقیماً به فایل، آرایه بایت یا Stream تولید کند.

**FastReport .NET**

FastReport .NET قابلیت‌های گزارش‌گیری و خروجی PDF را فراهم می‌کند. مستندات رسمی آن شامل یک API خروجی PDF و مستندات جامع گزارش‌گیری دات‌نت است.

### 85.2 معیارهای انتخاب

راه‌حل فاکتور/گزارش‌گیری باید در برابر موارد زیر ارزیابی شود:

### 85.3 ارزیابی پیشنهادی

کاندید فعلی ترجیح‌داده‌شده عبارت است از:

**Stimulsoft Reports.WEB**

دلیل این انتخاب آن است که پروژه از قبل دارای معماری وب ASP.NET Core است و این محصول به‌طور خاص گزارش‌گیری، طراحی گزارش، مشاهده در مرورگر، خروجی PDF و اسناد سبک فاکتور را برای ASP.NET/ASP.NET Core هدف قرار داده است.

با این حال، انتخاب نهایی کتابخانه باید پس از بررسی موارد زیر انجام شود:

* هزینه مجوز.
* رندر فاکتور فارسی/RTL.
* فونت‌های موردنیاز.
* نیازمندی‌های استقرار.
* روند کار قالب گزارش.
* کیفیت خروجی PDF.
* فرمت‌های خروجی موردنیاز.
* نگهداری بلندمدت.
* نیازمندی‌های استفاده تجاری.

QuestPDF باید یک جایگزین قدرتمند باقی بماند، برای زمانی که تیم مدلی مبتنی بر کد برای تولید PDF را به‌جای یک طراح گزارش بصری ترجیح می‌دهد. آموزش رسمی فاکتور آن، این کتابخانه را به‌طور خاص برای این کاربرد مرتبط می‌سازد.

### 85.4 مرز رندر فاکتور

برنامه باید یک انتزاع مانند زیر تعریف کند:

```csharp
public interface IInvoiceRenderer
{
    Task<byte[]> RenderPdfAsync(
        InvoiceDocument document,
        CancellationToken cancellationToken);
}
```

لایه Domain نباید به Stimulsoft، QuestPDF، FastReport یا هر کتابخانه گزارش‌گیری دیگری ارجاع دهد.

لایه Infrastructure باید حاوی پیاده‌سازی مشخص (Concrete) باشد.

برای مثال:

```text
IInvoiceRenderer
       |
       +---- StimulsoftInvoiceRenderer
```

این پیاده‌سازی بعداً می‌تواند بدون تغییر مدل Domain مربوط به Invoice جایگزین شود.

## 86. مدل داده فاکتور

فاکتور باید تصویر لحظه‌ای مالی (Financial Snapshot) را در زمان صدور خود حفظ کند.

فاکتور نباید قیمت‌های تاریخی را با کوئری‌گرفتن از موجودیت فعلی Course محاسبه کند.

یک فاکتور باید اطلاعات مالی غیرقابل‌تغییر (Immutable) اختصاصی خود را داشته باشد.

حداقل:

```text
شماره فاکتور
تاریخ فاکتور
مشتری
تلفن مشتری
ایمیل مشتری
مرجع سفارش
مرجع پرداخت
اقلام
تعداد
قیمت واحد
تخفیف
کد کوپن (در صورت استفاده)
تخفیف کوپن (در صورت استفاده)
مالیات در جایی که کاربرد دارد
جمع جزء
مبلغ نهایی
وضعیت پرداخت
```

هر قلم فاکتور باید Snapshot قیمت اختصاصی خود را داشته باشد.

برای مثال:

```text
InvoiceItem
    نام محصول/دوره
    تعداد
    UnitPrice
    تخفیف
    TotalPrice
```

تغییرات قیمت دوره پس از صدور فاکتور نباید فاکتور را تغییر دهد.

## 87. غیرقابل‌تغییر بودن فاکتور (Invoice Immutability)

پس از نهایی‌شدن/صدور یک فاکتور، محتوای مالی آن نباید از طریق عملیات معمول CRUD تغییر کند.

اصلاحات باید در صورت معرفی چنین فرآیندی در آینده، از طریق یک فرآیند صریح و مستندشده انجام شوند.

سیستم نباید اطلاعات تاریخی فاکتور را در موارد زیر به‌صورت خاموش (Silently) رونویسی کند:

* تغییر قیمت دوره‌ها.
* تغییر اطلاعات کاربر.
* تغییر تخفیف‌ها.
* تغییر نام محصولات.
* تغییر اطلاعات پرداخت.

## 90. قواعد به‌روزشده قیمت‌گذاری دوره

نیازمندی‌های قبلی قیمت‌گذاری دوره باید با موارد زیر جایگزین شوند:

```text
Course.Price : decimal?
```

و:

```csharp
public bool IsFree => Price is null;
```

`IsFree` نباید ذخیره (Persist) شود.

بنابراین:

```text
Price == null
    => دوره رایگان

Price != null
    => دوره پولی
```

برنامه باید این قاعده را به‌طور یکپارچه در موارد زیر استفاده کند:

* فهرست دوره‌ها.
* جزئیات دوره.
* سبد خرید.
* پرداخت (Checkout).
* ایجاد سفارش.
* دسترسی به دوره.
* تولید فاکتور.
* پنل مدیریت.

## 91. نیازمندی‌های به‌روزشده حسابرسی (Audit)

فیلدهای زیر باید به‌عنوان فیلدهای استاندارد حسابرسی در نظر گرفته شوند:

```text
CreatedAt
CreatedBy
UpdatedAt
UpdatedBy
IsDeleted
DeletedAt
DeletedBy
```

هر فیلد لزوماً برای هر موجودیت الزامی نیست، اما تمام موجودیت‌های پایدار کسب‌وکاری باید صراحتاً مشخص کنند کدام فیلدهای حسابرسی برای آن‌ها کاربرد دارد.

برای موجودیت‌های شرکت‌کننده در مجوزدهی، عملیات مالی، مدیریت محتوا و عملیات مدیریتی، قابلیت حسابرسی باید الزامی در نظر گرفته شود.

## 92. خلاصه به‌روزشده قواعد کسب‌وکاری صریح

قواعد زیر الزامی هستند و بر نیازمندی‌های قبلی متعارض اولویت دارند:

1. Soft Delete راهبرد پیش‌فرض حذف است.
2. Hard Delete فقط برای استثناهای صراحتاً مستندشده مجاز است.
3. موجودیت‌های Soft-Deletable باید در جایی که کاربرد دارد شامل `IsDeleted`، `DeletedAt` و `DeletedBy` باشند.
4. موجودیت‌های کسب‌وکاری باید در جایی که کاربرد دارد شامل `CreatedAt`، `CreatedBy`، `UpdatedAt` و `UpdatedBy` باشند.
5. کوئری‌های عادی باید رکوردهای Soft-Delete‌شده را حذف کنند.
6. Repositoryهای خواندن و نوشتن باید جدا شوند.
7. Repositoryهای خواندن باید از Dapper استفاده کنند.
8. Repositoryهای نوشتن باید از Entity Framework Core استفاده کنند.
9. یک Repository عمومی نباید پیاده‌سازی شود.
10. `DbContext` باید درون Infrastructure باقی بماند.
11. Controllerها، Razor Pageها و Handlerهای Application نباید مستقیماً به `DbContext` دسترسی داشته باشند.
12. وضعیت رایگان بودن دوره/محصول باید از یک `Price` قابل‌Null مشتق شود.
13. `IsFree` نباید در پایگاه‌داده ذخیره شود.
14. احراز هویت مرورگر باید مبتنی بر Cookie باشد.
15. JWT نباید مکانیزم اصلی احراز هویت مرورگر باشد.
16. احراز هویت گوگل باید یک Session محلی احرازهویت‌شده مبتنی بر Cookie برقرار کند.
17. ارائه‌دهنده ساختگی پیامک باید یک پروژه API جداگانه باشد.
18. API پیامک باید از یک فروشگاه داده In-Memory استفاده کند.
19. API پیامک باید یک HTTP API شبیه ارائه‌دهنده واقعی افشا کند.
20. API پیامک باید یک داشبورد HTML برای بازرسی درخواست‌های پیامک فراهم کند.
21. سرویس ساختگی پیامک باید با یک پیاده‌سازی ارائه‌دهنده واقعی قابل جایگزینی باشد.
22. رندر فاکتور باید پشت یک انتزاع ایزوله شود.
23. لایه Domain نباید به کتابخانه‌های گزارش‌گیری/PDF ارجاع دهد.
24. Stimulsoft Reports.WEB کاندید فعلی ترجیح‌داده‌شده فاکتور/گزارش‌گیری است.
25. QuestPDF و FastReport .NET باید به‌عنوان جایگزین‌های مستندشده باقی بمانند.
26. داده فاکتور باید تصاویر لحظه‌ای مالی تاریخی را حفظ کند.
27. فاکتورهای نهایی‌شده نباید از طریق عملیات معمول CRUD تغییر کنند.
28. پردازش پرداخت باید Idempotent باقی بماند.
29. رکوردهای مالی نباید از طریق مدیریت عادی به‌صورت فیزیکی حذف شوند.
30. تمام اطلاعات حساس باید از لاگ‌ها و Cookieهای احراز هویت مستثنی بمانند.

## 94. اصول به‌روزشده پیاده‌سازی

پیاده‌سازی باید علاوه‌بر موارد قبلی از این اصول نیز پیروی کند:

* Soft Delete را بر حذف فیزیکی ترجیح دهید.
* اطلاعات حسابرسی را برای تغییرات مدیریتی حفظ کنید.
* مسیرهای Persistence خواندن و نوشتن را از هم جدا کنید.
* از Dapper برای Repositoryهای خواندن‌محور استفاده کنید.
* از EF Core برای Repositoryهای نوشتن‌محور استفاده کنید.
* یک Repository عمومی معرفی نکنید.
* یک فیلد افزونه `IsFree` را ذخیره نکنید.
* وضعیت رایگان بودن را از `Price` قابل‌Null مشتق کنید.
* از احراز هویت امن مبتنی بر Cookie برای مرورگر استفاده کنید.
* شبیه‌ساز پیامک را خارج از پردازه اصلی برنامه نگه دارید.
* شبیه‌ساز پیامک را به‌عنوان یک وابستگی خارجی HTTP در نظر بگیرید.
* وضعیت شبیه‌ساز پیامک را در حافظه ذخیره کنید.
* یک داشبورد ساده HTML برای بازرسی پیامک فراهم کنید.
* رندر فاکتور را مستقل از لایه Domain نگه دارید.
* Snapshotهای مالی غیرقابل‌تغییر را در فاکتورها حفظ کنید.
* جزئیات پیاده‌سازی اختصاصی ارائه‌دهنده را پشت انتزاع نگه دارید.
* وابستگی‌های کتابخانه گزارش‌گیری را در جایی که امکان دارد خارج از مدل‌های کسب‌وکاری Domain و Application نگه دارید.
* رکوردهای مالی تاریخی را به‌صورت فیزیکی حذف نکنید.
* اجازه ندهید فیلدهای حسابرسی توسط کلاینت ارائه شوند.

## 95. قواعد کسب‌وکار کوپن

1. اعتبار کوپن باید در زمان ایجاد سفارش، در سمت سرور مجدداً بررسی شود، نه فقط زمانی که کد برای اولین بار اعمال می‌شود، تا از سوءاستفاده از وضعیت کهنه یا شرایط رقابتی جلوگیری شود.
2. `UsedCount` باید به‌صورت اتمیک افزایش یابد تا از استفاده بیش از حد در درخواست‌های هم‌زمان جلوگیری شود.
3. یکتایی `Code` باید در لایه ذخیره‌سازی اعمال شود.
4. منطق محاسبه تخفیف (درصدی در مقابل مبلغ ثابت) باید در لایه دامنه قرار گیرد و نباید در لایه‌های اپلیکیشن یا ارائه تکرار شود.
5. محدودیت استفاده به ازای هر کاربر مستقیماً روی موجودیت Coupon مدل‌سازی نمی‌شود. در صورت نیاز، باید از طریق یک رکورد ردیابی استفاده جداگانه که Coupon، User و Order را به هم مرتبط می‌کند، اعمال شود.
6. فیلدهای Coupon باید از الزامات استاندارد حسابرسی و حذف نرم تعریف‌شده در بخش‌های ۷۸ و ۷۷ پیروی کنند.
7. یک سبد خرید و یک سفارش هر کدام حداکثر یک کوپن اعمال‌شده دارند.
8. یک کوپن فقط زمانی قابل اعمال است که تمام شرایط زیر برقرار باشند:
   * وجود داشته باشد و حذف نرم نشده باشد.
   * `IsActive` برابر `true` باشد.
   * زمان جاری UTC در بازه `StartDate` تا `EndDate` (با احتساب دو سر بازه) باشد.
   * `UsageLimit` تهی باشد یا `UsedCount < UsageLimit` برقرار باشد.
   * `MinOrderAmount` تهی باشد یا جمع جزء سبد خرید حداقل برابر `MinOrderAmount` باشد.
9. جمع جزء سبد خرید پس از تخفیف‌های سطح دوره و پیش از کوپن محاسبه می‌شود. مبالغ باید با این ترتیب محاسبه شوند:
   ```text
   قیمت دوره
       -> تخفیف سطح دوره (قیمت واحد مؤثر)
       -> جمع جزء
       -> تخفیف کوپن
       -> مبلغ قابل پرداخت
   ```
   * `Percentage`: تخفیف کوپن = جمع جزء × `Value` / 100.
   * `FixedAmount`: تخفیف کوپن = `Value`.
   * محاسبه باید از `decimal` و یک قاعده گردکردن مستندشده واحد استفاده کند.
10. کوپنی که تخفیف آن مبلغ قابل پرداخت را به صفر یا کمتر برساند قابل اعمال نیست. سفارش‌های با مبلغ صفر در این نسخه پشتیبانی نمی‌شوند.
11. کوپن روی کل سبد خرید اعمال می‌شود. محدودسازی به دوره‌ها یا دسته‌بندی‌های خاص مدل‌سازی نشده است. دوره‌های رایگان سهمی در جمع جزء ندارند.
12. استفاده از کوپن با افزایش `UsedCount` هنگام ایجاد سفارش، داخل تراکنش ایجاد سفارش و با یک به‌روزرسانی شرطی (`UsedCount < UsageLimit`) رزرو می‌شود تا درخواست‌های هم‌زمان نتوانند از سقف عبور کنند.
    * اگر سفارش `Failed` یا `Cancelled` شود، استفاده رزروشده باید دقیقاً یک‌بار آزاد شود و آزادسازی باید Idempotent باشد.
    * اگر سفارش `Paid` شود، استفاده مصرف‌شده باقی می‌ماند.
    * پردازش مجدد نتیجه پرداخت هرگز نباید `UsedCount` را تغییر دهد.
    * سفارش‌هایی که پس از انقضای خود در حالت `Pending` باقی بمانند مطابق بخش ۳۲.۱ لغو می‌شوند که استفاده رزروشده را آزاد می‌کند.
13. سفارش باید `CouponId` و `CouponDiscountAmount` را ذخیره کند. تغییر، انقضا یا حذف نرم کوپن در آینده نباید سفارش‌های موجود را تغییر دهد و سفارش‌های تاریخی همچنان باید بتوانند کوپن خود را شناسایی (Resolve) کنند.
14. کدهای کوپن باید Trim شوند و بدون حساسیت به حروف تطبیق داده شوند و قاعده یکتایی لایه ذخیره‌سازی (قاعده 3) باید با آن سازگار باشد. تلاش‌های اعمال باید Rate Limit شوند و پیام‌های شکست نمایش‌داده‌شده به کاربر باید از قواعد صفحه سبد خرید در بخش ۴۲ پیروی کنند.

## 96. تعریف انجام‌شده بازبینی‌شده (Definition of Done)

یک ویژگی زمانی کامل در نظر گرفته می‌شود که:

1. نیازمندی‌های Domain پیاده‌سازی شده باشند.
2. Command/Queryهای Application پیاده‌سازی شده باشند.
3. عملیات خواندن از مرز Repository خواندن استفاده کنند.
4. عملیات نوشتن از مرز Repository نوشتن استفاده کنند.
5. Repositoryهای خواندن از Dapper استفاده کنند.
6. Repositoryهای نوشتن از EF Core استفاده کنند.
7. هیچ Repository عمومی معرفی نشده باشد.
8. فیلدهای الزامی حسابرسی پر شده باشند.
9. Soft Delete در جایی که کاربرد دارد پیاده‌سازی شده باشد.
10. احراز هویت از مکانیزم مبتنی بر Cookie استفاده کند.
11. مجوزدهی بر پایه Permission باشد.
12. محدودیت‌های موردنیاز Persistence وجود داشته باشند.
13. رابط کاربری موردنیاز پیاده‌سازی شده باشد.
14. یکپارچه‌سازی پیامک در جایی که کاربرد دارد از مرز API خارجی پیامک استفاده کند.
15. رندر فاکتور پشت یک انتزاع ایزوله شده باشد.
16. Snapshotهای مالی حفظ شده باشند.
17. مدیریت خطا پیاده‌سازی شده باشد.
18. لاگ‌ها و تله‌متری مرتبط وجود داشته باشند.
19. تست‌های خودکار قواعد کسب‌وکاری مهم را پوشش دهند.
20. هیچ مرز معماری‌ای دور زده نشده باشد.
21. هیچ اطلاعات حساسی از طریق لاگ‌ها، Cookieها یا رابط کاربری فاش نشود.
22. پیاده‌سازی از تمام قواعد کسب‌وکاری الزامی تعریف‌شده در این SRS پیروی کند.
